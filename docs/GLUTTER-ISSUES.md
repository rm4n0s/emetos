# Glutter issues

Things Glutter is missing or gets wrong, found while building Emetos. Each entry says what is wrong, where Emetos works around it (if it does), and what the fix in Glutter would be. An entry is removed when the fix is in the Glutter version Emetos uses.

## No public way to draw a view off screen and to read its pixels (15.1)

- **What:** Remote Work (SPEC §10.18) needs a second view of a workspace that is drawn when it changes and gives its pixels to a goroutine that sends them. Glutter 1.8.3 has what is needed in pieces but none is public: the software renderer is `internal/gpu/soft` (only `gluttertest.Tester.Screenshot` reaches it), `ui.Scene.ToImage` and `ui.Picture.ToImage` take a `ui.Rasterizer` that no public package provides, the engine's windows are made from a platform (`ui.PlatformHost` is public but "apps never implement it"), and the fake platform of `gluttertest` keeps every scene it is given, for the life of the tester (`renderhost.Host.RenderView` appends to `scenes` and to `byView`, and `Tester.Scenes` copies the whole list), which is right for a test and a leak for a view that draws thirty times a second. The scenes themselves cannot be drawn on another goroutine: a paragraph is painted by asking the text engine that laid it out (`ui.ParagraphPainter.PaintParagraph`, through `textdraw.Expand`), and that engine's caches (`shapeCache.info`) are not safe for two goroutines, so a renderer on a goroutine of its own races with the layout of the next frame (found by `go test -race`).
- **Where the workaround is:** `internal/gui/app/headless_engine.go` (the `// Glutter:` comment above `rasterizer`): the view's binding is made by hand (`ui.NewPlatformDispatcher` over a four-method `ui.PlatformHost` of Emetos's own that keeps the latest scene only, `widgets.NewWidgetsBinding` with the UI thread of the application as its `UIThread`, driven by posting to the application's binding), and the pixels come from a `gluttertest.Tester` that is used as a rasterizer: `Tester.View.Render(scene)` then `Tester.Screenshot()`, with the tester replaced every eight frames so that it keeps few scenes. That makes `gluttertest` (and so the `testing` package and the `-update-goldens` flag of Glutter's golden helper) part of the editor binary, and the renderer runs on the UI thread of the application: a 1280x800 picture takes about 85 ms of it (the rest of a frame, build, layout and paint, takes under 3 ms), so a view makes a frame at most every twice the time the last picture took (`headlessPaceFactor`) and its caret does not blink.
- **What Glutter could provide:** a public software `ui.Rasterizer` (for example `ui.NewSoftwareRasterizer()`, or `rendering.SoftwareRasterizer`) that holds no scene after it returns; text painting that does not depend on the layout engine's caches once a paragraph is laid out (the glyph outlines the paragraph needs copied into it, or the caches guarded), so that a scene can be drawn on any goroutine; a public offscreen host (`ui.NewOffscreenView(size)`: a dispatcher and a view whose `Render` calls a function) for apps that draw a view into pixels; and, because the software renderer redraws the whole scene whatever changed, a damage rectangle (`soft.Render` of a clipped region, or a scene that says which layers changed) so that a typed character does not cost 85 ms.
