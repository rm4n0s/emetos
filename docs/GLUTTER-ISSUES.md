# Glutter issues

Things Glutter is missing or gets wrong, found while building Emetos. Each entry says what is wrong, where Emetos works around it (if it does), and what the fix in Glutter would be. An entry is removed when the fix is in the Glutter version Emetos uses.

## Cold start is dominated by the first draw (3.11)

- **What:** from the start of the process to the first presented frame takes about 0.85 s in a headless compositor with software GL (llvmpipe), against the 400 ms target of SPEC §14. Glutter's own `examples/counter` takes 0.93 s in the same run, so none of it is Emetos's: the build of Emetos's first frame is 0.05 ms, and the whole startup before the first draw is under 30 ms. The log of `GLUTTER_FRAME_STATS=1` puts 0.85 s of it in the startup stage "first draw (renderer, GL context, shaders, first frame)". Before it, the Vulkan renderer is tried and given up (`VulkanSwapchainFailed`: "the swapchain of the window cannot be made or used") on the headless compositor, and then the GLES renderer makes its context and compiles its shaders; with a cold Mesa shader cache the first run takes 1.2 s.
- **Where the workaround is:** none; there is nothing to work around in Emetos. `scripts/perf.sh` keeps the Mesa shader cache between its runs and warms it first, so the numbers are not those of a cache that has just been emptied.
- **What Glutter could provide:** compile the shaders lazily or in parallel with the creation of the window, draw the first frame before the shaders of the rarer paths are ready, and cache the compiled programs itself (its own cache next to the Mesa one); report the time of each part of the first draw so a start can be profiled below the single "first draw" figure.
- **Status:** headless numbers don't decide (SPEC §14); the figure with the GPU is the manual check `scripts/perf.sh --session` (`docs/MANUAL-CHECKS.md`). Step 3.11 went on without a decision from the user, see its entry in `docs/IMPLEMENTED.md`.

## A headless compositor gives its windows no keyboard focus events (3.11)

- **What:** the headless sway (`scripts/headless-wayland.sh`) has no keyboard, so a Glutter window never receives `ViewFocusStateFocused` or `Unfocused`: `WidgetsBindingObserver.DidChangeViewFocus` is never called, however many windows are open. A window is assumed focused until told otherwise. The idle-and-unfocused target (no frames at all, SPEC §14) cannot be measured headless.
- **Where the workaround is:** `scripts/perf.sh` measures that one only with `--session`; the unit tests send the focus events through `gluttertest`.
- **What Glutter could provide:** an initial `ViewFocusEvent` when a window is created (so the app knows whether it has the focus), and, for a seat without a keyboard, a way to follow the compositor's active window (xdg-toplevel state `activated`) as the focus of the window.

## RawTooltip cannot take a hover delay that changes, report its hiding or be driven from outside (6.1)

- **What:** `widgets.RawTooltip` reads `HoverDelay` from its options, so the delay cannot depend on the moment the pointer enters (VS Code shows a hover at once when another hover hid less than 200 ms ago); it has no callback for "hidden" (needed to start that 200 ms); its state exposes `EnsureTooltipVisible` but no `Hide` and no constructor that gives the caller the state, so the keyboard navigation of an action bar cannot show the tooltip of the item that got the focus; and nothing dismisses a tooltip on a key press (Escape) without the caller finding the state.
- **Where the workaround is:** `kit.Hover` (`internal/gui/kit/hover.go`, the `// Glutter:` comment above the type) builds its own `OverlayPortal` with `NewOverlayPortalOverlayChildLayoutBuilder`, the way RawTooltip does, and adds the delay rule, a `HoverController`, a `HoverDelegate` shared by a group of hovers and a hardware keyboard handler that hides the hover.
- **What Glutter could provide:** `RawTooltipOpts.HoverDelayFunc func() time.Duration` (read when the pointer enters), `OnShown` and `OnHidden` callbacks, and a `RawTooltipController` (`Show`, `Hide`, `IsShowing`) that can be passed in the options; plus a `DismissOnKey` option that hides the tooltip on a key down without handling the key.

## A pressed pointer does not keep the cursor of the region it was pressed on (6.2)

- **What:** the mouse cursor is chosen by the `MouseRegion` the pointer is over now. While a sash is dragged, the pointer can outrun it (a pane that cannot shrink any more stops the sash) and the cursor falls back to the one of whatever is under the pointer, though VS Code keeps the resize cursor for the whole drag (`* { cursor: ... !important }`).
- **Where the workaround is:** `SplitView` (`internal/gui/kit/splitview.go`, the `// Glutter:` comment in `content`) puts one `MouseRegion` over the whole split view, always there so that the panes keep their state, and gives it the cursor of the sash while a sash is dragged. It does not cover a pane that sets a cursor of its own (a text editor's I-beam) and it ends at the edge of the split view.
- **What Glutter could provide:** a way for a pointer that is pressed to keep the cursor of the region it was pressed on until it is released (`MouseRegionOpts.HoldCursorWhilePressed`), or an app-wide cursor override that a widget can set and clear.

## TreeSliver cannot remove nodes, toggles only nodes with children and keeps the expansion in its nodes (6.4)

- **What:** `widgets.TreeSliver` keeps whether a node is expanded in the node (`TreeSliverNode.expanded`) and offers `AddChild` but no way to remove or replace a child, to give a lazy folder a chevron without children (`toggleNode` does nothing for a node with no children, and `NewTreeSliverNode` is never expanded without children), to expand a node of a tree that is built again except through the node's own options, or to look a node up by anything but `reflect.DeepEqual` of its content (`TreeSliverController.GetNodeFor`, `IsExpanded`). It draws no focus, selection or hover and has no keyboard, which is as it should be; those are the app's.
- **Where the workaround is:** `kit.Tree` (`internal/gui/kit/tree.go`, the `// Glutter:` comment above `glutterNodes`): the `TreeModel` owns the expansion state by key, and every change of the model builds the nodes again (only the expanded part has children; a node that is not read, or is loading, has one placeholder child), so Glutter's own toggling, controller and animation are not used (`AnimationStyleNoAnimation`, `TreeSliverIndentationTypeNone`); the content of a node is `treeContent{Key}`.
- **What Glutter could provide:** `TreeSliverNode.SetChildren`/`RemoveChild`, a `TreeSliverNode` option `HasChildren` (or a `Lazy` flag) that makes a node toggleable without children and tells the sliver to ask for them, and `TreeSliverOpts.NodeEqual func(a, b T) bool` (or a key function) in place of `reflect.DeepEqual`. With those a tree could keep its nodes between changes instead of making them again.

## Draggable starts a mouse drag after 1 px, cannot be cancelled from the keyboard and DragTarget reports no position while the pointer rests (6.4b, 6.10)

- **What:** `widgets.Draggable` starts its drag with `MultiDragGestureRecognizer`, whose slop for a mouse is `PrecisePointerHitSlop` (1 px) and cannot be set: a click on a row of a list with a hand that moves one pixel becomes a drag and loses its tap. A running drag (`dragAvatar`) has no way to be cancelled other than the pointer's own cancel (Escape does nothing), and `DragTarget` calls `OnMove` only when the pointer moves, so nothing can scroll a list while the pointer rests near its edge or expand a folder after a delay without its own timer and the position.
- **Where the workaround is:** `dragController` in `internal/gui/kit/listdnd.go` (the `// Glutter:` comment above the type): the drag is built on the pointer events of a `Listener` around the rows (with `HitTestBehaviorTranslucent`: the non-opaque `MouseRegion` of `ScrollableElement` makes the hit test of the rows report "not hit" to what is above it, so a defer-to-child `Listener` would be left out of the path of the press and never see the moves; see `list.go` and `tree.go`), with its own 4 px slop, timers of the binding for the auto-expand and the scrolling, and Escape handled by the list's key handler.
- **Also in step 6.10:** the drag of a tab is built the same way: `tabState.move` in `internal/gui/kit/tabs.go` (the `// Glutter:` comment) starts it after 4 px on the pointer events of the tab's `Listener` and cancels it with a keyboard handler of the binding for Escape; the strips and the editor areas that a tab can be dropped on are found by their places on the screen (`kit.Bounds`, `kit.TabsController`), because a `DragTarget` would report no move while the pointer rests at the end of a strip that has to scroll (`shellState.scrollNearEdge` in `internal/gui/app/tabdrag.go`, a timer of the binding).
- **What Glutter could provide:** `DraggableOpts.Slop` (or a gesture setting for the mouse slop), `DraggableOpts.CancelOnEscape` or a `DragController.Cancel()`, a per-frame callback or a repeating `OnMove` for a `DragTarget` while a drag is over it.

## BaseWindowController has no SetTitle, and the fake platform does not record the title of the implicit view (6.6)

- **What:** `widgets.WindowScope.Controller()` of the first window is a `BaseWindowController`, whose interface has no `SetTitle` (nor `SetSize`...): they exist on `RegularWindowController`, promoted from an unexported base struct, so only an interface assertion reaches them. `gluttertest.Tester.Windows()` lists the windows the app asked for with controllers and leaves the implicit view out, so a test cannot see the title the app set on the first window.
- **Where the workaround is:** `shellState.syncTitle` in `internal/gui/app/app.go` (the `// Glutter:` comment): it asserts `interface{ SetTitle(string) }` on the controller and calls it after the title of the window changed. The tests check the title the window computed (`Window.Title`), not the one the platform got.
- **What Glutter could provide:** `SetTitle` (and `Title`) in `BaseWindowController` or in an exported `TitledWindowController` interface, and the implicit view in `Tester.Windows()` (or `Tester.ViewTitle(view)`), so that the title can be asserted.

## gluttertest.Tester does not dispose the widget tree when a test ends (6.13)

- **What:** at the end of a test the `Tester` cancels the context of its binding but does not unmount the tree, so `State.Dispose` is never called and the `Lifetime()` of the states is not cancelled. A state that starts something that holds an operating system resource for its lifetime (here the inotify instance of the file watcher, started through `State.Lifetime()`) leaves it behind for every test that pumps the shell; after about a hundred such tests inotify's `max_user_instances` (128 by default) is used up and later tests fail with "too many open files".
- **Where the workaround is:** `ProcessOptions.WatchFiles` (`internal/gui/app/process.go`, the `// Glutter:` comment): the shell starts the watcher only when the process asks for it; the editor does, tests leave it off, and the tests of the watcher start it themselves with a context they cancel.
- **Second workaround:** `testutil.New` (`internal/gui/testutil/testutil.go`, the `// Glutter:` comment) registers a cleanup that pumps an empty widget, so the tree of every UI test of Emetos is unmounted when the test ends. Without it the app package kept every window of every test alive (about 11 goroutines and the whole window each) and ran 2.9 times slower under `-race` (821 s against 282 s). The `States` of the app save the window and the binding in `InitState`, because `Dispose` cannot look up an ancestor.
- **What Glutter could provide:** `Tester` unmounting the root (or cancelling the lifetimes of the states) in its cleanup, so that `Dispose` runs and the goroutines and descriptors of the states end with the test.

## FakeDesktop cannot make the file chooser portal unavailable (7.1)

- **What:** `gluttertest.Tester.FakeDesktop()` always answers the file chooser portal (`AnswerFileChooser`, `CancelFileChooser`); there is no way to get the `FileChooserUnavailable` failure that a desktop without the portal gives, and without a fake desktop a test would reach for the user's real session bus. The save dialog of Emetos falls back to a prompt for the path on exactly that failure.
- **Where the workaround is:** `Window.SaveDialog` in `internal/gui/app/window.go` (the `// Glutter:` comment): tests replace the dialog with a function that returns an error whose cause has the tag `FileChooserUnavailable`; the real call and the answers of the fake portal are tested through the default.
- **What Glutter could provide:** `FakeDesktop.DisableFileChooser()` (or an option of `FakeDesktop`) that makes the portal calls fail with `FileChooserUnavailable`.

## The request to close the implicit first window reaches the app without the window (7.2)

- **What:** `widgets.WindowingOwner.handleCloseRequested` hands the close request of a window to the delegate of its `RegularWindowController` (`OnWindowCloseRequested`), but not for the window of the implicit controller (the first window, the one `RunApp` opens): its request goes to `PlatformDispatcher.OnExitRequested`, which the binding turns into `HandleRequestAppExit`, and the observers' `DidRequestAppExit()` (the `AppLifecycleListener.OnExitRequested` callback) takes no view ID. An app with several windows cannot tell which window was closed when it is the first one, and the implicit window has no delegate to replace (its controller's delegate is the base one and is skipped), so a window that is asked to close with unsaved changes cannot be told apart from another one.
- **Where the workaround is:** `shellState.initClosing` (`internal/gui/app/closing.go`, the `// Glutter:` comment): the shell listens with an `AppLifecycleListener`, answers `AppExitResponseCancel` at once and runs the per-window flow (`Window.RequestClose`: the dialog, the saves, then `Window.Quit`, which ends the app with `ExitApplication(AppExitTypeRequired)`). That is right while the process has one window; step 7.8 gives every other window a regular window controller whose delegate calls `Window.RequestClose` and then `controller.Destroy()`, and then the first window is the only one that goes through the observer.
- **What Glutter could provide:** pass the `ViewID` to `WidgetsBindingObserver.DidRequestAppExit` (or add `DidRequestWindowClose(view)`), or hand the close request of the implicit window to its controller's delegate like any other window's, so the app can decide per window.
