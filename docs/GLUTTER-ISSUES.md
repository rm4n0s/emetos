# Glutter issues

Things Glutter is missing or gets wrong, found while building Emetos. Each entry says what is wrong, where Emetos works around it (if it does), and what the fix in Glutter would be. An entry is removed when the fix is in the Glutter version Emetos uses.

## Cold start headless: the Vulkan renderer is tried first and given up (3.11, 9b.1b)

- **What:** Glutter 1.7 (27.10) splits the first draw in the log (`GLUTTER_FRAME_STATS=1`) and keeps GLES program binaries in `$XDG_CACHE_HOME/glutter/shaders`. With them `scripts/perf.sh` shows where the start goes on the headless compositor (software GL): 560 to 600 ms of about 850 ms is the Vulkan renderer being tried and given up (`VulkanSwapchainFailed`: "the swapchain of the window cannot be made or used", the compositor presents no GPU buffers), 140 ms the GLES context, 20 to 30 ms the shaders (2 programs, 32 ms from Glutter's cache against 45 ms built with Mesa's cache warm) and 20 ms the frame. Glutter's own counter takes 30 to 50 ms longer than Emetos in the same runs, so none of it is Emetos's. The target of SPEC §14 is 400 ms.
- **Where the workaround is:** none; there is nothing to work around in Emetos. `scripts/perf.sh` reports the three states of the caches and the parts of the first draw.
- **What Glutter could provide:** try GLES first where Vulkan presents to no output, or find that out before the swapchain is made (Glutter's 27.10 entry measured 320 ms against 960 ms with `GLUTTER_RENDERER=gles`); its release notes ask the owner to decide.
- **Status:** headless numbers don't decide (SPEC §14); the figure with the GPU is the manual check `scripts/perf.sh --session` (`docs/MANUAL-CHECKS.md`), where Vulkan works and the try costs nothing.

## A character no font has makes Glutter load every font of the style: the tab (10.1)

- **What:** Glutter 1.7 (`internal/text/layout`, `styleFonts.ResolveFace`) looks for a face with a glyph for each rune it shapes, in the order of the font files of the style, and when none has one it loads **all** of them (each font is parsed whole, outlines included: `font.NewFont` -> `tables.ParseGlyf`) before it asks the system for a fallback and, failing that, draws the first face's missing-glyph box. A tab has a glyph in no font, so the first row of text that has a tab (every Go file) loaded the 62 files that fontconfig lists for `monospace` on the development machine: 116 MB on disk (a 32 MB CJK collection among them), 170 MB of live Go heap, and 300 MB more resident memory (849 MB against 525 MB with the same 10,000-line file, headless), plus the time to parse them on the UI thread in the first frame. The result is cached per rune, so it happens once per style, but the fonts stay. Evidence: heap profile (`EMETOS_PROFILE_DIR`, `cmd/emetos/profile_dev.go`) with 100 MB in `opentype.(*Loader).findTableBuffer` and 41 MB in `tables.ParseGlyf`, all under `layout.(*styleFonts).ResolveFace` <- `splitByFace` <- `BuildParagraph`; a build with a `println` in `Collection.load` showed the 62 paths; the log of the same build with the workaround shows two (`AdwaitaSans`, `AdwaitaMono`). Any text with a control character or a character that no installed font has (an unassigned code point, a private-use character) does the same.
- **Where the workaround is:** `fonts.ControlsFont` (`internal/gui/kit/fonts/controls.go`: a TrueType font of under 300 bytes with two empty glyphs, `.notdef` and one for U+0009, loaded under the family `fonts.Controls`) and `textStyle.families` (`internal/gui/editor/text.go`, the `// Glutter:` comment): a row that has a tab gets that family before the editor's own, so the tab is found in the first file. The paragraph's own family (which measures the tab stop with the width of a space) stays the editor's, and `TestTheFontOfTheTabChangesNoMeasure` pins that widths and heights are what they were.
- **What Glutter could provide:** resolve the control characters (U+0009 and the other `Cc`, and the default-ignorable ones) to the first face without the search, as every shaper does (HarfBuzz takes them out of the run); and, for any other rune, check the coverage of a candidate from its `cmap` only (what `fontscan` footprints already hold: `fp.Runes.Contains(r)`) before parsing the font, and parse the outlines lazily (a glyph the first time it is drawn), so that a font that only covers a script costs nothing until its script is shown. Loading fonts whose `cmap` says they cannot have the glyph is the waste.

## TreeSliver cannot set the expansion of a node that exists (6.4, 9b.1b)

- **What:** Glutter 1.7 (27.9) lets an app change the children of a node (`InsertChild`, `RemoveChild`, `SetChildren`), make a node lazy (`HasChildren`) and key the contents (`TreeSliverOpts.NodeKey`). The expansion is still held by the node (`TreeSliverNode.expanded`) and can be given only when the node is made (`TreeSliverNodeOpts.Expanded`), or toggled for a node that is shown (`TreeSliverController.ExpandNode`/`CollapseNode`, which also animate). `kit.Tree` keeps the expansion in its model, by key, also of the nodes that are not shown and of the find filter (`shownExpanded`), so it cannot keep its nodes between changes: the model's state would have to be written to the nodes that are hidden. With `NodeKey` set, a tree built again with new nodes keeps the expansion of the old nodes of the same key, which undoes the model's (tried in step 9b.1b: the toggling, reveal and rebuild tests of the tree fail).
- **Where the workaround is:** `kit.Tree` (`internal/gui/kit/tree.go`, the `// Glutter:` comment above `glutterNodes`): every change of the model builds the nodes again (only the expanded part has children; a node that is not read has one placeholder child), and Glutter's own toggling, controller and animation are not used (`AnimationStyleNoAnimation`, `TreeSliverIndentationTypeNone`); the content of a node is `treeContent{Key}`.
- **What Glutter could provide:** a way for the app to say which nodes are expanded without making them again: `TreeSliverNode.SetExpanded(bool)` (also for a node that is not shown), or `TreeSliverOpts.IsExpanded func(content T) bool` read when the active nodes are made. With either, the tree could keep its nodes and change them with `SetChildren`.

## WindowDecoration: the whole bar is the drag area (9b.2)

- **What:** `widgets.WindowDecoration` (Glutter 1.7, 27.4) wraps the row of `Leading`, `Title` and `Actions` in one `GestureDetector` that moves the window on a pan, maximizes or restores it on a double tap and shows the window menu on a secondary tap. An app that puts widgets of its own in the bar (Emetos: the menu button, the workspace tabs and the `+` button) gets those gestures on them too: a drag of a tab would move the window, a double click on a tab maximize it, and a right click on a tab ask for the window menu next to the tab's own context menu.
- **Where the workaround is:** `workspaceStripState.Build` in `internal/gui/workbench/titlebar.go` (the `// Glutter:` comment): the strip is wrapped in a `GestureDetector` with no-op `OnPanStart`, `OnDoubleTap` and `OnSecondaryTapDown`, which win the gesture arena over the decoration's detectors, because they are deeper in the tree. The tabs and the `+` button read raw pointer events (`Listener`), which the arena does not touch, so a plain click is not delayed by the double tap of the window.
- **What Glutter could provide:** a way to say which part of the bar is the draggable one: for example `WindowDecorationOpts.Leading` and `Actions` outside the detector (only `Title` inside), or `WindowDecorationOpts.DragArea Widget`; or a `NoDrag` marker widget that the detector's hit test skips.

## No error boundary: the host cannot tell whose widget failed (11.5)

- **What:** Glutter 1.7 contains a panic in `Build` at the element that panicked: the widget is replaced with an error widget (`BuildOwner.ErrorWidgetBuilder`, one for the whole application) and the error goes to `OnError`. The error carries the element and the chain of its creators as text, but nothing in Glutter lets a widget say "the build errors of my subtree are mine": there is no error boundary. Emetos's views of extensions (SPEC §10.15) have to show "<Name> failed" and deactivate the extension in that tab when the widget an extension built fails, and a panic deeper than the extension's own `Build` function (in a widget it built, or in one of the `State`s it wrote) is invisible to the box.
- **Where the workaround is:** `ui.NewBuilder` (`extension/ui/box.go`, the `// Glutter:` comment): a builder with a `recover` that reports to the box above it (`ui.BoxScope`), which fails the extension; and the `recover` in the box around the extension's `Build` function (`internal/gui/exthost/box.go`). A panic that neither covers gets Glutter's error widget in its place and a line in the log, and the extension stays on.
- **What Glutter could provide:** an error boundary: `widgets.NewErrorBoundary(child, func(err error) Widget)` (or `ErrorBoundaryOpts.OnError`), a widget that is told of the build errors of its subtree before the owner's `OnError` and builds the widget that takes the failed subtree's place.
