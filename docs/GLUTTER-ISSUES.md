# Glutter issues

Things Glutter is missing or gets wrong, found while building Emetos. Each entry says what is wrong, where Emetos works around it (if it does), and what the fix in Glutter would be. An entry is removed when the fix is in the Glutter version Emetos uses.

## The frame that handles an input event asks for a second frame, which draws nothing new (Glutter 1.9.4 to 1.9.5)

- **What:** `handler.OnFrame` (`internal/engine/engine.go`) clears the window's wish for a frame, flushes the queued input events (a key, a click), and then begins the frame. The widgets that the events change call `SetState`, which reaches `SchedulerBinding.ScheduleFrame` and `window.RequestFrame` (Wayland: `frameRequested = true`) while the frame is already on its way to build those very changes. The request is not taken back at the start of the frame, so every frame that handles an input event is followed by a second frame, which builds and draws nothing new. Under the software renderer of the headless runs (llvmpipe, 16 to 19 ms for a 1280x800 window) a held key at 50 repeats a second needs one frame in 20 ms and gets two, so the editor types about 31 characters in the second the compositor announces 50 for (`TestDesktopFastKeysHeld`); on a GPU the second frame is only a waste of power. With the request cleared after the flush (a patch of a copy of Glutter 1.9.4, `ClearFrameRequest` on the window, called by `OnFrame` after `input.flush()`) the editor types 51 characters in that second at the full window size.
- **Where the workaround is:** none for the second frame itself. Emetos removed the other frames a key caused (the scrollbars of `kit.ScrollableElement`, the repaint for the tokens the frame made, the delivery of fast extension events, the status bar and the breadcrumbs, `kit.RebuildSoon`), so that this one is the only one left; `TestDesktopFastKeysHeld` draws a window of 640x400 px (marked with a `// Glutter:` comment), where the two frames fit in the period.
- **What Glutter could provide:** `OnFrame` takes back the frame request that the flush of the input made (the engine clears `wanted`, and the platform window `frameRequested`, after `input.flush()` and before `BeginFrame`), as Flutter's `ensureVisualUpdate` ignores a request made while a frame is being produced.

## A key that repeats is paced from when the last repeat was handled, not from when it was due (Glutter 1.9.4 to 1.9.5)

- **What:** `keyboard.fireRepeat` (`internal/platform/linux/wayland/keyboard.go`) hands over a repeat and then sets the timer of the next one for a period (`1/rate` of a second) from that moment. A repeat that is late, because the loop was busy drawing a frame, makes every later repeat late too, and the lateness adds up in each period: the rate of the characters is lower than the rate the compositor announces by the time the loop is busy in every period. With 18 ms frames and a period of 20 ms the timer fired 16 ms late and the period was 36 ms, which is 28 characters a second for an announced 50.
- **Where the workaround is:** none. Emetos keeps its frames cheap instead (see the entry above); it cannot reach the timer.
- **What Glutter could provide:** a fixed-rate timer: each repeat is scheduled from the due time of the previous one (`due += period`), and repeats that are more than one period late are skipped or coalesced into one, so that the rate stays the announced one while the loop keeps up and a loop that does not keep up does not queue repeats.

## The clipboard carries plain text only (Glutter 1.9.4 to 1.9.5)

- **What:** `services.Clipboard` reads and writes one string (`text/plain`); there is no way to put a second representation such as `text/html` on the clipboard. The terminal's **Copy Output as HTML** (step 17d.5, `workbench.action.terminal.copyLastCommandOutput` and the decoration's menu) is meant to give a rich editor formatted text with the colors of the terminal; with plain text only, the HTML markup itself is what is pasted.
- **Where the workaround is:** `paneView.outputHTML` and `paneView.copyText` in `extensions/terminal/shell_pane.go` (the markup is copied as text, with a `// Glutter:` comment).
- **What Glutter could provide:** `Clipboard.SetData(map[mimeType][]byte)` (and a matching read), with the Wayland data offer and the X11 selection offering every type.

## An EditableText stays scrolled out of range for about a second after its text gets shorter (Glutter 1.9.4 to 1.9.5)

- **What:** a single-line field whose text is longer than the field scrolls to the caret with an animation of 100 ms (`scheduleShowCaretOnScreen`). When the text is replaced by a shorter one (a controller's `SetValue`), the scroll extent shrinks and the position is out of range (offset 278 of a maximum of 0). Glutter, as Flutter, brings it back with the ballistic spring of `ScrollPhysics`, which takes about a second, and an animation that was still running keeps going toward its old target. For that time a text that fits is shown with its start cut off (the quick input's path prompt showed `o/such/folder/new.go` for `/no/such/folder/new.go`), and a text that is still too long shows blank space after its end.
- **Where the workaround is:** `inputBoxState.settleScroll` in `internal/gui/kit/inputbox.go` (with a `// Glutter:` comment). The box owns the `ScrollController` and, after the frame that laid out the new text, shows the caret (when it has the focus) and jumps a position that is out of range to the nearest end, which also stops the spring and the animation. It costs one frame with the old offset. It covers `InputBoxController.SetValue` and the history, not a change of a controller that the owner makes directly. `TestInputBoxSetValueScrollsBack` is the test.
- **What Glutter could provide:** an `EditableText` that, when its text changes, stops the caret animation and, when the layout shrinks the extent, corrects an out-of-range position at once (`correctPixels`) instead of with the spring, in the same frame as the layout.
