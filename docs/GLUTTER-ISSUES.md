# Glutter issues

Things Glutter is missing or gets wrong, found while building Emetos. Each entry says what is wrong, where Emetos works around it (if it does), and what the fix in Glutter would be. An entry is removed when the fix is in the Glutter version Emetos uses.

## A reverse list does not keep what the user reads in place when items are added at its start (16.3)

- **What:** the Events panel of the Relay tab (SPEC §10.19) is a live log whose newest row is at the bottom and which follows the newest row while the user is at the end. A `widgets.ListView` with `Reverse: true` does that (offset 0 is the newest row), but its offset is measured from item 0, so when rows are added at item 0 and the user has scrolled up to read an older row, that row moves away by the height of the new rows. Glutter 1.9.1 (checked again: nothing in 1.9.x touches it) has nothing to keep the content in place (an anchor item, or a "maintain scroll offset" option; `ScrollView.Anchor` is Flutter's anchor of the zero offset, not that); `SliverList` has no `maintainScrollOffset` either.
- **Where the workaround is:** `extensions/relay/clienttab.go` (`keepPlace`, with the `// Glutter:` comment): after the rows are added it moves the offset with `ScrollController.JumpTo` by the number of added rows times the height of a row (every row that arrives is collapsed, and the extent of each row is known, so the sum is exact), and only when the offset is not 0 (the user is not at the end).
- **What Glutter could provide:** a `ListView`/`SliverList` option that keeps the first visible item in place when items are inserted before it (the scroll offset changes by the extent of what was inserted), for logs, chats and feeds.

## An `offscreen.View` has no clipboard of its own (Glutter 1.9.1)

- **What:** the clipboard calls of an `offscreen.View` go to the clipboard of its parent binding (`viewHost.SetClipboardText` and the others call `parent.PlatformDispatcher()`), which is the application's, and `WidgetsBinding.Clipboard()` has no way to be replaced. A view that another machine types in (Remote Work, SPEC §10.18) must not read the clipboard or the primary selection of the desktop of the host or replace them, and its client must be told of the text its user copies and be able to give it the text to paste (`HeadlessView.OnCopy`, `SetClipboard`). Glutter's `EditableText` (every input box) reaches the clipboard through `WidgetsBindingOf(ctx).Clipboard()` and its own state methods, so it cannot be redirected with actions.
- **Where the workaround is:** `internal/gui/app/headless_clipboard.go` (`viewClipboard`, `clipboardHost`, `newClipboardParent`, with the `// Glutter:` comment): the parent of the view is not the application's binding but a binding of its own that never draws, with the same UI thread, error reporter, debug flags, assets and text engine, whose platform host is the view's clipboard. Every clipboard path of the view is then the view's, with no widget changed (the editors, the input boxes, the primary selection, the paste check); the tests assert that the host's clipboard and primary selection are neither read nor written.
- **What Glutter could provide:** an option of `offscreen.ViewOpts` for a `ui.ClipboardHost`/`ui.RichClipboardHost` that the view's dispatcher uses in place of the parent's; `clipboardParent` is then not needed.

## An `offscreen.View` starts with a default platform configuration and a blank window (Glutter 1.9.1)

- **What:** the view's platform configuration (fonts, locales, text scale, brightness, caret blink time) is the default one, not the application's (Glutter's own step 29.7 lists it as a follow-up), and its `ui.ViewConfiguration` has a blank `Window` (no decoration, not activated, not maximized), which an app that draws its own title bar and its inactive state reads. `ViewOpts` cannot set either, and `View.SetSize` writes the view's own copy of the configuration with a blank `Window` again, so a window set by `UpdateViewConfiguration` is lost at the next resize. The tree is mounted inside `NewView`, so a state that reads the configuration in `InitState` sees the default one unless something sets it first.
- **Where the workaround is:** `internal/gui/app/headless.go` (`viewSetup`, `configure` and `applyWindow`, with the `// Glutter:` comment): the root of the view is a widget whose `InitState` (it starts before the shell's) calls `UpdatePlatformConfiguration` with the application's values and `UpdateViewConfiguration` with the window, and `Resize` calls `applyWindow` after `SetSize`.
- **What Glutter could provide:** `ViewOpts` with the platform configuration and the `ui.WindowInfo` of the view (or a copy of the parent's configuration, following its changes), and `SetSize` that keeps the rest of the view's configuration.

## `testing` is linked into every Glutter program (Glutter 1.9.1)

- **What:** `internal/platform/linux/dl/layout.go` is not a test file and imports `testing` (for `AssertLayout`), so every program that links the Linux platform, the editor included, links the `testing` package. `go list -deps ./cmd/emetos | grep -E '^testing$'` prints it. It registers no flags (Go does that in a test binary only), so it costs size and nothing else.
- **Where the workaround is:** none.
- **What Glutter could provide:** `AssertLayout` in a `_test.go` file or in a test helper package.

## An `EditableText` mounted again with the focus on its node gets no input connection, and nothing brings one back (Glutter 1.9.1)

- **What:** `EditableTextState` opens its input connection only when the focus changes (`handleFocusChanged` -> `openOrCloseInputConnectionIfNeeded`, as Flutter's does). A field that is mounted (or its state made again) while its `FocusNode` already has the focus shows the focus and the caret, and takes no key: `services.TextInput.HandleUnhandledKey` has no client. Flutter's `TextField` repairs it with a tap (its gesture detector calls `requestKeyboard`), but the raw `EditableText` of Glutter has no pointer handling that does, and a tap on a raw `EditableText` does not even change the selection (the `RenderEditable`'s tap recognizer calls `onSelectionChanged` only when it wins the arena, which the test of Emetos never saw). This is how the desktop test of 2026-10-27 lost every key after the first in each empty input box with a placeholder (Emetos removed a `Stack` and mounted the field again).
- **Where the workaround is:** `internal/gui/kit/inputbox.go`: the tree of the box is the same with or without the placeholder (the field is never mounted again while it is typed in), and `pointerDown` (a `Listener` around the field, with the `// Glutter:` comment in `Build`) calls `EditableTextState.RequestKeyboard` when a click lands in a box that has the primary focus. `kit.TypeAhead` and the keys of the quick input (`typeAhead`) cover the frame between a shortcut and the field that it opens.
- **What Glutter could provide:** `EditableTextState` opening the connection in `InitState`/`DidChangeDependencies` (after the first layout) when its node has the primary focus and no connection exists, or when `FocusNode.ConsumeKeyboardToken` is pending at mount.

## The caret of an obscured `EditableText` is placed by byte offsets into the string of bullets (Glutter 1.9.1)

- **What:** with `ObscureText`, `EditableTextState` shows `strings.Repeat(ObscuringCharacter, GraphemeCount(text))` (editable_text_state.go) but the selection and the caret keep the byte offsets of the real text. The default obscuring character is the bullet U+2022, three bytes in UTF-8, so after "secret" (offset 6) the caret is drawn after two bullets (offset 6 of an 18-byte string) instead of after six; with text that is not ASCII it is wrong in another way. It showed once the input boxes stopped being mounted again at their first key (the golden of the passphrase dialog drew the caret at 16 px instead of 48).
- **Where the workaround is:** `internal/gui/kit/inputbox.go` (`Build`, with the `// Glutter:` comment): `ObscuringCharacter: "*"`, a one-byte character, so the offsets agree for ASCII text. Passphrases and keys that are not ASCII still place the caret wrong.
- **What Glutter could provide:** the render object (or the field) converting the selection offsets of the real text into offsets of the obscured string, by grapheme; the workaround and its asterisk can then go, and the box shows bullets again.

## A `SliverList` lays out every item between the first one it has and the offset of a jump (Glutter 1.9.1)

- **What:** `RenderSliverList.PerformLayout` finds the first child at the scroll offset from the children it already has and adds more with `InsertAndLayoutChild` (as Flutter's does), so a jump of the offset into a list whose items have different heights (the Markdown preview of a document of 3000 blocks: a click on the scroll bar, a line) builds, lays out and drops every item between the first one it has and the target, in one frame. `ItemExtentBuilder` would give the position of any item at once, but it forces the extent of each child, which is not known before it is laid out (a paragraph's height depends on its text and the width).
- **Where the workaround is:** `extension/ui/markdown/preview.go` (`previewState`, `blockLayout`, with the `// Glutter:` comment): the list is a `CustomMultiChildLayout` of the blocks near the viewport only, chosen from a Fenwick tree of heights (measured, or estimated until a block has been laid out) and positioned from an anchor block, so a jump costs the blocks of one window. `kit.ScrollableElement` with a `ScrollModel` gives the scroll bar and the wheel.
- **What Glutter could provide:** a sliver list (or an option of `SliverList`) that estimates the position of an item it has never laid out (an average of the extents it knows, as `estimateMaxScrollOffset` already does for the end of the list) and starts its layout there, correcting the scroll offset as the items are measured, as the web's virtual lists do.

## The Vulkan renderer draws the shapes that are outside the clip, and hashes every path of the scene every frame (Glutter 1.9.1)

- **What:** `frameBuilder.draw` of `internal/gpu/explicit` skips a draw only when its clip is empty (`c.Clip.IsEmpty()`) or when the bounds of the clip do not meet the surface (`outer.Empty()`), never when the shape of the draw is outside the clip, so every shape of the scene is described and masked on every frame, off screen too. Describing a path means `gpu.ShapeOf` -> `ui.Path.Fingerprint` (`ui/path_flatten.go`), which hashes every verb, every point (two floats, eight bytes each, a byte at a time) and every weight of the path on each call, and the clip masks do the same for a clip path (`gpu/clipmask.go`); nothing remembers the hash of a path that has not changed, although the path of a retained picture is the same object frame after frame. Measured on the desktop of 2026-10-27 with the Markdown preview of a 700 KB document (before step 17b.2 mounted only the blocks near the viewport): `Path.Fingerprint` was 18% of the CPU of a frame and the masks 85% of its raster time.
- **Where the workaround is:** `extension/ui/markdown/preview.go` (`cacheMargin`, with the `// Glutter:` comment): the preview builds blocks only 250 logical pixels beyond the viewport, so little is mounted off screen. Nothing else in Emetos draws much outside its clip (the editor paints the rows it shows; the lists build the rows they show).
- **What Glutter could provide:** (1) `frameBuilder.draw` skipping a draw whose bounds (`gpu.ShapeOf` already returns them; for a rectangle it is the rectangle) do not intersect `c.Clip.Bounds`, before the mask or the fingerprint is made, and the same for the clip layers of `PushClipRect`; (2) the fingerprint of a `ui.Path` computed once and kept in the path (a `uint64` and a flag that every method that changes the path clears), so that an unchanged path costs nothing the second time.

## The gesture arena resolves its default winner on the next turn of the event loop, and Linux gives every mouse event the pointer id 0 (Glutter 1.9.1)

- **What:** `GestureArenaManager.tryToResolveArena` schedules `resolveByDefault(pointer, state)` with `scheduleMicrotask`, which Glutter makes `PlatformDispatcher.Post`: the function runs on the next turn of the event loop (`internal/platform/linux/loop.go`, `runPosted`), not before the next pointer event as a Dart microtask does. The Linux platform gives every mouse event the pointer identifier 0 (`internal/platform/linux/input/pointer.go`, `base` sets none), and a slow frame makes the pointer events that arrived meanwhile be dispatched in one go (`GestureBinding.flushPointerEventQueue`), before that turn. Then: the only member of the first arena (a tap that the mouse moved away from, past the slop) rejects itself, the arena is deleted, the second press opens a new arena for pointer 0, and the turn finds `m.arenas[0]` (the new arena), deletes it and takes `state.members[0]` of the old state, which has none: `panic: runtime error: index out of range [0] with length 0` at `gestures/arena.go:309`, from `Loop.runPosted` (`loop.go:301`), which is not guarded, so the process ends. It happened on the desktop of 2026-10-27, with the Markdown preview open (frames of 1.2 to 1.65 s). Flutter's `_resolveByDefault` asserts `_arenas[pointer] == state`, and its microtask runs before the next event. Where the old state still has its member (a release swept the arena, which does not empty it), the turn resolves the new arena with the old arena's member.
- **What in Emetos triggers it:** nothing that Emetos does on purpose and nothing it could stop doing: every `GestureDetector` with `OnTap` (and every `TapGestureRecognizer`, such as the links of the Markdown preview) is the lone member of an arena that a mouse that moves away rejects. What Emetos adds is slow frames, which batch the events; the id 0 and the late microtask are Glutter's. Reproduced without a display with `gluttertest`, in `internal/gui/app/arenafix_test.go`: `TestGestureArenaSurvivesPointerIDReuseInOneTurn` (a `GestureDetector`, pointer 0: press, move 150 px, release, press, then the turn of the loop; Glutter alone panics with the message above) and, on the arena itself, `TestTheArenaIsFixedInTheApplicationAndInTheView`.
- **Where the workaround is:** `internal/gui/app/arenafix.go` (`fixGestureArena`, with the `// Glutter:` comment), installed by the root of the window (`trayHostState.InitState`) and by the root of each headless view (`viewSetupState.InitState`): the binding gets a `GestureArenaManager` made with a scheduler of its own that queues the microtasks and runs them on the next turn of the loop or, if a pointer event comes first, before that event is dispatched (it is chained to `GestureBinding.OnDispatchEvent`, which the renderer binding already uses for the mouse tracker and which runs before the targets of the hit test add themselves to an arena). The old arena is then resolved (it is gone, so the function returns) before the second press opens a new one.
- **What Glutter could provide:** `resolveByDefault` returning unless `m.arenas[pointer] == state` and `state` has a member (Flutter's assert as a check); its microtasks running before the next pointer event of the binding (at the end of `GestureBinding.handlePointerEvent`); and a pointer identifier for the mouse that changes with each press, as the touch path has.

## The Wayland keyboard logs "no keymap" at error level (Glutter 1.9.1)

- **What:** `internal/platform/linux/wayland/keyboard.go` `onKeymap` logs `slog.Error("the compositor sent a keymap that is not xkb_v1", "format", 0)` when the compositor sends `wl_keyboard.keymap` with the format `no_keymap` (0). A compositor does that when the last keyboard of the seat goes away (a virtual keyboard removed, a USB keyboard unplugged), which is legal: the keys work again when a keyboard comes back with a keymap. The code does the right thing (it drops the layout and returns); only the level and the wording are wrong. Found by the real-input harness of step 17b.1, which keeps one virtual keyboard for the whole run for this reason.
- **Where the workaround is:** none. The message goes to the default `slog` logger (standard error), which Emetos does not replace and does not want to filter by the text of a message; it is a line in the terminal of whoever runs Emetos from one, and nothing in the window.
- **What Glutter could provide:** `format == no_keymap` treated as "no keyboard" (the layout dropped, a log at debug level), and the error level kept for the formats that really are unknown.

## The renderers flatten the whole scene every frame, including the layers the raster cache holds (Glutter 1.9.1)

- **What:** `gpu.Flatten` (`internal/gpu/flatten.go`) turns the scene into a list of commands on every frame: it walks every layer and expands every picture, and a paragraph becomes one command per glyph run (`textdraw.Expand` -> `paragraph.paintGlyphs` -> `flattener.emit`, with a `Matrix4` clone per command). When the layer cache holds a layer (`FlattenOpts.Boundary` answers true for a `TransformLayer` or `ContainerLayer` that was in the last three scenes), `boundaryGroup` still flattens everything under it, and the renderer then drops those commands (GLES `layers.go`: "The layer's pixels are there: draw them, and drop what is inside"; the Vulkan renderer is made the same way). So a frame whose only change is the blink of a cursor (one new picture of three operations, checked by walking the scenes of the tester) costs as much to flatten as a frame in which everything changed. Measured on 2026-10-27 in a headless run (GLES, llvmpipe: `scripts/headless-wayland.sh` and `scripts/isolated.sh`, a release build with `emetos_dev`, `EMETOS_PROFILE_DIR`, `allocs` profiles written by `SIGUSR1` before and after 24 s of idle, cursor blinking at 2 frames a second): with a 10,000-line Go file open, **1.9 MB and 7,900 allocations a frame on the UI thread, 99% of it under `drawScene`** (`flattener.emit` 40%, `paragraph.paintGlyphs` 12%, `shapeContext.paintWith` 9%, `frame.add` 6%, `Matrix4.Clone` 6%, `gpu.PaintAccess` 4%); with the Markdown preview of a 700 KB document open beside its source, **8.4 MB and 30,000 allocations a frame**, 17 MB a second (`flattener.emit` 39%, `paintWith` 21%, `PaintAccess` 8%, `paintGlyphs` 8%, `frame.add` 6%). The profile of the desktop of 2026-10-27, before step 17b.2 (Vulkan), had the same list (`flattener.emit` 29%, `explicit.shapeContext.paintWith` 23%, `PaintAccess` 9%, `frameBuilder.draw` 7%). It is garbage, not a leak: the live heap is flat (34 to 64 MB, or 80 to 147 MB with the preview), a collection runs every 5 to 10 s, and the CPU of the window is 1.7% of a core with the profiler on. What the rest of the UI thread allocates in the same frames is 0.77 MB of 88 MB before step 17b.4 (17 KB a frame) and 0.50 MB after (10 KB), and the budget test of that part is `TestIdleBlinkFrameAllocationStaysInBudget`.
- **Where the workaround is:** none. Emetos already repaints only what changes (the layer of the cursors is a repaint boundary of its own, so a blink adds one picture to the scene), and nothing in Emetos draws text that is not on screen (the editor paints the rows it shows, the preview the blocks near the viewport). The cost is proportional to the glyphs on screen and is paid whether or not anything changed.
- **What Glutter could provide:** `Flatten` not descending into a boundary group whose pixels the cache holds (it can ask the cache before it walks the children: let `FlattenOpts.Boundary` say "cached" and emit only the begin and end of the group, with its layer, transform and clip); the glyph expansion of a paragraph cached by the paragraph and the transform, so that unchanged text costs a copy; the `DrawList` and the `Matrix4` of a command reused between frames in place of a clone per command; and, when the scene differs from the last one by one layer, a render of the damaged region from that layer (`DamageTracker` already measures the damage).
