# Glutter issues

Things Glutter is missing or gets wrong, found while building Emetos. Each entry says what is wrong, where Emetos works around it (if it does), and what the fix in Glutter would be. An entry is removed when the fix is in the Glutter version Emetos uses.

## A key that a hardware handler took still goes to the focus tree, and a key that comes while no node has the focus reaches no early handler (Glutter 1.9.1 and 1.9.2)

- **What:** `HardwareKeyboard.HandleKeyData` gives every key to the message handler of the focus system "also those the handlers handled" (as Flutter does), so a handler of the hardware keyboard that takes a key cannot keep the focused widget from acting on it (a letter typed after F2 started the find of the Explorer's tree, Enter made a new line in the editor). An early handler of the `FocusManager` that returns `Handled` does keep it away, but `highlightModeManager.handleKeyMessage` returns before the early handlers when `primaryFocus` is nil, which is the case for a few frames when the editor that had the focus goes away with its tab (the settings editor opens in its place): the keys of that time reach the hardware handlers and nothing else. Found by the keys typed at 10 ms after Ctrl+, (D5, step 17b.6); it is not one of the bugs of Glutter 1.9.2's steps 29.17 to 29.19.
- **Where the workaround is:** `internal/gui/kit/typeahead.go` (`TypeAhead`, with the `// Glutter:` comment): the keys are taken by a hardware handler (it sees them all the time), and an early handler of the focus manager claims the key that was just taken, so that no focus node sees it.
- **What Glutter could provide:** a way for a hardware handler to say that the focus tree must not see the event (a result that is not only "handled"), or early handlers that also run when no node has the focus.

## The debug build checks the goroutine on every mark-dirty call, and finding the goroutine parses `runtime.Stack` (Glutter 1.9.2)

- **What:** in a debug build (no `glutter_release` tag) `UIThread.AssertCurrent` runs in `RenderObject.MarkNeedsLayout`, `Element.MarkNeedsBuild`, `State.Go`, `ChangeNotifier.NotifyListeners` and a few more, and `IsCurrent` reads the goroutine id with `goid.ID`, which calls `runtime.Stack` and parses its header (`internal/goid`: "it is not on any path that runs for every widget or render object", but in a debug build it is). Mounting a workbench or the blocks of a Markdown preview marks thousands of objects. In a CPU profile of the start of the editor and two opens of the preview in the debug build, `AssertCurrent` was 63 ms of about 150 ms of UI-thread work outside the renderer; the frame that builds the first 10 blocks of the preview takes 42 to 47 ms in the debug build and 8 to 9 ms in the release build, and the first frame of the window 100 to 114 ms against 10 to 20 ms (D13 of `docs/DESKTOP-PASS.md`).
- **Where Emetos is affected:** the display tests (`internal/testenv/display`) run the debug build; their UI-thread budgets are five to ten times the release build's (`previewFirstFrameBudget` in `cmd/emetos/preview_display_test.go`), and SPEC §14's 16 ms is the release build's. There is no workaround in Emetos.
- **What Glutter could provide:** a cheaper check in debug builds: for example a goroutine-local token that the binding sets on the UI goroutine and the mark-dirty calls compare (no `runtime.Stack`), or the check at the entry points that other goroutines can reach (`SetState`, `Post`) only.

## There is no way to rasterize one glyph into an image, so the glyph atlas of the terminal draws paragraphs into a picture and reads it back (Glutter 1.9.2)

- **What:** the terminal (`extensions/terminal/atlas.go`, SPEC §10.25 "Speed") draws its grid with `Canvas.DrawAtlas`: each glyph is rasterized once into a sprite sheet and the sheet is drawn with the `BlendModeModulate` mode, so that one draw tints thousands of glyphs. Glutter has no call that rasterizes a glyph (or a run of text) of a font into an image of a given size with the font's hinting and antialiasing; the only way to get the pixels is to lay out a paragraph per glyph, draw them in white on a recording, and read the picture back with `Picture.ToImage` and the software rasterizer of `offscreen`. It works and is fast enough (a glyph is rasterized once per font and style; a page of 512 x 512 px holds several hundred), but it makes a paragraph and a picture for every new glyph, and the metrics of the cell (width, height and baseline) are measured from a paragraph of its own.
- **Where the workaround is:** `extensions/terminal/atlas.go` (`atlas.rasterize`), with the `// Glutter:` comments.
- **What Glutter could provide:** `ParagraphFactory.RasterizeGlyphs(font, size, runes) (image.Image, []GlyphMetrics)` or a `gpu.GlyphAtlas` that exposes the sheets it keeps for text, so that a widget draws its own grid of glyphs from them; and `FontMetrics` of a font at a size (advance of the zero, ascent, descent, line gap) without a paragraph.

## A pane that has the focus and leaves the tree is not told that it lost it (Glutter 1.9.2)

- **What:** when a widget that has the keyboard focus is unmounted (the terminal's pane of a tab that another tab replaces), the `Focus` widget's `OnFocusChange` is not called with false, so a widget that keeps its own "focused" flag (the terminal draws a filled cursor while it has the focus and an outline otherwise) stays in the state it had. Flutter's `Focus` calls `onFocusChange` from the node's listener, and the node leaves the scope without notifying when it is detached with the tree.
- **Where the workaround is:** `paneView.unmounted` in `extensions/terminal/pane.go` clears the flag itself.
- **What Glutter could provide:** the focus node notifies its listeners with `hasFocus` false when it is detached from the focus tree while it has the focus.
