# Glutter issues

Things Glutter is missing or gets wrong, found while building Emetos. Each entry says what is wrong, where Emetos works around it (if it does), and what the fix in Glutter would be. An entry is removed when the fix is in the Glutter version Emetos uses.

## Cold start headless: the Vulkan renderer is tried first and given up (3.11, 9b.1b)

- **What:** Glutter 1.7 (27.10) splits the first draw in the log (`GLUTTER_FRAME_STATS=1`) and keeps GLES program binaries in `$XDG_CACHE_HOME/glutter/shaders`. With them `scripts/perf.sh` shows where the start goes on the headless compositor (software GL): 560 to 600 ms of about 850 ms is the Vulkan renderer being tried and given up (`VulkanSwapchainFailed`: "the swapchain of the window cannot be made or used", the compositor presents no GPU buffers), 140 ms the GLES context, 20 to 30 ms the shaders (2 programs, 32 ms from Glutter's cache against 45 ms built with Mesa's cache warm) and 20 ms the frame. Glutter's own counter takes 30 to 50 ms longer than Emetos in the same runs, so none of it is Emetos's. The target of SPEC §14 is 400 ms.
- **Where the workaround is:** none; there is nothing to work around in Emetos. `scripts/perf.sh` reports the three states of the caches and the parts of the first draw.
- **What Glutter could provide:** try GLES first where Vulkan presents to no output, or find that out before the swapchain is made (Glutter's 27.10 entry measured 320 ms against 960 ms with `GLUTTER_RENDERER=gles`); its release notes ask the owner to decide.
- **Status:** headless numbers don't decide (SPEC §14); the figure with the GPU is the manual check `scripts/perf.sh --session` (`docs/MANUAL-CHECKS.md`), where Vulkan works and the try costs nothing.

## TreeSliver cannot set the expansion of a node that exists (6.4, 9b.1b)

- **What:** Glutter 1.7 (27.9) lets an app change the children of a node (`InsertChild`, `RemoveChild`, `SetChildren`), make a node lazy (`HasChildren`) and key the contents (`TreeSliverOpts.NodeKey`). The expansion is still held by the node (`TreeSliverNode.expanded`) and can be given only when the node is made (`TreeSliverNodeOpts.Expanded`), or toggled for a node that is shown (`TreeSliverController.ExpandNode`/`CollapseNode`, which also animate). `kit.Tree` keeps the expansion in its model, by key, also of the nodes that are not shown and of the find filter (`shownExpanded`), so it cannot keep its nodes between changes: the model's state would have to be written to the nodes that are hidden. With `NodeKey` set, a tree built again with new nodes keeps the expansion of the old nodes of the same key, which undoes the model's (tried in step 9b.1b: the toggling, reveal and rebuild tests of the tree fail).
- **Where the workaround is:** `kit.Tree` (`internal/gui/kit/tree.go`, the `// Glutter:` comment above `glutterNodes`): every change of the model builds the nodes again (only the expanded part has children; a node that is not read has one placeholder child), and Glutter's own toggling, controller and animation are not used (`AnimationStyleNoAnimation`, `TreeSliverIndentationTypeNone`); the content of a node is `treeContent{Key}`.
- **What Glutter could provide:** a way for the app to say which nodes are expanded without making them again: `TreeSliverNode.SetExpanded(bool)` (also for a node that is not shown), or `TreeSliverOpts.IsExpanded func(content T) bool` read when the active nodes are made. With either, the tree could keep its nodes and change them with `SetChildren`.
