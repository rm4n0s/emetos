# Emetos: Specification

Emetos is a code editor in the spirit of Visual Studio Code, written in Go on the [Glutter](https://github.com/rm4n0s/glutter) GUI toolkit, for the Linux desktop. This file is the source of truth: when the code and this file disagree, one of them is wrong, and the user decides which.

The work is split into the eleven areas of VS Code listed in §3. **This version of the spec covers areas 1 (the editor) and 2 (the workbench).** The other areas are listed so that the architecture leaves room for them, and get their own sections when they are planned.

"VS Code" below means VS Code 1.143.0, the version pinned in `scripts/reference-versions.txt` (§17). Where this spec says "as VS Code", VS Code's source at that version is the definition, and this spec's description is a summary.

---

## 1. Goals

| # | Goal |
|---|---|
| G1 | **What VS Code has.** Areas 1 and 2 (§3) match VS Code's behavior, defaults, command ids and Linux keyboard shortcuts closely enough that a VS Code user feels at home. When in doubt, do what VS Code does |
| G2 | **Private.** No telemetry, no crash reporting, no update checks, no network access of its own (§12) |
| G3 | **Native and light.** One Go binary, no Electron, no Node.js, no cgo. Starts fast, stays responsive on large files, uses no CPU when idle (§14) |
| G4 | **Compatible file formats.** VS Code's color themes, file icon themes, TextMate grammars, language configurations, snippet files, `settings.json` and `keybindings.json` formats work, so existing material can be reused |
| G5 | **Core and UI apart.** The editor core never imports Glutter. It is tested without a display, and the UI only shows and edits its state (§5) |
| G6 | **Testable.** Every feature has tests; UI features have widget tests and golden images that run without a display (§15) |

## 2. Non-goals

- Running VS Code extensions or a Node.js extension host.
- Windows, macOS, the web. Linux desktop only (Wayland and X11 through Glutter).
- Areas 3–11 of §3, until they are planned. Their hooks are listed where they matter (for example, the Problems panel exists but has no producers until area 3).
- Microsoft's proprietary features: Marketplace, Settings Sync with a Microsoft/GitHub account, Live Share, Copilot.
- Workspace trust (it guards extensions and tasks, which don't exist yet).
- Multi-root workspaces (`.code-workspace` with several folders). One window opens one folder or loose files.
- Vim/Emacs emulation (in VS Code they are extensions).
- Moved-code detection in the diff editor, and the accessible diff viewer.

## 5. Architecture

### 5.1 Processes, windows and threads

Emetos is one process with one or more windows. Glutter's UI goroutine owns every widget and render object.

**Per process**: settings registry and default/user layers, command registry, default keymap, theme service, language and grammar registries, the notification and log sinks, `core/ipc`, the profile in use by default.

**Per window** (a `Window` value created by `gui/app` for each Glutter window): the folder (workspace) or none, the workspace settings layer, the root context key scope, the documents (the same file open in two windows is two documents, as in VS Code's separate windows), editor groups, the file watcher, UI state, backups, the profile in use by that window.

Threads:
- **Documents** are changed only on the UI goroutine. Every change produces a new immutable **snapshot** of the buffer (§6.1) that background goroutines read freely.
- **Background work** (tokenizing, folding ranges, wrapping, file watching, fuzzy file search, diffing, backups) runs on goroutines with a `ctx`, reads snapshots, and posts results to the UI goroutine through `WidgetsBinding.Post` or `State.SetState`. A result for an older document version is dropped.
- **Child processes** (language servers, debug adapters, terminals) come with later areas and follow the same rule.

### 5.3 Boundary rules (checked by `internal/archtest`)

- No package under `internal/core/` imports `github.com/rm4n0s/glutter/...` or `internal/gui/...`.
- No package imports `net/http`, `net/rpc` or `crypto/tls`. `net` is allowed only in `internal/core/ipc` and, later, in the packages that talk to language servers and debug adapters.
- No `import "C"`.
- `github.com/dlclark/regexp2` only in `internal/core/regex`.
- No import of the standard library `errors`, and no call of `fmt.Errorf` (CLAUDE.md "Error handling").

### 5.4 Key handling

One **key dispatcher** per window, a `Focus` node at the root of the window's widget tree, resolves every key event through `core/keybinding` against the context key scope of the focused widget (§11.2), so a shortcut works wherever focus is (editor, explorer, quick input). Widgets below it handle a key themselves only for text entry. A key with no binding is left unhandled, and Glutter types its character into the focused text input client. Modifier-only key events never cancel a pending chord.

**Implementation (step 3.5).** `app.KeyDispatcher` sits above the app in the window's tree: it registers an early key handler of the focus manager, so a bound key is used before focus traversal and before the focused widget; `ChordOf` turns a key event into a chord (`KeyOf`: a Latin letter or digit comes from the logical key, any other key, and a letter on a layout without Latin letters, from the name of the physical key on a US keyboard); `Window.DispatchKey` resolves it with the window's `Dispatcher` in the context key scope of the focus node (`kit.FocusScopes` maps nodes to scopes; the nearest ancestor with a scope counts, the window's root scope otherwise), runs the command and reports whether the key was used. Key ups dispatch nothing; a press of a modifier alone keeps a pending chord; a chord's status is passed to `Window.OnChordStatus` (logged until the status bar shows it). A command that fails is logged; the key counts as used. The editor (`editor.EditorOpts`) makes its own scope under the window's with `editorTextFocus`, `editorFocus`, `textInputFocus`, `editorHasSelection` (any selection with text), `editorHasMultipleSelections`, `editorColumnSelection`, `editorReadonly`, `editorTabMovesFocus` (false) and `editorLangId`, and binds the handlers of its commands (`editor.BindCommands`, which uses the registry's handler stack) while it has the focus and unbinds them when it loses it.

**Text input (step 3.6).** The editor connects to the platform's text input (`services.TextInputConnection`) when its focus node gets the focus and closes it when it loses it. `editor/input.go`: the client speaks the delta model and gives the input method the current line of the primary cursor (a selection over several lines is a caret at its active end; the value is given again whenever the line, its text or the selection differs, which moves the input method's window with the cursor). A change of the input method is the difference between the line it was given and the text it holds apart from the composing range, found as one replaced stretch aligned to characters; it is typed at every cursor (`Commands.Type` for a stretch that is the selection, `CompositionType` with the characters before and after the cursor for a replacement around it). The composing range is the view model's `Preedit`: drawn above the text at the primary cursor, on the editor's color, with a line below it and a thicker one below the part the method highlights, with the cursor inside it; it is never in the document or the undo history, and it ends when the editor loses the focus. After each frame in which the editor moved, scrolled or changed, `SetEditableSizeAndTransform` and `SetCaretRect` tell the method where the editor and its caret are (the caret rect is the cursor, or the method's cursor inside the preedit): Glutter's `SetComposingRect` does not reach the platform. Characters of keys that no binding takes reach the editor through Glutter's `HandleUnhandledKey` (a key with a character commits it; Enter commits "\n", typed as a new line with the indentation of the line; keys with Control, Alt or Meta type nothing).

## 6. Text core

### 6.1 Buffer (`core/buffer`)

- A **piece tree**: a balanced tree of pieces pointing into read-only original chunks and an append-only add buffer, using VS Code's `PieceTreeTextBuffer` algorithms. Each node keeps the byte length and the number of line feeds of its subtree.
- **Persistent**: nodes are never changed after they are shared; an edit copies the path from the root to the changed nodes (no parent pointers). `Snapshot()` returns an immutable view in O(1), safe to read from any goroutine.
- Operations: insert, delete, replace at byte offsets; `LineCount`, `LineContent(n)`, `LineLength(n)`, `OffsetAt(Position)`, `PositionAt(offset)`, `Text(Range)`, iteration over chunks and lines. All are O(log n) in the number of pieces plus the size of the result.
- The buffer holds only `\n` line endings: `fileio` converts `\r\n` and lone `\r` when it reads (§6.3), and the document remembers the file's line ending for saving.

### 6.2 Positions and columns

- `Position{Line, Col int}`: zero-based line and **byte** column. `Range{Start, End Position}`. `Selection{Anchor, Active Position}`.
- **Visual columns** (column selection, rulers, `editor.tabSize`, vertical cursor movement, the status bar's "Col") follow VS Code's `CursorColumns`: walk the grapheme clusters of the line; for each cluster, take its first code point: a tab advances to the next tab stop, a full-width character or an emoji counts 2, anything else 1. The status bar's "Col" is not the visual column: as VS Code's `toStatusbarColumn`, it counts every code point as 1 (a tab goes to the next tab stop) and adds one, so a wide character or an emoji counts 1 there.
- Grapheme clusters (go-text's segmenter, through Glutter's dependencies) bound cursor movement and deletion.

### 6.3 Files (`core/fileio`)

- Reading returns the text (line endings converted to `\n`), the encoding, the BOM flag, the line ending (`\n` or `\r\n`; mixed endings become the most common one and are reported), and a `FileStat` (modification time, size, mode). Writing returns the new `FileStat`, so the watcher can ignore Emetos's own writes (§10.5).
- Encodings: UTF-8, UTF-8 with BOM, UTF-16 LE/BE (BOM), and the encodings of VS Code's `files.encoding` list that `golang.org/x/text/encoding` has; the others are left out of the list. `files.autoGuessEncoding` (off by default, as in VS Code) tries, in order, a BOM, valid UTF-8, then `files.encoding`; VS Code's statistical guessing (jschardet) is not done.
- Saving is atomic: write to a temporary file in the same folder, `fsync`, rename over the original, keep the original mode. When the folder isn't writable, write in place. A read-only file fails with a tagged error; "Overwrite" adds the owner's write permission (`chmod u+w`) and saves, as VS Code does.
- Binary detection, as VS Code's `detectEncodingFromBuffer`: a byte order mark decides the encoding; without one, the first 512 bytes are looked at: if every other byte is a NUL the file is UTF-16 (little or big endian), which is true of Latin-1 text and not of other scripts (those open with "Reopen with Encoding"); any other NUL byte means binary. Binary files open as a notice with "Open anyway".
- Delete moves to the freedesktop.org home trash (`$XDG_DATA_HOME/Trash`, with `.trashinfo` files); a file on another filesystem than the home trash can't be trashed, and the caller asks to delete permanently. A trashed item can be restored (used by undo in the explorer).

### 6.4 Large files and long lines

| File size | Behavior |
|---|---|
| < 20 MB and < 300,000 lines | Everything on |
| 20 MB – 256 MB, or ≥ 300,000 lines | "Large file mode" (`editor.largeFileOptimizations`): no tokenization (plain text), no bracket colorization, no folding, no minimap, no word wrap, and a notice saying so. The decision is made when the document opens and stored on the document; every feature checks it |
| > 256 MB | Refused with an error notice (VS Code's default limit) |

Long lines, as VS Code: a line is drawn up to `editor.stopRenderingLineAfter` (10,000 characters) and the rest is not drawn (cursor positions beyond it are computed with the monospace advance); tokenization of a line stops after `editor.maxTokenizationLineLength` (20,000 bytes). Word wrap does not wrap a line longer than `editor.stopRenderingLineAfter`.

As built (step 5.12): `editor.largeFileOptimizations` (default true; window scope) turns large file mode off when false. In large file mode the tokenizer, the bracket pairs, the folding regions, the minimap, word wrap, sticky scroll and the occurrence and selection highlights are off, and the window shows one notification (`LargeFileNotice`, a warning, once for each document) that says which. Sizes are checked when the file is read (`fileio.Read`: 20 MB or 300,000 lines for large file mode, 256 MB for `FileTooLarge`, which the window shows as "Cannot open <path>: ..."). A file that looks binary fails with `FileBinary`; the window then shows a notice in place of the editor (`editor.Notice`: "The file is not displayed in the editor because it is either binary or uses an unsupported text encoding." and a button "Open Anyway", also reached with Enter or Space) and "Open Anyway" reads it again with `AllowBinary`. Long lines: a row is laid out and drawn up to `editor.stopRenderingLineAfter` bytes (cut at the start of a character; zero or less means no limit); the x of a column past that is the width of the drawn part plus one character width for each byte, the point of a click there is the nearest such column, a selection reaches to the end of the line, and the horizontal scroll extent counts the whole line. `editor.maxTokenizationLineLength` is passed to the grammar of every document (`tokens`). The benchmark of a 200 MB file is `BenchmarkOpen200MB` (`docs/PERFORMANCE.md`).

## 7. Documents and editing

### 7.1 Document (`core/document`)

- A document has: a URI, the buffer, a version id (incremented by every change), an **alternative version id** (as VS Code's: incremented by a change, and restored by undo/redo to the value it had at that point), the saved alternative version id, language id, encoding, line ending, BOM flag, indentation options (`tabSize`, `insertSpaces`, detected or from settings), large-file flag, read-only flag, and the `FileStat` of the last read or write.
- **Dirty** means the alternative version id differs from the saved one, so undoing back to the saved state clears it.
- URI schemes: `file:` (a path), `untitled:<n>` (the lowest free number; title "Untitled-n"), and `emetos-virtual:` (read-only generated content, such as the default settings JSON or the saved version of a file for "Compare with Saved").
- **Edits** are applied as a batch of non-overlapping replacements; the document returns the inverse batch.
- **Undo/redo** stack of edit groups, as VS Code's `EditStack`: a group stores the edits, their inverses, and the selections before and after; consecutive edits of the same kind (typing, deleting left, deleting right, other) from the same cursors merge into one group, and a cursor move by other means, a different kind, or an explicit `PushStackElement` closes the group. Typing also follows VS Code's rule for spaces: a space typed after other characters starts a new group, spaces typed one after the other stay together, and the characters typed after a single space join it. Undo and redo restore the selections.
- **Decorations**: ranges that move with edits, with VS Code's four stickiness modes, kept in an interval tree; used for find matches, bracket highlights, snippet tab stops, auto-closed characters, diff changes, folded regions and, later, diagnostics. Every decoration has an **owner** (a number of 1 or more) that the feature that made it passes in; two editors that show one document (two editor groups, §10.3) must not share owners, so each takes a block of them from `Document.AllocOwners(n)` (the first reservation of a document starts at 1).
- Change events carry the version, the edits and the new snapshot.

### 7.2 Editing commands (`core/edit`)

Pure functions from (snapshot, cursors, options) to (edit batch, new cursors, edit kind), so they are tested without a document or a UI. A cursor whose edits overlap the edits of an earlier cursor is dropped from the result, as in VS Code. They cover every row of §3.1 under "Editing", "Line commands" and "Cursors and selections". One options struct carries everything they read (tab size, insert spaces, word separators, auto-closing, indentation rules...), so later features add fields, not parameters. Word boundaries follow `editor.wordSeparators` (VS Code's default) and word parts split camelCase and snake_case.

Cursor movement keeps a **desired visual column** for vertical moves. Movements that depend on the view (page up/down, vertical moves over wrapped or folded lines, Home/End on a wrapped line) ask a `LineLayout` interface, which the editor's view model implements; its default implementation treats every model line as one row.

## 8. Language support without a language server

### 8.1 Languages (`core/language`)

- A **registry** of languages: id, aliases, file extensions, file names, file name globs, first-line regex, MIME types, configuration, grammar, embedded languages and token types. Language of a file, as VS Code's `languagesAssociations.ts`: the user's `files.associations` first (globs, on the whole path when they have a slash and on the file name otherwise; the longest glob wins), then the languages' own: an exact file name, then the longest glob (`filenamePatterns`), then the longest extension; among equals the one registered last wins; the first line is looked at only when nothing else claims the file; otherwise `plaintext`. Paths and extensions are matched without regard to case. A `firstLine` that matches the empty text is left out.
- The registry (`language.Registry`) is filled by `AddExtension(fs.FS)` from the `package.json` of a VS Code extension at the root of the file system: `contributes.languages` (merged when several extensions contribute to one id, as `languagesRegistry.ts` does) and `contributes.grammars` (`language`, `scopeName`, `path`, `embeddedLanguages`, `tokenTypes`, `injectTo`). Entries that are not valid are left out and listed in `Problems`. Languages have a number (0 none, 1 plain text, then in order of registration), which the tokens of the grammars carry as their language. `Registry` is the `textmate.Registry` of the grammars (a grammar file is read when first asked for; `Injections` of a scope include those of the scopes that start it, as `TMGrammarFactory` does) and `NewGrammar(language)` makes the tokenizer of a language with its embedded languages (those of the injected grammars too) and token types. Grammars must be JSON; the one grammar of the reference extensions in the plist format (`source.js.regexp`) is converted to JSON by `scripts/update-assets.sh` (with `internal/core/language/internal/plist2json`, which also changes the path in the copied `package.json`) when JavaScript is bundled (step 4.6b). `language.Bundled()` makes a registry of its own from the embedded extensions (`internal/core/language/assets/<extension>/`, copied by `copy_extension` of `scripts/update-assets.sh`: `package.json`, the language configurations, `syntaxes/` and `cgmanifest.json`). The oracle test (`oracle_test.go`) tokenizes the colorize fixtures of the bundled languages as the Snapper of VS Code does and compares each line with `colorize-results`; the lines where Emetos differs are listed in `testdata/expected-differences.txt` (`<fixture> <lines> <reason>`), and an entry whose lines no longer differ fails the test. A rule whose included grammar is not bundled is left out, as vscode-textmate does, so a fenced block of such a language is not highlighted.
- **Language configuration** in VS Code's `language-configuration.json` format: comments, brackets, colorized bracket pairs, auto-closing pairs (with `notIn`), auto-close-before characters, surrounding pairs, folding markers and `offSide`, word pattern, indentation rules, on-enter rules. Its regular expressions are JavaScript syntax (as a string or `{pattern, flags}`) and compile with `core/regex`'s ECMAScript mode (the `u` flag turns on `\p{..}` property escapes, which `core/regex` translates). A field of the wrong type, or a regular expression that does not compile, is left out and listed as a problem; the other fields are kept (`ParseConfiguration`).
- **Bundled languages** (assets embedded with `embed`, copied from the pinned references by `scripts/update-assets.sh`, with their licenses in `third_party/`):
  - First (D13): Go, Markdown (with embedded code blocks for the bundled languages), JSON, JSON with Comments, YAML, Python, JavaScript, JavaScript React, TypeScript, TypeScript React.
  - Added by step 4.10: HTML (it embeds CSS and JavaScript), CSS, SCSS, Less, XML, XSL, SQL, Shell Script, Makefile, Dockerfile, INI and Properties.
  - Added by step 4.11: C, C++, CUDA C++, Rust, Diff, Git commit, Git rebase, Ignore files (`.gitignore` and others) and the Go module files (`go.mod`, `go.sum`; `go.work` uses the `go.mod` grammar; from `golang/vscode-go`, as the extension `go-mod` that `scripts/update-assets.sh` writes). `.h` is C++ as in VS Code. Plain text needs no grammar.
  - VS Code has no TOML grammar of its own; TOML is left for later.

### 8.2 Regular expressions (`core/regex`)

TextMate grammars use Oniguruma regular expressions; Go's `regexp` (RE2) lacks lookbehind and backreferences. `core/regex` wraps `github.com/dlclark/regexp2` (D11):

- Translation of Oniguruma-only syntax to regexp2: `\h`, `\H`, `\A`, `\z`, `\Z`, `\G` (an anchor position given by the tokenizer), `\K`, possessive quantifiers (as atomic groups), POSIX bracket classes, `\p{Alpha}`-style property names, class intersection `&&`, `(?x)` comments, and `(?m)` (Oniguruma's dot-matches-newline). A pattern that can't be translated is reported with a tag, and the rule using it never matches.
  - The pattern is parsed into a tree and written out again (`regex.Compile`), as vscode-oniguruma compiles it (`ONIG_OPTION_CAPTURE_GROUP`): every group captures and the groups are numbered by their opening parentheses, named ones included (regexp2 numbers named groups after the others, so names become numbers: `\k<name>` is `\k<n>`). `^` and `$` are lines anchors (`^` does not match after a final line break); `(?m)` is dot-all; `(?i)` and `(?x)` last to the end of the group, alternatives that follow included (`a(?i)b|c` is `a(?i:b|c)`); `(?x)` whitespace and comments are removed by the translator.
  - Repetition: `a*+` as an atomic group; `{n,m}+` repeats the interval (the Ruby syntax); `{n}?` is optional; `{,m}` is `{0,m}`; `{n,m}` with `n > m` is `{m,n}` that does not give back.
  - Classes: nested classes, `&&`, POSIX brackets (`[:alpha:]`, `[:^alpha:]`) and `\p{..}` (POSIX names, general categories long and short, Go's script tables) for Unicode text; `\x{85 2028}` (several code points) and `\x{...}`, `\h`, `\H`, `\R`, `\X`, `\N`, `\O`.
  - Calls of groups (`\g<name>`, `\g<1>`, `\g<-1>`, `\g<0>`) are replaced by a copy of the group that does not capture, with the ignore-case flag of the group; a group may be called inside itself 6 times, and the copy at the limit never matches, so recursive patterns (balanced parentheses) match up to that depth. When the pattern gets longer than 256 KB plus twice its source, the depth is lowered until it fits (`RegexTooLarge` when depth 1 does not).
  - `\K` is an empty group that marks the start of the match; the absence operator `(?~x)` is `(?:(?!x)[\s\S])*`; conditionals `(?(1)a|b)` and `(?(<name>)a|b)`.
  - Alternatives that match without consuming text and without capturing (`(?<=\W)|(?=\W)|^`), when they are next to each other in an alternation, are written as one atomic group: after one of them has matched, the others lead to the same state, and regexp2, unlike Oniguruma 6.9.9+, does not remember failed searches, so a loop around them (the whitespace of the C++ grammar) would take time exponential in the text it runs over.
  - Not supported, with a tag: options `W D S P y`, `\C-x`, `\M-x`, `\y`, `\Y`, levels in references (`\k<name+1>`).
  - `regex.Compile(pattern, Options)` takes the syntax, ignore case, the timeout, and `DisableA`/`DisableG` (the scanner asks for `\A` and `\G` that never match when the position is not the start of the text or the anchor). `regex.Cache` compiles a pattern once, failures included.
  A pattern that can't be translated is reported with a tag, and the rule using it never matches. All 5,900 patterns of the grammars under `reference/` compile (the corpus test of step 4.1).
- A **scanner** over several patterns, as vscode-textmate's `OnigScanner`: `Find(line, pos, anchorPos, isFirstLine)` returns the earliest match, ties broken by the lowest pattern index, with captures as byte offsets. A line is converted to runes once (`regex.NewLine`, which the tokenizer makes once per line and uses for every search of it); invalid UTF-8 bytes are treated as U+FFFD, one rune per byte, with the byte mapping kept. `\G` is allowed when `pos == anchorPos` and `\A` on the first line, as vscode-textmate's `compileAG` resolves them: the scanner compiles a variant of a pattern with the anchor that never matches the first time a line needs it. A pattern that does not compile never matches (`Scanner.Err` gives the reason).
- Every match runs with a time limit (100 ms, tag `RegexTimeout`); a line whose tokenization times out is plain text from that point.
- An **ECMAScript mode** (`regexp2.ECMAScript`) for find (§9.8) and for language configurations (§8.1).

### 8.3 Tokenization (`core/textmate`, `core/tokens`)

- Grammar loading (JSON) with `patterns`, `repository`, `include` (`#name`, `$self`, `$base`, `source.other#name`), `match`, `begin`/`end`, `begin`/`while`, all captures (including captures with patterns), `contentName`, `name` with `$1`-style back-references, `injections` and `injectionSelector`, embedded grammars through a grammar registry (scope name → grammar).
- A line tokenizer: (line, start state) → (tokens with scope stacks, end state). States compare for equality so re-tokenization stops when a line's end state is unchanged.
  - `textmate.ParseGrammar` reads a JSON grammar into a `RawGrammar` (read-only, shared by all documents); a `Registry` (implemented by the language registry of step 4.5) gives a grammar by scope name. `textmate.NewGrammar(scope, registry, opts)` makes the `Grammar`, which compiles its rules when the first line is tokenized and is safe for concurrent use. `Grammar.TokenizeLine(line, prev *State, timeLimit)` returns the tokens (byte offsets, each with its `ScopeStack`, a persistent list that shares its tail with the stack it was made from), the end `State` (a persistent list too; `nil` is the start of a document) and whether it stopped early. The tokenizer is a port of vscode-textmate (`tokenizeString.ts`, `rule.ts`, `grammar.ts`): the line is tokenized with a line break added, the token of the break is dropped, and the tokens are cut at the end of the line; an empty line has one empty token. The theme is not applied here: styles are resolved from the scopes later.
  - `begin`/`while` rules check their while pattern at the start of every line, outermost first: a rule whose pattern does not match is closed with the rules inside it, one that matches gives the line its `whileCaptures` and moves the start of the line past its match. Injections are the `injections` of the grammar (selector → rule, in the order of the file) and the grammars the registry says are injected into it (`Registry.Injections`, their `injectionSelector`); selectors have vscode-textmate's syntax (`L:`/`R:` priorities, `-`, `,`, `|`, parentheses; a name matches a scope that is it or starts with it and a dot). An injection that starts earlier than the rule of the scope wins, and so does one with `L:` that starts at the same place. Each token also has its **standard type** (`TokenType`: comment, string, regex or other — from the innermost scope that names one; `meta.embedded` resets to other — and then `GrammarOptions.TokenTypes` selectors) and its **language id** (`GrammarOptions.EmbeddedLanguages`: the innermost scope that starts with one of the scope names of the map; `InitialLanguage` elsewhere); the scope stack keeps both for each of its scopes.
  - A rule whose pattern does not compile never matches (`Grammar.Problems` lists why, once each); a pattern that runs past its limit (§8.2) ends the line as plain text in the scopes where it stopped (`StoppedEarly`). A line of `editor.maxTokenizationLineLength` bytes or more (default 20,000) is one token without scopes and leaves the state as it was. `\z` in a pattern is the end of the text without its line break, as in vscode-textmate.
- Each token also gets, as vscode-textmate does: a **standard token type** (comment, string, regex, other) from its scopes (the `\b(comment|string|regex|meta\.embedded)\b` rule plus the grammar's `tokenTypes`), and the **language id** of its embedded language (from the grammar's `embeddedLanguages`). Brackets, auto-closing and comments use them.
- Per document: line states cached; edits invalidate from the first edited line; a background goroutine tokenizes the rest in slices of at most 5 ms, checking for a newer version between slices; the visible lines are tokenized first, synchronously, before they are painted. Changing a document's language re-tokenizes it.
- Tokens are stored compactly per line: (end offset, style index, token type, language index).
  - `tokens.New(doc, grammar, opts)` makes the tokenizer of a document. `Line(i)` returns the tokens of a line (or none while it is not tokenized), `Ensure(line, budget)` tokenizes up to a line synchronously within a time budget and reports whether it got there, `Run(ctx)` is the background loop, `OnChange` tells the editor which lines have new tokens and `SetGrammar` re-tokenizes everything. An edit invalidates from its first line; the last new line takes the end state of the line it replaced, and re-tokenization stops at the first line whose new end state equals the old one. The loop works on snapshots; a result made for an older version of the document is dropped. Token scopes are interned (`Scopes`, a trie of `ScopeID`s) so the editor resolves a theme style once per scope stack.
  - The editor builds a text span per token from the theme (`kit.TokenThemeOf`) and caches paragraphs with their spans. Measuring and hit-testing use paragraphs without spans (the font is the same for every token), so the lines are laid out alike before and after highlighting. The synchronous budget for the visible lines is 6 ms per frame.

### 8.4 Themes (`core/theme`)

- VS Code color theme JSON (JSON with comments): `type` (dark, light, hc-dark, hc-light), `colors` (workbench colors; a value of `default` takes the color back to its default), `tokenColors` (inline, or the path of a TextMate `.tmTheme` file, a plist), `include` of a parent theme (the parent's colors and rules come first, and the child's override), `semanticHighlighting`/`semanticTokenColors` (stored for area 3). The old format (a `settings` list) and a `.tmTheme` file as the theme itself are read as VS Code reads them: the rule without scope sets the editor's colors (`background`, `foreground`, `selection`, `caret`, ... of `themeCompatibility.ts`). `theme.Load(fsys, file, defaultType)` reads a theme; a theme file that includes itself, or a chain deeper than 16, has the tag `ThemeIncludeCycle`.
- Token style resolution follows vscode-textmate's `theme.ts` (`ParseRules`, `NewTokenTheme`: scope selectors with descendant parts, `>` child combinators and comma lists, the rule of the deepest scope wins, then the longer parent scopes, then the later rule) and produces a foreground color, a background color and a font style (bold, italic, underline, strikethrough) as numbers into the theme's color map. `TokenTheme.Match(scopes)` is `Theme.match` of vscode-textmate (the rule that fits the scopes as they are); `Resolve(scopes)` is the style of a token: the defaults changed by the rule that fits each prefix of the scopes, outermost first, which is how the tokenizer of vscode-textmate merges attributes. `Theme.TokenRules(custom)` and `TokenTheme(custom)` build the rules as VS Code's `ColorThemeData.tokenColors` does: a default rule with `editor.foreground`/`editor.background` (a theme without them gets VS Code's defaults for its type until the color registry of step 4.8 holds all defaults), the theme's rules, the user's `editor.tokenColorCustomizations` (`custom`), and the `token.info-token`... rules unless the theme has its own. VS Code's colorize results are the oracle: the foreground color of every token of all fixtures, for the eight default themes, equals the one Emetos resolves.
- A **workbench color registry** (`theme.ColorRegistry`, filled by `theme.DefaultColorRegistry()`): every color id Emetos uses, registered by the step that first uses it, with VS Code's defaults for dark, light, hc-dark and hc-light (from `editorColorRegistry.ts`, `workbench/common/theme.ts` and the platform color files), including derived defaults. A default is a `ColorValue`: a color (`Hex`, `Lit`), the color of another id (`Ref`), or one derived from others (`Transparent`, `Darken`, `Lighten`, `Mix`, `Opaque`, `OneOf`, `IfDefinedThenElse`, `LessProminent`, as `colorUtils.ts` has them); nil is no color. `theme.Color` is VS Code's `Color` (whole RGB, alpha to three decimals, lightness changes through HSL) with its tests. `theme.NewColorTheme(theme, registry).Color(id)` gives the color a theme sets or else the default for its type; a color the theme writes in a form that is not a color is red, as in VS Code; references that loop have no color. Steps 4.8 registered the colors of the 20 ids of `kit.Colors` and the ones they refer to (`contrastBorder`, `contrastActiveBorder`, the deprecated `editorActiveLineNumber.foreground` and `editorIndentGuide.background`).
- The **theme service** (`theme.Service`, one per process, `Process.Themes`): `workbench.colorTheme`, `window.autoDetectColorScheme`, `workbench.preferredDarkColorTheme` and `workbench.preferredLightColorTheme` (registered settings; their values are the label or id of a bundled or user theme, with no fixed list since users add themes; the defaults are "Dark Modern" and "Light Modern", where VS Code says "Default Dark Modern"). It picks the theme: the preferred one for the system's brightness when auto detect is on, else `workbench.colorTheme`; an unknown or unreadable theme leaves the default one of that brightness and gives an error (a `Warn` notification). `gui/app` gives it the settings of the window (`Window.followTheme`, now and on every change) and the brightness of the platform (`themeHost`, a `WidgetsBindingObserver`), and rebuilds the UI under a new `kit.Theme` when it changes; `kit.ColorsOf(colorTheme)` makes `kit.Colors`, and `kit.DarkModern()` (for a widget with no theme above it) is the same function over the bundled Dark Modern. With several windows, the settings of the last one that applied them win. `high contrast` detection (`window.autoDetectHighContrast`) comes later.
- Bundled themes: Dark Modern, Light Modern, Dark+, Light+, Dark High Contrast, Light High Contrast (MIT, from VS Code), with the Visual Studio Dark and Light themes that Dark+ and Light+ include (files only, not offered). `theme.Bundled()` lists them with their names from the extension's `package.nls.json`, `theme.LoadBundled(name)` loads one by label or id. Default: Dark Modern, or the preferred light theme when `window.autoDetectColorScheme` is on and the system is light.
- User themes: JSON and `.tmTheme` files in `$XDG_CONFIG_HOME/emetos/themes/` (`storage.Paths.ThemesDir`), shared by the profiles; `theme.LoadUserThemes(fsys)` lists them by file name, with the file name as the id and the theme's `name` as the label; a file that cannot be read is among the problems, not an error.

### 8.5 Brackets (`core/brackets`)

Bracket pairs come from the language configuration (`brackets`, and `colorizedBracketPairs`, whose pairs are brackets too; when it is not defined, all pairs but `<` `>` are colorized); brackets inside comments, strings and regular expressions (by token type) are ignored, and a bracket is found only inside one token's text (neighbouring tokens with the same scopes count as one), in the language of the token, without regard to case, and at the edge of a word when the bracket text starts or ends with a letter (`end` is not in `friend`). A bracket pair structure is kept up to date after edits (VS Code's bracket pair tree is the reference; a simpler incremental scheme is fine if it passes the ported tests and the "incremental equals full" fuzz test) and answers: matching bracket of a position, enclosing pairs of a position (guides, expand selection), and the nesting level of each bracket (colors `editorBracketHighlight.foreground1..6`).

- `brackets.Index` reads a `Source` (lines, tokens, document language) and gives, for a range: `Pairs` (every pair that touches it, in the order of the opening brackets, with `Level`, the number of pairs around it, and `EqualLevel`, those around it that open with the same bracket) and `Brackets(range, onlyColorized)` (each bracket with its level; a closing bracket that closes nothing has `Invalid` set and the level of the pairs around it minus one; with `onlyColorized` the brackets of pairs without colors are left out and the levels count the colorized pairs only). `Match` (the two brackets of the closed pair a position is in or next to; where two touch, the one that starts later), `Enclosing` (the innermost closed pair with the position strictly inside), `MatchingUp` (the opening bracket a closing bracket text would close), `Prev` and `Next` (the nearest bracket), and `HasUnmatchedClosingAfter` (false until the tokens are complete). These are VS Code's `bracketPairsTextModelPart` queries.
- A closing bracket closes the innermost open pair it fits; the pairs above that one stay unclosed and end where the closing bracket starts; one that fits none is an unexpected closing bracket. An opening bracket deeper than 150 pairs is text. This is VS Code's parser (`parser.ts`) as a stack; its tree and its reuse of unchanged nodes are not ported (the ported tests that cover the tree, `beforeEditPositionMapper`, `combineTextEditInfos`, `concat23Trees`, `length` and `smallImmutableSet`, test those parts).
- The brackets of each line are kept until an edit or new tokens touch it; the pairs are made again, in one pass over all the brackets, at the next question (about 30 ns for each bracket: 2 ms for a file of 10,000 lines with 60,000 brackets). A document in large file mode has no index.

#### 8.5.1 In the editor

- `editor.matchBrackets` (`always`, `near`, `never`): while the editor has the focus, each cursor without a selection boxes the two brackets of the pair it is at (`Match`), and with `always` those of the pair around it (`Enclosing`) when it is at none; the box is the colors `editorBracketMatch.background` and `editorBracketMatch.border` (1 pixel inside), drawn below the text; more than 100 cursors box nothing. `editor.bracketPairColorization.enabled` colors each bracket of a pair that has colors with `editorBracketHighlight.foreground1..6` by its level (repeating after the sixth; the level counts the pairs of the same bracket when `editor.bracketPairColorization.independentColorPoolPerBracketType` is true), and a bracket that closes nothing or is never closed with `editorBracketHighlight.unexpectedBracket.foreground`; a transparent color (levels 4 to 6 in the default themes) leaves the token's color. The brackets keep the font style of their token.
- Commands (VS Code's): `editor.action.jumpToBracket` (Ctrl+Shift+\), `editor.action.selectToBracket` (argument `{"selectBrackets": false}` selects only what is inside) and `editor.action.removeBrackets` (Ctrl+Alt+Backspace). Expand Selection gains the steps of the brackets around the cursor (the text inside, the pair, and, when the pair spans lines, the line it starts on or the one above: `edit.NewBracketSelectionRanges`, VS Code's `bracketSelections.ts`) and the steps of a string around it (the text inside the quotes and the string with them, from the tokens of the standard type "string": `edit.NewStringSelectionRanges`; VS Code has no such step of its own, so this one is Emetos's).
- A document in large file mode has no brackets: the commands do nothing and nothing is colored or boxed.

### 8.6 Indentation (`core/indent`)

Indentation detection (VS Code's `indentationGuesser`), `increaseIndentPattern`/`decreaseIndentPattern`/`indentNextLinePattern`/`unIndentedLinePattern`, on-enter rules, type-time re-indentation (as VS Code's `getIndentActionForType`), `editor.autoIndent` levels (none, keep, brackets, advanced, full), `editor.autoIndentOnPaste` (VS Code's default: false), and the indent and bracket pair guides (VS Code's `guidesTextModelPart`).

#### 8.6.1 Detecting and changing the indentation

- `indent.Guess` is VS Code's `guessIndentation`: from the first 10,000 lines, tabs or spaces by counting the lines that start with each (a tie keeps the default), and with spaces the tab size from the differences between the indentation of lines that follow each other (2, 4, 6, 8, 3, 5, 7 in that order of preference; a difference caused by alignment after a comma is skipped; 2 wins over 4 when it has two thirds of its occurrences). A file opens with `editor.tabSize` and `editor.insertSpaces` of its language (the languages' `configurationDefaults` apply: Go and Makefile use tabs, YAML two spaces) and, when `editor.detectIndentation` is on, with what `Guess` finds in its text.
- Commands (VS Code's): `editor.action.indentationToSpaces` and `editor.action.indentationToTabs` (the indentation of every line, white space only lines included, with the primary selection moved along), `editor.action.indentUsingSpaces`, `editor.action.indentUsingTabs` and `editor.action.changeTabDisplaySize` (the tab size as an argument, `{"tabSize": 4}` or a number from 1 to 100, until the quick input of §10.6 can offer VS Code's list of 1 to 8), and `editor.action.detectIndentation` (guess again, with the settings of the language as the defaults). A change of the tab size changes the width of a tab in the text too.

#### 8.6.2 Indentation rules and Enter

- **`editor.autoIndent`** has VS Code's levels, each adding to the one before (`indent.AutoIndent`): `none` (a new line starts at the first column), `keep` (it gets the indentation of the line before the cursor), `brackets` (an opening bracket at the end of the text before the cursor indents the new line one level, and a pair of brackets around the cursor puts the closing one on a line of its own, from the language's `brackets`), `advanced` (the language's `onEnterRules` apply first) and `full` (the language's `indentationRules` apply when a line is started, when a character is typed and when text is pasted or reindented). The default is `full`. A language without `brackets`, `indentationRules` and `onEnterRules` has no on-enter support, so Enter only keeps the indentation (as in VS Code, where plain text does the same).
- **The rules read each line with the brackets taken out of its strings, comments and regular expressions** (the tokens of the standard type string, comment and regex), so `"{"` or `// {` does not indent; the brackets removed are those of the language of the line. Rules are evaluated with the ECMAScript patterns of the configuration (`core/regex`).
- **Enter** (`edit.Commands.NewLine`, `LineBreakInsert`, `InsertLineBefore`, `InsertLineAfter`; `indent.Indenter.EnterAction`, `IndentForEnter`): the first matching `onEnterRule` of the language at the cursor (`beforeText` against the text before the cursor, `afterText` against the text after the selection, `previousLineText` against the line above, all in the language at the cursor) decides `indent`/`indentOutdent`/`outdent`/`none`, `appendText` and `removeText`; `indentOutdent` puts the text after the cursor on its own line and the cursor on an indented line between; without a rule, the brackets of the language do the same from level `brackets`; at level `full` the indentation of the line below is then taken from the indentation rules (the nearest line above that is not ignored by `unIndentedLinePattern`, one level deeper after `increaseIndentPattern` or `indentNextLinePattern`, one level less when the text after the cursor matches `decreaseIndentPattern`), and the cursor stays at the same place of the indentation when it was inside it. When the tokens of the line are not at hand (`CheapToTokenize`) Enter keeps the indentation.
- **Typing** (`edit.Commands.Type` with one character, `indent.Indenter.IndentActionForType`, at `full`): when the character makes the line match `decreaseIndentPattern` (`}`, `end`), the line is re-indented to the indentation the rules give; a line that matched before the character is left as it is (it may have been indented on purpose), and so is a line of several languages. The other case of VS Code is an auto-closing character as the first on a line after a line that matched `indentNextLinePattern`; it is applied together with the auto-closing of §8.6.4 (the indentation edit and the closing text are one step; with an opening of several characters the character is typed and re-indented first and the closing text follows as a step of its own).
- **Tab** on a line of white space only puts the indentation the rules suggest (`IndentForBlankLine`: the indentation inherited from above, or that Enter at the end of the last line with text gives) instead of one level.
- **Reindent** (`editor.action.reindentlines`, `editor.action.reindentselectedlines`; `Indenter.ReindentEdits`): the lines are given the indentation the rules want, taking the first line as the base (for the selected lines, the line above them), skipping lines of `unIndentedLinePattern` and lines that start inside a string; it is one undo step and the cursors follow the text.
- **`editor.autoIndentOnPaste`** (default `false`) and **`editor.autoIndentOnPasteWithinString`** (default `true`): after a paste at one cursor, when the pasted text is not white space only, its first line (when only white space precedes it) gets the indentation the rules give and the other lines move by as much as the second line does (`Indenter.PasteEdits`); the paste and the indentation are two undo steps. A paste into a line of white space whose indentation is already right and that matches no rule is left alone. With `editor.autoIndentOnPasteWithinString` off, a paste that starts or ends in a string is left alone.
- The tests of VS Code that need auto-closing pairs or surrounding (`{` typed on an Allman line, #225916) are ported with §8.6.4.

#### 8.6.3 Guides

- **Settings** (VS Code's `editor.guides.*`): `indentation` (default `true`), `highlightActiveIndentation` (`true`, `"always"`, `false`; default `true`), `bracketPairs` (`true`, `"active"`, `false`; default `false`), `bracketPairsHorizontal` (`true`, `"active"`, `false`; default `"active"`) and `highlightActiveBracketPair` (default `true`).
- **Indent guides** (`indent.Guides.LinesIndentGuides`, `ActiveIndentGuide`; VS Code's `guidesTextModelPart`): a line has as many guides as it has indent levels (its indentation in columns divided by the tab size, rounded up); a line of white space only has the level of the lines around it (inside the region above when the line below is deeper, between two regions at their level, inside the region that ends below, or, for languages with `folding.offSide`, at the level of the region below; none at the top or bottom of the text). The active guide is the one of the scope the cursor's line is in, found by looking up and down for lines at the same or a deeper level (at the start of a scope the child's guide is the active one, at its end too), no further than the lines on the screen and 50,000 lines; it is highlighted unless the line also has bracket pair guides (`highlightActiveIndentation: "always"` highlights it there too). `indent.Levels` keeps the indentation of each line, computed when asked and forgotten when an edit touches the line, with the smallest indentation of each block of 64 lines, and follows a document (`indent.AttachLevels`).
- **Bracket pair guides** (`Guides.BracketGuides`): for a closed pair that spans lines, a vertical guide on each line from the opening bracket's line to the line before the closing bracket's (to its own line too when text comes before the closing bracket), at the smallest of the column of the opening bracket, that of the closing bracket and the smallest indentation inside the pair plus one (the lines after the opening bracket's, up to the closing bracket's; this stands for VS Code's `minVisibleColumnIndentation` of the pair's text nodes); with the horizontal guides (`bracketPairsHorizontal`) a line from the guide's column to the bracket where a bracket is further right than the guide, at the bottom of the opening bracket's row and at the top of the closing bracket's row (the bottom when text comes before it), and a line from after the opening to the closing bracket for a pair on one line. Only the pair around the cursor (the innermost one that has the cursor strictly inside) when `bracketPairs` is `"active"`; its guides are highlighted (`highlightActiveBracketPair`). The color is that of the pair's nesting level, counted among the pairs of the same bracket with `editor.bracketPairColorization.independentColorPoolPerBracketType`. A bracket pair guide takes the place of the indent guide at its column (`LineGuides`, VS Code's `IndentGuidesOverlay.getGuidesByLine`).
- **Colors** (`editorIndentGuide.background1..6`, `editorIndentGuide.activeBackground1..6`, `editorBracketPairGuide.background1..6`, `editorBracketPairGuide.activeBackground1..6`): a level with a transparent color is left out and the levels of the guides go round the ones that remain (the bundled themes color one indent level, so all use it); a bracket pair guide with no color of its own takes the color of the brackets of its level, at 30% opacity when inactive.
- **Drawing**: the layer below the text draws them after the selections and before the matching-bracket boxes: a vertical guide is a line of 1 pixel at the left of the column `(visible column − 1)` characters from the start of the text, as tall as the row; a horizontal one is a line of 1 pixel at the top or the bottom of the row from its start to the bracket. They follow the cursor, the document, the tokens (the bracket pairs) and the settings. The rows that word wrap (§9.2) adds to a line have no guides.

#### 8.6.4 Auto-closing and surrounding (`core/autoclose`, `edit.Commands.Type`)

- **Settings** (VS Code's): `editor.autoClosingBrackets`, `editor.autoClosingQuotes` and `editor.autoClosingComments` (`languageDefined`, `beforeWhitespace`, `always`, `never`; default `languageDefined`) say when the closing text is added; `editor.autoClosingOvertype` and `editor.autoClosingDelete` (`auto`, `always`, `never`; default `auto`) say whether a closing character is typed over and whether Backspace deletes the pair; `editor.autoSurround` (`languageDefined`, `quotes`, `brackets`, `never`; default `languageDefined`) says what typing over a selection does.
- **Pairs** (`autoclose.Language`, VS Code's `CharacterPairSupport`): the language's `autoClosingPairs`, else its `brackets`, else none, each with its `notIn` (`string`, `comment`, `regex`) and `beforeText`; the surrounding pairs are `surroundingPairs`, else the auto-closing pairs; `autoCloseBefore` is the set of characters a pair may be closed before (default for brackets `'"`;:.,=}])> ` with a space, tab and line end, for quotes the same without the quotes and the backtick; `beforeWhitespace` is a space, a tab or the end of the line). The pairs come from the language of the document, the token types from the token before the cursor in the language run it is in.
- **Order**, for one typed character, after the type-time indentation of §8.6.2 (VS Code's `typeWithInterceptors`): type over a closing character, close a pair, surround a selection, type the character. Only a single character goes through them; a longer text (a paste, an input method's commit) is inserted as it is.
- **Typing over** (`isAutoClosingOvertype`): the character is the closing of a pair of two single characters, every selection is empty and the character after it is the same one, it is not a quote after a backslash, and, with `auto`, it is a closing character the editor typed (the tracked ranges below).
- **Closing a pair** (`getAutoClosingPair`): every selection is empty; of the pairs whose opening ends with the typed character and matches the text before it (and `beforeText`), the one with the longest opening; quotes use `autoClosingQuotes`, a pair whose opening contains the block comment start of the language uses `autoClosingComments`, the others `autoClosingBrackets` (`never` closes nothing). The character after the cursor must be one of the allowed set, or start the closing text of a pair without starting the opening of one. For brackets, unless `always`, a closing bracket that closes nothing at or after the cursor (`brackets.Index.HasUnmatchedClosingAfter`) stops it. `'` and `"` are not closed after a word character (unless `always`). A line that is not cheap to tokenize is not closed. The pair's `notIn` is checked against the token before the cursor, and for a pair with `notIn` also against the type of a neutral character (a digit or letter that is in neither text of the pair) as if it were typed there (`tokens.Tokenizer.TypeIfInserting`: the line is tokenized again with it): that tells a quote that begins a string from one that ends it. A pair contained in another (`(` in `(*`) whose closing text already follows the cursor is not inserted twice. An opening of several characters (`begin`, `/**`) types the character first and inserts the closing text as a second undo step (`Result.FollowUp`), so that undo takes only the closing text away.
- **Tracking** (`edit.AutoClosedTracker`, VS Code's `AutoClosedAction`): the closing text a result inserted (`Result.AutoClosed`) is kept as a decoration with the typed character and the closing text around it. The pair is forgotten when a cursor is not strictly inside it any more, when it spans several lines, or when the cursors do not all lie in its pairs. The ranges of the closing characters are `Options.AutoClosed`, which typing over and Backspace read.
- **Backspace** (`isAutoClosingPairDelete`): with empty selections, an opening character before every cursor and its closing character after it, of a pair of one character each, deletes both; with `auto` only for a closing character the editor typed. `autoClosingBrackets` and `autoClosingQuotes` both `never`, or the pair's kind `never`, turn it off.
- **Surrounding** (`SurroundSelectionOperation`): a typed character that opens a surrounding pair, over selections that are not empty, not only spaces and tabs, and not a quote typed over a single quote character, puts the opening character before each selection and the closing one after it; the selection stays on the text between them (a backwards selection becomes forwards). An empty closing text is allowed.
- **Not done yet**: the interceptors of an input method's commit (VS Code's `compositionEndWithInterceptors`), which type over, close and surround after a composition, and the legacy electric characters of VS Code (no bundled language uses them).

#### 8.6.5 Comments (`core/comment`, `edit.Commands.ToggleLineComment`)

- **Commands** (VS Code's): Toggle Line Comment `editor.action.commentLine` (Ctrl+/), Add Line Comment `editor.action.addCommentLine` (Ctrl+K Ctrl+C), Remove Line Comment `editor.action.removeCommentLine` (Ctrl+K Ctrl+U) and Toggle Block Comment `editor.action.blockComment` (Ctrl+Shift+A on Linux). **Settings**: `editor.comments.insertSpace` (default `true`: a space goes between the token and the text) and `editor.comments.ignoreEmptyLines` (default `true`: empty lines are left out by the line commands).
- **Tokens** (`comment.Language`): the language's `comments` (`lineComment`, also as `{comment, noIndent}`, and `blockComment`; a block comment needs both tokens). The language is the one **of the token at the start of the first line of the selection** (column 1; for the block command, at the start of the selection), so code embedded in another language (a fence in Markdown, JSX in a script) is commented in its own language.
- **Line comments** (`LineCommentCommand`): a selection that ends at column 1 of a later line does not take that line. Each line is analysed: lines of white space only are left out when `ignoreEmptyLines`, a comment is looked for at the indentation of the line (at column 1 with `noIndent`) without regard to ASCII case; Toggle removes when every line (not left out) has one and adds otherwise, Add always adds, Remove takes off the ones there are; lines of white space only all get comments when Toggle finds nothing else. A removed token takes the space after it with it (with `insertSpace`). Comments are added at the smallest indentation of the lines (rounded down to a multiple of the indent size), so they line up. A language without a line comment uses its **block comment** for the lines (the one the cursor is in is removed, else the selection from the first non-white character of its first line to the end of its last line, or of the cursor's line when it is empty, is wrapped). A selection is kept: it follows the edits, a cursor at the end of a line that gets a comment there goes after it, and a selection that ended at column 1 ends there again.
- **Several selections**: they are taken in order of their starts, and when two share a line the first one in the list keeps it (the other ignores its first line). The cursors come back in that order.
- **Block comments** (`BlockCommentCommand`): a selection (or the cursor) inside a block comment, or whose own ends touch the tokens, gets them taken off (with the spaces next to them with `insertSpace`); a text that has an end token inside the supposed comment is wrapped instead. An empty selection becomes `start␣␣end` with the cursor between the spaces. The selection is kept between the tokens.

### 8.7 Folding (`core/folding`)

As VS Code without language servers: the indentation provider (`indentRangeProvider`, which also handles the language's `folding.markers` and `offSide`) for every language; `editor.foldingStrategy: auto` will prefer a language server's ranges in area 3. Ranges are computed on a snapshot in the background and limited to `editor.foldingMaximumRegions` (5,000). Folded ranges are decorations, so they survive edits. Arrow keys move over a folded range; only commands that reveal a position inside it (go to line, find, undo) unfold it.

#### 8.7.1 The model (`folding.Regions`, `folding.Model`)

- **Regions** (VS Code's `FoldingRegions`): sorted by their first line and nested; each has the first and last line (zero-based, 0 to 16,777,215), a folded flag, a source (`FromProvider`, `UserDefined`, `Recovered`) and a kind (`comment`, `imports`, `region`, or none); at most 65,535. `FindRange(line)` is the innermost region with the line, `Parent(i)` the one around it. A region hides every line of it but the first when it is folded.
- **Indentation provider** (`ComputeRanges`, `IndentProvider`): scanning from the last line up, a line with text followed by lines indented deeper starts a region that ends on the last of them (the line with the closing brace is outside it); with `offSide` the empty lines after a block are part of it; the `folding.markers` of the language make regions from the line that starts to the line that ends (the start marker pattern is tested first; a start with no end is a regular line). Over the limit the regions that start on the lines with the least indentation are kept. `Attach` runs a provider in the background: after the document has been quiet for 200 ms it computes the regions on a snapshot in a goroutine, cancels the work when the document changes again and drops a result for an older text, and gives the result to a function (which hands it to the goroutine of the editor, where `Model.Update` runs). Nothing is computed in large file mode.
- **The model** (`Model.Update`, `UpdatePost`, `ToggleCollapseState`): each region is a decoration of the document from the end of its first line to the end of its last (it never grows when typed at), with the options a provider function gives for (folded, hidden by a folded region around it, made by the user). `Update` merges the regions the provider found with the folded and the user-made ones, taking the lines from where their decorations are now (`SanitizeAndMerge`): a folded region the provider finds again at the same first line stays folded, unless a cursor is in it and its size changed; a folded region the provider no longer finds is kept as a recovered region (folded, source `Recovered`) while it is not invalid; ranges that are out of order, overlap without nesting or are out of the text are dropped. `RemoveManualRanges` removes the user-made regions a cursor is in (the innermost; all of them if the cursor is in none) or a selection touches. `Memento` and `ApplyMemento` save and restore the folded and the user-made regions with a checksum of the second and the last line of each, so a region whose text changed is not folded again.
- **Commands** (functions on the model, run on the first lines of the selections): Fold, Unfold (one region, with levels down or up), Toggle, Fold and Unfold Recursively, Toggle Recursively, Fold All, Unfold All, Fold Level 1 to 7 (the regions of the level that do not hold a cursor), Fold All Except Selected, Unfold All Except Selected, Fold All Block Comments (by kind, else by the lines that start with the block comment token), Fold and Unfold All Regions (by kind, else by the start marker); and the jumps to the parent fold, to the previous and the next fold at the same level.

#### 8.7.2 Folding in the editor (`gui/editor`)

- **The view model** owns the folding: `StartFolding(provider, delay)` makes the `Model` and, with a provider, an `Attach`ed updater whose result is posted to the UI thread and given to `Model.Update` with the first lines of the selections (a folded region that holds a cursor and changed is unfolded). The app starts it for every document with the `IndentProvider` of the language's `folding.offSide` and `folding.markers` and `editor.foldingMaximumRegions`. Nothing is folded while `editor.folding` is off, and the folding commands do nothing then (`foldingEnabled` is a context key of the editor).
- **The projection**: the lines a folded region hides have no row. They are read from the decorations of the folded regions (`Model.HiddenLines`: the lines after the first line of the region to its last, merged), so they follow edits made before the regions are computed again, and the projection is made again when the document or a fold changes (`foldedProjection`: binary search over the hidden spans; a hidden line has no rows and its first row is that of the line that holds the fold). Layout, scrolling, hit testing, selections and the line numbers go through it. `edit.ModelLineLayout` has `Hidden`: vertical movement and page movement count rows (lines that are shown), Left and Right step over a folded range (Left from the line after it goes to the end of the line that holds the fold, Right from there to the start of the line after it), and moving past the last row goes to the end of the last line that is shown.
- **Reveal rules** (VS Code's `HiddenRangeModel.adjustSelections` and `revealCursor`): when a fold hides the end of a selection, that end goes to the end of the line that holds the fold; when a command puts the start of a selection (its anchor) in a hidden line (go to line, find, undo, a click), the folded regions that hide it are unfolded, with no scrolling of their own beyond revealing the cursor. The changes the view makes itself are not revealed again.
- **The commands** have VS Code's ids and keys: `editor.fold` (Ctrl+Shift+[), `editor.unfold` (Ctrl+Shift+]), `editor.toggleFold` (Ctrl+K Ctrl+L), `editor.foldRecursively` (Ctrl+K Ctrl+[), `editor.unfoldRecursively` (Ctrl+K Ctrl+]), `editor.toggleFoldRecursively` (Ctrl+K Ctrl+Shift+L), `editor.foldAll` (Ctrl+K Ctrl+0), `editor.unfoldAll` (Ctrl+K Ctrl+J), `editor.foldLevel1` to `7` (Ctrl+K Ctrl+1 to 7), `editor.foldAllBlockComments` (Ctrl+K Ctrl+/), `editor.foldAllMarkerRegions` (Ctrl+K Ctrl+8), `editor.unfoldAllMarkerRegions` (Ctrl+K Ctrl+9), `editor.foldAllExcept` (Ctrl+K Ctrl+-), `editor.unfoldAllExcept` (Ctrl+K Ctrl+=), `editor.createFoldingRangeFromSelection` (Ctrl+K Ctrl+,), `editor.removeManualFoldingRanges` (Ctrl+K Ctrl+.), and `editor.gotoParentFold`, `editor.gotoPreviousFold` and `editor.gotoNextFold` (no keys). They work on the first lines of the selections, or on `selectionLines` (zero-based) of the argument; `editor.fold` and `editor.unfold` also take `levels` and `direction` (`up` or `down`). `editor.toggleImportFold` and the kinds `imports` and `comment` need a language server's ranges and come with area 3.
- **The gutter** has, in the 16 pixels at the start of the line decorations (the width is reserved by `editor.folding`, and not with `editor.showFoldingControls` `never`), a chevron (Codicon `chevron-down` for an open region, `chevron-right` for a folded one) on the first line of each region, in `editorGutter.foldingControlForeground`. With `editor.showFoldingControls` `always` all of them show, with `mouseover` (the default) the folded ones always and the open ones while the pointer is over the gutter. A press on the control (not in its first 4 pixels) toggles on release, as VS Code does and without moving the cursor: Alt works on the regions that are neither around nor inside it (those that are folded, or all of them when none is), Shift or the middle button on the regions inside it too.
- **The folded line** has the background `editor.foldBackground` (`editor.foldingHighlight`) across the editor and a `…` placeholder after its text in `editor.foldPlaceholderForeground`. A press on the placeholder places the cursor as usual and unfolds the region on release; with `editor.unfoldOnClickAfterEndOfLine` the empty space after it does too.
- **View state**: `ViewState.Folds` is the `Memento` of the model (the folded and the user-made regions with a checksum of their lines). `RestoreViewState` applies it, or keeps it until the regions of the document are first known.
- `editor.foldingStrategy` and `editor.foldingImportsByDefault` are registered with VS Code's defaults but have no effect before area 3 (the indentation provider is the only one and has no kinds).

## 9. The editor widget (`gui/editor`)

### 9.1 Structure

- An editor has a **view model**: the document, the cursors, scroll positions, and the **line projection** from model lines to view rows: identity at first; folding hides rows (§8.7), word wrap splits a line into several rows (§9.2), and view zones insert rows of a given height between lines (used by the diff editor, §9.11, and later by area 3). Layout, scrolling, hit testing, vertical movement (`LineLayout`), the minimap and sticky scroll all go through the projection. Several editors (in several groups) can show one document, each with its own view model.
- **`RenderEditorText`**: a leaf `RenderBox` driven by a `Scrollable`'s `ViewportOffset` (vertical) and its own horizontal offset. It lays out and paints only the visible rows plus a margin of 10 rows. It is a repaint boundary, so Glutter's raster cache keeps the text when only the cursor changes.
- Separate layers for the cursors (blink), the gutter (line numbers, folding controls, later breakpoints and diff markers), the minimap, sticky scroll, rulers and overlays (find widget, later hover and completion). They share the view model's line layout cache.
- Editor view state (selections, scroll position, folded ranges) can be read and restored, for history (§10.3) and restore (§10.10).

- **Scrollbars and hit testing**: the editor is wrapped in `kit.ScrollableElement` with a `ScrollModel` (`ScrollableElementOpts.Model`; the editor turns the wheel handling of the element off and scrolls with the wheel itself) made of the scroll controller (vertical), the view model (horizontal) and what the text layer measured (`SetTextMetrics`: text area size, vertical extent, the widest row laid out since the last document or font change, plus four characters of room). The scrollbars are VS Code's: 14 pixels wide and 12 pixels high (the editor passes the sizes of `editor.scrollbar.*`; the kit's own default is 10, §10.2), overlaid, shown while the pointer is over the editor or after a scroll and faded away 500 ms later (100 ms in, 800 ms out), slider of at least 20 pixels, a click on the track jumps the slider there (or pages with `ScrollByPage`), a drag goes on outside the scrollbar, and a shadow marks scrolled content. The text layer turns a point into a position (`RenderEditorText.PositionAt`: the row from the projection, the column nearest to x at a grapheme boundary: `columnAt` counts characters for plain ASCII without tabs in a monospace font and otherwise searches the grapheme boundaries with the x of each from the paragraph's boxes) and a position into the rectangle of its character (`RectOf`).

### 9.2 Text rendering

- **One `ui.Paragraph` per visible row**, built with a new `ui.ParagraphBuilder` from token spans, cached by (line content, tokens, theme, font settings, wrap width) and dropped by an LRU of 2,000 lines. Glutter caches shaped runs but not paragraphs: a cold code line costs about 41–58 µs, an unchanged one rebuilt 5–10 µs (Glutter's `docs/PERFORMANCE.md`, steps 22.6 and 22.10). Keeping the paragraphs of unchanged lines is what makes an edit cost about one line.
- **Tabs**: Glutter's tab stops (`ParagraphStyleOpts.TabSize` = `editor.tabSize`) place tabs, so paragraph offsets equal buffer byte columns. A tab draws nothing; whitespace rendering draws the arrows and dots itself. `editor.renderControlCharacters` (default true) draws control characters as a box over their position, so offsets stay equal: the C0 controls except the tab, DEL and the Unicode directional formatting characters (U+202A–202E, U+2066–2069, U+200E–200F, U+061C) get a dark red box (`rgb(150, 0, 0)`, VS Code's `.mtkcontrol`) over the cell the font gives them, or a bar of 2 pixels when the font gives them none, and the C0 controls and DEL show their Control Pictures glyph (U+2400 + code, DEL U+2421) in white. The boxes are drawn in the layer above the text, so that they cover what the font draws for the character.
- **Fonts**: `editor.fontFamily` defaults to the desktop's monospace font (`PlatformDispatcher.MonospaceFont()`, followed live), then the generic `monospace` (D14). The setting's registered default is the empty string, which means that (VS Code's default is a list of platform fonts); `editor.fontSize` defaults to 14. A comma-separated `editor.fontFamily` becomes `FontFamily` plus `FontFamilyFallback`, which Glutter tries in order. Positions come from the paragraph's queries (`GetBoxesForRange`, `GetPositionForOffset`), except for the fast path of pure-ASCII lines in a monospace font.
- **Line height**, as VS Code's `fontInfo.ts`: `editor.lineHeight` 0 means `round(1.35 × fontSize)`; a value below 8 is a multiplier of the font size; otherwise pixels.
- Ligatures follow `editor.fontLigatures` (`liga` and `calt` features on or off).
- **Font weight and letter spacing**: `editor.fontWeight` (`normal` 400, `bold` 700, or a number from 1 to 1000) and `editor.letterSpacing` (pixels between letters, which widens every character: columns, hit testing and the cursor use the measured width) go into the paragraph style and its cache key. **Zoom**: the zoom of the window (`editor.Zoom`, shared by its editors; level -5 to 20) makes the font and the lines `1 + level/10` times their size, over the settings; `editor.action.fontZoomIn`, `fontZoomOut` and `fontZoomReset` change it, and with `editor.mouseWheelZoom` Control with the mouse wheel does (a notch is a level; a touchpad pan of 200 pixels is a level). Every setting of this section is applied live: the shell re-reads the options when `editor.*` changes.
- **Word wrap** breaks lines at the wrap width: lines that are pure ASCII in a monospace font are broken by counting columns (VS Code's `simple` wrapping strategy), others by paragraph layout; breaks for the whole document are computed in the background in slices, with an estimate (one row per line) until they're known, and the scroll position is anchored to the top visible line when a line's row count changes.
  - **Settings**: `editor.wordWrap` (`off`, `on`, `wordWrapColumn`, `bounded`), `editor.wordWrapColumn` (80), `editor.wrappingIndent` (`none`, `same`, `indent`, `deepIndent`), `editor.wrappingStrategy` (`simple`, `advanced`); `editor.action.toggleWordWrap` (Alt+Z) turns wrapping on or off for one editor, over the setting. The wrap width in columns is the viewport (without the scrollbar) divided by the character width for `on`, `editor.wordWrapColumn` for `wordWrapColumn`, and the smaller of the two for `bounded`. No wrapping in large file mode (§6.4), and a line longer than `editor.stopRenderingLineAfter` is not wrapped.
  - **Breaks** are `core/wrap.Compute(line, options)`, a port of VS Code's `MonospaceLineBreaksComputer` (kinsoku rules for East Asian text, a break after a space or a hyphen-like character, a hard break when a word is wider than a row). Continuation rows are indented by the line's own indentation plus 0, 1 or 2 tab stops (`wrappingIndent`), and none when the indentation would leave no room for text in the row. A line that has a non-ASCII character, a font that is not monospace, or `advanced` strategy gets its columns from the paragraph's measurements (`breaksByLayout`) instead of counting.
  - **Projection**: `wrappedProjection` keeps the first row of each line and the breaks of each line; a row is `text[start:end]` of its line, indented by `RowIndentColumns` characters (a pure x offset: the text of a continuation row is its own paragraph). A fold hides the rows of its lines. The line numbers, the guides and the fold controls are drawn on the first row of a line only, the current line highlight on all the rows of the line, selections and find matches through `selectionRows` on each row they cross.
  - **Computing**: the breaks of the document are computed on the UI thread in slices of a few milliseconds through the view model's timer (lines that were edited, then the viewport, then the rest); until a line's breaks are known it is one row. An edit splices the breaks of the changed lines and breaks them at once. When the breaks of a line above the viewport change, the scroll position is moved so that the top visible row stays where it was (`captureAnchor`, `restoreAnchor`).
  - **Cursor**: Up and Down move by rows and keep the pixel column (`edit.ModelLineLayout` takes the projection's rows as an `edit.RowMap`); Home goes to the start of the row when the cursor is on a row that continues a line (otherwise the smart home of the line), End to the end of the row.
  - **Deviations from VS Code**: tabs after a wrap are measured from the start of the row, not from the start of the line; the cursor at a wrap point has no affinity (it is drawn at the start of the next row); wrapped continuation rows have no indent guides; `editor.wordBreak`, `editor.wordWrapBreakAfterCharacters`, `wordWrapBreakBeforeCharacters` and `editor.wrappingStrategy: advanced`'s browser-specific behavior are not registered, VS Code's defaults are used; `editor.stopRenderingLineAfter` only stops wrapping and the drawing of whitespace (the line is drawn in full).


- **Whitespace** (`editor.renderWhitespace`: `none`, `boundary`, `selection` (the default), `trailing`, `all`): the overlay under the text draws a dot (radius a seventh of a space, centered in the space) on each space and an arrow (one space wide, at the left of the tab) on each tab that the mode says, in `editorWhitespace.foreground`, as VS Code's SVG whitespace overlay does. `boundary` skips single spaces between words; `trailing` draws only the white space at the end of a line that is blank or ends with it, and nothing on a row that is followed by the next row of a wrapped line; `selection` draws only inside the selections (a selection that runs over a row to its end or from its start covers the row's end or start); on a row that is followed by the next row, `boundary` skips a single space at its end. Nothing is drawn after `editor.stopRenderingLineAfter` bytes.
- **Rulers** (`editor.rulers`: numbers, or objects with `column` and `color`; sorted by column; columns from 0 to 10,000): a line of 1 pixel at the left of the column, `column` characters from the left edge of the text, as high as the editor, in the color of the ruler or `editorRuler.foreground`. They scroll horizontally with the text.

### 9.3 Input

- **Keys** go through the window's key dispatcher (§5.4). Key names are VS Code's (`ctrl+shift+k`, `ctrl+k ctrl+c`): letters and digits come from Glutter's logical key (Latin layout, so they work on any keyboard layout); punctuation and other keys come from the physical key, named by its US-layout key (VS Code's `keyboard.dispatch: code`).
- **IME**: the editor implements `services.TextInputClient` with the delta model (`EnableDeltaModel`, `UpdateEditingValueWithDeltas`). Glutter's input layer keeps a full copy of the text it is given, so Emetos gives it only the current line (line-local offsets) and maps the deltas back. A committed text is typed at every cursor, as VS Code does. The preedit (composition) text is drawn as an underlined overlay at the primary cursor, not inserted into the document, so it never enters undo. The caret rect (`SetCaretRect`, which places the candidate window) is updated after every frame.
- **Mouse**: click places the cursor, double-click selects a word, triple-click a line; drag extends by character/word/line according to the click count; Shift+click extends; Alt+click adds a cursor (`editor.multiCursorModifier`); Shift+Alt+drag selects a column; Ctrl+click is reserved for "go to definition" (area 3); middle click pastes the primary selection. The mouse is a raw `Listener` on the row of gutter and text (not a gesture recognizer): the editor counts the clicks itself (a press within 400 ms and 5 pixels of the one before is the next click; four or more select everything) and reads the modifier keys from the binding's `HardwareKeyboard` at the press. What a press or drag does is VS Code's `ViewController.dispatchMouse`: Shift extends from the anchor (by words or lines after a double or triple click); `editor.multiCursorModifier` (`alt`, or `ctrlCmd`, which is Control on Linux) makes a click add a cursor (a click inside an existing selection or cursor removes it), a double or triple click add a word or a line, and dragging go on selecting with the cursor added last; with it and Shift, or with Alt when it is not the modifier (or `editor.columnSelection`, for every drag), the drag selects a column, from the anchor to the column under the pointer, also past the end of short lines; a press on the line numbers selects lines, and in the rest of the gutter goes to the start of the line. Only the primary button selects; the other buttons come with middle-click paste (3.8) and the context menu. A touch only places the cursor. `editor.mouseStyle` (`text`, `default`, `copy`) is the pointer over the text; the gutter has the default arrow. The word and line selection by unit are pure functions in `core/edit` (`Mover.WordSelect`, `WordSelectDrag`, `LineSelect`, `LineSelectDrag`).
- **Drag and drop of text** (`editor.dragAndDrop`): a single click without Alt on the text of the primary selection (not in a read-only document, not with `editor.columnSelection`) arms a drag of the selected text. The selection pressed is the one dragged when the pointer moves (VS Code takes the one under the first move; Emetos takes the pressed one first, so a quick first move does not lose the drag), a dotted drop caret (2 pixels, in the cursor color) follows the pointer except over the dragged text, the pointer is the copy cursor while Control is held and the default arrow otherwise, and Escape cancels. On release inside the editor the text moves (`edit.Commands.DragAndDrop`, one undo step; the dropped text is selected), or is copied with Control, unless the position is inside the selection (a copy beside it is allowed); outside the editor nothing happens. A release without a move is a click: the cursor goes there (the other selections stay; Shift extends the primary selection from its anchor). It is the editor's own pointer logic, not `Draggable`.
- **Scrolling**: the editor claims the pointer signal through the `PointerSignalResolver` when the scroll would move it (so `Scrollable` does not scroll twice), and the `Scrollable` is given a scroll behavior in which only a finger or a pen drags it (the touchpad is the editor's). A wheel notch is 53 logical pixels in Glutter and scrolls 50 pixels at `editor.mouseWheelScrollSensitivity` 1 (a smaller delta, from a high-resolution wheel, scrolls in proportion; a step is rounded away from zero); Alt multiplies by `editor.fastScrollSensitivity`; Shift scrolls sideways; a touchpad pan scrolls 1:1 with the same multipliers, opposite to the pan. `editor.smoothScrolling` animates the vertical scroll of the wheel over 125 ms with an ease-out cubic, and the next notch goes on from where the animation ends; the animation moves the position with `JumpTo` on every frame, because `Scrollable` ignores pointer events while its own animation runs (Emetos's scrolling to reveal the cursor and the touchpad are not animated). Scrolling beyond the last line is `editor.scrollBeyondLastLine`. While a selection is dragged beyond the top or bottom of the editor it scrolls every frame at VS Code's speed (30 to 200 lines a second, faster the farther the pointer is) and the end of the selection goes to the edge line, at the pointer's column, or to the start or end of the line when the editor cannot scroll further; beyond the left or right edge it scrolls sideways and the selection goes to the start or end of the pointer's line. The scrolling stops with the button, or when the pointer comes back inside.
- **Middle button** (`editor.selectionClipboard`, Linux): a middle click places the cursor and, on release, pastes the primary selection of the desktop there (`GetPrimaryData`, in the callback on the UI thread); a middle press that moves selects like the primary button and pastes nothing. Without the setting the middle button selects a column (VS Code's behavior).
- **Clipboard**: `editor.action.clipboardCopyAction`, `…CutAction` and `…PasteAction` (Ctrl+C, Ctrl+X, Ctrl+V, Shift+Insert; they are the editor's commands while it has the focus). Copy puts the selections on the system clipboard, one after the other in the order of the text with a line break between them; with no selection it copies the line with its break (`editor.emptySelectionClipboard`; the cursors of one line copy it once), and with the setting off an empty selection copies nothing. Cut copies and deletes (the line, with its break, of an empty selection, the last line taking the break before it; in a read-only document it only copies). Paste is applied in the callback of Glutter's asynchronous clipboard, on the UI thread, as one undo step, and does nothing in a read-only document. Every cursor gets the whole text, except: the pieces of a copy made by as many cursors go one to each cursor from the top; with `editor.multiCursorPaste` `spread` (the default) a text with as many lines as there are cursors goes line by line (a trailing line break is not a line); a block copied from a column selection into one cursor goes down the lines at the same visual column, padded to the width of the block, past the end of the text if it must; and a line copied from an empty selection goes above the line of an empty cursor, which stays in its text. The editor knows how its last copy was made (`ClipboardMemory`, shared by the editors of a window, matched by the copied text, as VS Code's in-memory metadata); a text copied by another program is plain. The primary selection of the desktop (`editor.selectionClipboard`, Linux) is set 100 ms after the selections stop changing, when every cursor has a selection and the editor has the focus, to the selected text in the order of the text, and the middle button pastes it (above). Copy with syntax highlighting is not implemented.

### 9.4 Decorations shown

Selections, current line, word and selection highlights, find matches, matching brackets, bracket colors and guides, indent guides, rulers, whitespace, folded lines and their `…` placeholders (§8.7.2), snippet tab stops, IME composition, and, from later areas, diagnostics squiggles, inlay hints and code lenses (the render object reserves the drawing order for them).

Occurrence highlights (`editor.occurrencesHighlight`: `off`, `singleFile` (the default), `multiFile`; `editor.selectionHighlight`, default true): Emetos has no language features yet, so the word highlight is VS Code's textual one: while the editor has a single-line selection inside one word (or a cursor in or next to a word), the other occurrences of the word (case sensitive, whole words) get `editor.wordHighlightTextBackground` and its border, `editor.occurrencesHighlightDelay` (250) milliseconds after the cursor moved; the marks stay while the cursor moves inside a marked word, go when it moves to another word, when it moves because of typing, and when the document changes. `multiFile` marks the same as `singleFile` (there are no other files to mark in a plain editor). The selection highlight marks the text that equals a selection that has text (single line unless `editor.selectionHighlightMultiline`, not only spaces and tabs, at most `editor.selectionHighlightMaxLength` characters (200, 0 for no limit)), with the switches of the find widget (match case and whole word), in `editor.selectionHighlightBackground` and its border, apart from the selections themselves; several selections must hold the same text (compared without case unless the find options match case); it is made at once when the selection changes and 300 ms after an edit, and it marks nothing while the find widget is open and looks for the same text with the same switches. Both are decorations of the document (the slots 4 and 5 of the view model's owners, §10.3, so they move with the edits), computed on the UI thread, and not in large file mode. They are drawn after the rulers and the guides and before the find matches; the whitespace comes after the find matches. Not ported: the overview ruler marks of the highlights, `editor.selectedTextMatchMode`, and the word highlight of language servers (read and write access), which comes with area 3.

Drawing order and layers: the layer below the text draws the current line (`editor.renderLineHighlight`: `none`, `gutter`, `line`, `all`; `editor.renderLineHighlightOnlyWhenFocus`; the text is highlighted only while no selection has text; a theme with a transparent line highlight gets the 2-pixel border) and the selections (`editor.roundedSelection`: 3-pixel corners, reversed corners where a row reaches further than its neighbor, rows extended by one character where the line break is selected, the inactive color without focus); the text layer follows; the layer above the text draws the line cursors (`editor.cursorWidth`, 0 meaning 2 pixels). Each layer is a repaint boundary, so a blink repaints only the cursors. The cursors blink every 500 ms with timers of the window's binding (`editor.cursorBlinking`: `solid` does not blink; `blink` toggles on a timer; `smooth`, `phase` and `expand` run VS Code's keyframe animation on every frame, after half a second shown, for 20 half-second iterations, every other one backwards, ease-in-out between the keyframes: `smooth` and `phase` fade the cursor out by 60% and 90% of an iteration, `expand` shrinks its height towards its middle by 80%); every move or edit shows them and starts counting again, and an editor without the window's focus has no cursors and no timer. `editor.cursorStyle` has VS Code's six styles: `line` and `line-thin` (a bar of `editor.cursorWidth` or 2 pixels, or 1, between the characters; a bar wider than 2 pixels shows the character it covers), `block` (the character's cell, with the character in the opposite color of the cursor's), `underline` and `underline-thin` (2 or 1 pixel at the bottom of the cell) and `block-outline` (a 1-pixel border); a block covers a tab with the width of one character and the end of a line with one character. The overtype cursor style is not implemented.

### 9.5 Minimap

Blocks colored by token, with VS Code's sizes, drawn into an image (`ui.NewImageFromRGBA`) from a CPU buffer that is patched by line ranges; for long files only the window of lines the minimap shows is drawn, scrolled proportionally as VS Code does. The slider shows the viewport; click and drag scroll; selections, find matches and the text equal to the selection are marked. Hidden by `editor.minimap.enabled: false` and in large file mode.

- **Settings**: `editor.minimap.enabled` (true), `side` (`right`, `left`), `size` (`proportional`, `fill`, `fit`), `showSlider` (`mouseover`, `always`), `scale` (1 to 3), `maxColumn` (120) and `renderCharacters` (registered with VS Code's default, true; Emetos always draws blocks, so a line is 3 canvas pixels at scale 1, where VS Code's text mode makes it 2 (a deviation)). Not registered: `autohide`, the section headers.
- **Layout** (`computeMinimapLayout`, a port of `EditorLayoutInfoComputer._computeMinimapLayout`): the minimap is `floor(((remaining - scrollbar - 2) * charWidth) / (textCharWidth + charWidth)) + 8` pixels wide, at most `maxColumn * charWidth`, where `remaining` is the width of the editor without its gutter, `charWidth` is the scale over the pixel ratio (a window of two device pixels per pixel uses scale 2 and a canvas of twice the size), and the 8 are the gutter of the minimap. On the right it sits next to the vertical scrollbar; on the left, before the gutter of the text. The text area is as wide as the editor without the gutter and without the minimap, which wrapping follows. `fill` stretches the lines to the height of the editor when the text is short (the scale grows up to one more than the setting) and `fit` does so only when that is needed to fit; when there are more rows than lines that fit, both show a sample of the rows (`computeMinimapSampling`: VS Code's `round(i * ratio + ratio / 2)` rows, from nothing each time). Emetos does not keep the last layout to break the loop of `fit` or `fill` with the width of wrapped text.
- **Slider and lines** (`createMinimapRenderLayout`, a port of `MinimapLayout.create`): the slider is `viewport / lineHeight * minimapLineHeight` high; it moves from the top to the point where the last row is at its top (with `editor.scrollBeyondLastLine`, which Emetos has by default) or at its bottom; when the minimap has more lines than fit, the lines drawn start so that the slider keeps its place, never moving the first line the wrong way while scrolling.
- **Drawing** (`minimapPainter`): a block of `scale` by `2 * scale` canvas pixels for each character that is not a space, in the color of its token blended half way into the background (`0.5 * minimap.foregroundOpacity` of the way), at 8 pixels from the left, a tab to its tab stop, a full-width character two blocks, up to the right edge. Only the lines whose row, text or token colors changed since the last frame are drawn; the pixels of the others are copied from the last frame to their new place (a scroll by a line draws one line). The marks of the selections (a bar across each selected line at half opacity, and the covered part of each line), of the find matches and of the text equal to the selection, and the slider, are drawn over the image on every frame.
- **Pointer**: a press on the slider drags it (the editor scrolls by the pointer's delta over the slider's ratio); a press elsewhere on a proportional minimap scrolls so that the row is in the middle of the editor (no smooth scroll), and on a minimap of the other sizes drags the slider from its middle; the wheel over the minimap scrolls the editor; with `showSlider: mouseover` the slider shows only while the pointer is over the minimap or dragging it, in `minimapSlider.background`, `hoverBackground` and `activeBackground`. Not ported: touch gestures, `minimap.autohide`, the shadow that shows while the text is scrolled sideways, the diff and problem marks (from later steps).
- **Colors**: `minimap.background` (the editor's when none), `minimap.foregroundOpacity`, `minimap.selectionHighlight`, `minimap.findMatchHighlight`, `minimap.selectionOccurrenceHighlight`, `minimapSlider.*`.
- **Tokens**: the minimap tokenizes the lines it shows on the UI thread for at most 2 ms a frame, after what the text layer needs; the view model repaints when the tokenizer finishes lines that the text or the minimap shows.

### 9.6 Sticky scroll

Uses the folding ranges (§9.3): the header lines of the ranges that contain the first visible line stay over the top of the text (`sticky.go`, `sticky_paint.go`; a port of VS Code's `StickyLineCandidateProvider` and `StickyScrollWidgetState`, built on the folding tree instead of a language's outline).

- **Settings**: `editor.stickyScroll.enabled` (true), `maxLineCount` (5, 1 to 20), `scrollWithEditor` (true: the sticky lines scroll sideways with the text).
- **Candidates**: a region of at least two lines is a candidate for the lines of its start line to its end line. The sticky lines are chosen by the position of the top of the viewport: the region at depth *d* sticks when its slot (`d * lineHeight`) is below the natural y of its start line, and while the slot is not below the bottom of its end line; when the end of the region is about to leave, the last sticky line is pushed up by the distance that remains (`Offset`), so it slides away under the line above. The number is at most `maxLineCount` and at most a quarter of the rows of the viewport (rounded). Lines hidden by a fold are not candidates and the lines come from the rows of the projection (folds, wrapping).
- **Drawing**: over the top of the text, in the colors `editorStickyScroll.background`, `editorGutter.background` over the gutter (`editorStickyScrollGutter.background`), `editorStickyScrollHover.background` for the line under the pointer, a border under the lines (`editorStickyScroll.border`) and a shadow of 4 pixels (`editorStickyScroll.shadow`, a gradient). The line numbers and folding controls of the gutter are drawn for each sticky line. The last line is drawn first so that it slides in under the others. The widget takes the pointer only over the lines, not over the shadow.
- **Pointer**: moving over a line sets the hover; a click moves the cursor to the clicked column of that line (column 0 on the gutter) and scrolls so that the line is not under the sticky lines (`RevealStickyPosition`); a Shift click scrolls the end of the range to the middle of the editor when it is off the screen; a click on the folding control folds the range. The wheel goes to the editor.
- **Reveal**: while sticky scroll is enabled, revealing a position (`RevealPosition`) keeps it clear of the sticky lines at the top (the rows that may be sticky are added to the top margin), so it is never hidden under them.
- Not ported: the outline model of language servers (area 3 may replace the candidates), `editor.stickyScroll.defaultModel`, the keyboard commands (`editor.action.focusStickyScroll`, `selectNext`, ...), the context menu, and the sticky lines of the diff editor.

### 9.7 Breadcrumbs

A bar above the editor (`breadcrumbs.go`, `breadcrumbs_widget.go`; a port of the file-path part of VS Code's `BreadcrumbsModel` and `BreadcrumbsControl`) with the path of the file; each segment opens a picker of its siblings. The symbol part is added in area 3.

- **Settings**: `breadcrumbs.enabled` (true), `breadcrumbs.filePath` (`on`, `last`, `off`) and `breadcrumbs.icons` (true). A bar that is off, or a document with no file (untitled, virtual), has no height. The settings are followed live.
- **Segments** (`BreadcrumbItems`): the parts of the absolute path of the file, a folder each and the file last. With a folder open and the file in it (§10.5; the window passes its folder as `BreadcrumbsOpts.Root`), the first segment is the folder, named as it is, and the others are relative to it. `last` shows only the file. A long path shrinks its segments (names are cut with an ellipsis); Emetos does not scroll the bar as VS Code does.
- **Drawing**: a bar of 22 px in `breadcrumb.background`, 13 px text in `breadcrumb.foreground`, a chevron between segments; the segment under the pointer is in `breadcrumb.focusForeground` and the one whose picker is open in `breadcrumb.activeSelectionForeground`. The icons are Codicons (a folder, a file); the file icon theme (§10.8) is not used yet.
- **Picker**: a click on a segment opens a `kit.ListOverlay` (§10.2) below it, in `breadcrumbPicker.background`, listing the entries of the folder that holds the segment, with the segment's own name focused. Folders come first, then files, each in natural order ignoring case (`ReadSiblings`). The folder is read in a goroutine with the `ctx` of the window and an answer that is not the latest is dropped; a folder that cannot be read shows one row that cannot be chosen. Typing filters the rows. Choosing a folder enters it (a `..` row goes back up); choosing a file closes the picker and calls `OnOpen`, which the shell turns into opening the file in the editor. A second click on the segment, Escape, a click outside and a change of file close it; a click on another segment switches to its picker.
- Not ported: the symbol path and its outline pickers, `breadcrumbs.symbolPath` and the other `symbol*` and `show*` settings, `breadcrumbs.useQuickPick`, `breadcrumbs.showEditorType`, the keyboard focus of the bar (`breadcrumbs.focus`, `focusAndSelect`, `toggle` and the arrow keys), the tree look of the picker (folders expand in place in VS Code), the file icon theme, `files.exclude` (a `ReadDir` option takes it from the workbench), dragging a segment, scrolling of a long path.

### 9.8 Find widget (`core/find`, `gui/editor`)

The model finds matches on a snapshot line by line (a multiline regex searches a bounded window of lines), capped at 19,999 highlighted matches like VS Code; tracks the current match; replaces with VS Code's replace pattern (`$n`, `$&`, `\n`, `\t`, `\u \l \U \L`) and preserve case.

#### 9.8.1 The model (`core/find`)

- **`Params`** (VS Code's `SearchParams`: the string, regex, match case and the word separators, which are not empty for whole words) make a **`Query`**, or none when the string is empty or the pattern does not compile. The pattern is an ECMAScript regular expression of `core/regex` (flags `i` unless match case, `m` when the search is multiline, `u` always); a string that is not a regular expression is escaped. A search is **multiline** when the string has a line feed or the regular expression can match one (`\n`, `\r`, `\W` or a line feed in it: `IsMultilineRegexSource`). A string without a line feed that is not a regular expression is searched with a plain substring search when its case matters (match case on, or no letters with another case), and otherwise with the expression. The text is held with line feeds only (SPEC §6.1), so `\r` is never found and `\n` matches every line break.
- **The search** (`FindMatches`, `FindMatchesIn` for several ranges whose touching ones are joined, `FindNext`, `FindPrevious`; VS Code's `TextModelSearch`) goes line by line, or, for a multiline search, over the lines joined by line feeds. `FindNext` and `FindPrevious` go round the text. A match is whole-word when the characters on both sides, or the first or last character inside it, are not regular characters of `editor.wordSeparators` (white space and line breaks count as separators). An empty match does not stop the search: it steps over one character (never into the middle of a surrogate pair or a UTF-8 sequence). Columns are byte columns; matches can be asked to capture the text of their groups (`Match.Groups`, an unmatched group is `""`).
- **Bounded windows**: a multiline search reads the text in windows of 5,000 lines with 500 lines of lookahead (a match starts in the first 5,000 and may run into the lookahead; the next window starts where the last match ended if it went further), so a document of millions of lines is never one string. Up to 5,500 lines it is one window, as in VS Code. A regular expression gives up after one second (`regex.Options.Timeout`).
- **`ReplacePattern`** (`ParseReplaceString`): `\n`, `\t`, `\\`, `\u \U \l \L` (one character or all the rest of the next group), `$$`, `$&` and `$0`, `$n` and `$nn`; a number that is not a group of the match is read as JavaScript reads it. Preserve case follows the case of the match (all upper, all lower, a capital first letter, the words of hyphenated or underscored names one by one).
- **`State`** (VS Code's `FindReplaceState`): the search and replace strings, the switches (with the overrides of a find with arguments, which the next change drops), the search scopes, `loop`, the position and the count of the matches and the current match; `Change` tells its listeners what it changed. A new search scope replaces the old one unless it is the same (VS Code leaves a scope alone when each new range differs from some old one, which never lets a scope change into another one: Emetos takes the evident intent).
- **`Model`** (VS Code's `FindModelBoundToEditorModel`) works for a `Host` (the selection and the cursors of the editor, scrolling, `editor.wordSeparators`, `editor.find.cursorMoveOnType`, and timers): it marks the matches (up to 19,999) as decorations of the document (`findMatch`, `currentFindMatch`, and the whole-line `rangeHighlight` and `findScope`), searches again 100 ms after an edit (240 ms after a change of the state in a document of more than 50 MB), moves to the next and previous match (from the decorations when there are fewer than 19,999, by searching otherwise; an empty match under the cursor is stepped over; a search that does not loop stops at the last match), `Replace` (the selection is replaced when it is a match, else the next match is selected), `ReplaceAll` (one undo step; the matches that touch are one edit; the selection follows the text; with 19,999 or more matches and no scope the whole text is replaced at once, with `^` and `$` matching at every line), `SelectAllMatches` (the selection that is a match stays the primary one) and `MoveToMatch`. The widget, the commands and the keys are §9.8.2.

#### 9.8.2 The widget and the commands (`gui/editor`)

- **The view model is the controller** (VS Code's `CommonFindController`): it owns the `find.State` (made when first asked for, `FindState`) and, while the widget is open, the `find.Model`, which is the model of §9.8.1 over a `find.Host` of the view model (the primary selection, `setSelections`, `RevealRangeInCenterIfOutsideViewport` for `Reveal`, `editor.wordSeparators`, `editor.find.cursorMoveOnType`, the timers of the window). Closing the widget (`IsRevealed` false) drops the model and with it every decoration of the view model's find owner (slot 3, `findOwner`); `DisposeFind` does so when the editor goes away. The switches (match case, whole word, regular expression, preserve case) are shared by the editors of a window (`FindMemory`, VS Code keeps them in the workspace storage; Emetos does not persist them yet).
- **Starting a find** (`startFind`, VS Code's `_start`): seeds the search string from the selection (a selection of one line, or the word at an empty selection; with a regular expression the string is escaped), forces the replace row open for Replace, limits the search to the selections when `editor.find.autoFindInSelection` says so (`always`, or `multiline` for a selection of several lines) or the command asks, takes `editor.find.loop`, opens the widget and, when asked, focuses its find or replace input. A search string that a command is given (`editor.actions.findWithArgs`) is never replaced by the seed (VS Code replaces it when the cursor is on a word; Emetos takes the evident intent).
- **Commands and keys** (ids and Linux keys as VS Code's): `actions.find` (Ctrl+F), `actions.findWithSelection` (the selection of several lines too; the focus stays), `editor.actions.findWithArgs` (`{"searchString","replaceString","isRegex","matchWholeWord","isCaseSensitive","preserveCase","findInSelection"}`), `editor.action.nextMatchFindAction` (F3; Enter in the find input), `previousMatchFindAction` (Shift+F3; Shift+Enter), `nextSelectionMatchFindAction` (Ctrl+F3) and `previousSelectionMatchFindAction` (Ctrl+Shift+F3: search for the selection or the word at the cursor, then move), `editor.action.startFindReplaceAction` (Ctrl+H: not on a read-only document; focuses the replace input when a line of text is selected or the find input has the focus), `closeFindWidget` (Escape, Shift+Escape), the switches `toggleFindCaseSensitive` (Alt+C), `toggleFindWholeWord` (Alt+W), `toggleFindRegex` (Alt+R), `toggleFindInSelection` (Alt+L: limits the search to the non-empty selections, a selection that ends at column 0 stopping at the end of the line before; again lifts it) and `togglePreserveCase` (Alt+P), `editor.action.replaceOne` (Ctrl+Shift+1; Enter in the replace input), `replaceAll` (Ctrl+Alt+Enter; Ctrl+Enter in the replace input) and `editor.action.selectAllMatches` (Alt+Enter; the editor gets the focus). A next or previous that finds no model (the widget is closed) starts a find (seeded when the search string is empty) and then moves; with `editor.find.closeOnResult` a move made from the find input closes the widget. The context keys are `findWidgetVisible` (in the editor's scope), `findInputFocussed` and `replaceInputFocussed` (in the scope of the widget's inputs, a child of the editor's: `editorFocus` is true there and `editorTextFocus` and `textInputFocus` false, so the keys of the text do not apply while typing a search). The editor's commands are bound while the editor *or* the widget has the focus. Not implemented yet: `editor.action.goToMatchFindAction` (needs the quick input, area 6), the small options widget that VS Code shows when a switch changes while the widget is closed, and the search history (`editor.find.history`).
- **The widget** (`findWidget`) is an overlay at the top right of the editor, 419 px wide (narrower in a narrow editor), 4 px below the top and left of the vertical scrollbar: a chevron that shows and hides the replace row (disabled on a read-only document), the find input with the match case, whole word and regular expression toggles inside it (red border when the search string finds nothing), the match count (`2 of 5`, `?` while the position is unknown, `19999+` at the cap, `No results`), previous and next (disabled without a search string or when the search cannot go that way: `State.CanNavigateBack/Forward`), the find in selection toggle (on while the search is limited) and close; the replace row has the replace input with the preserve case toggle inside it and the replace one and replace all buttons (disabled without a search string). It is not inside the editor's `Focus`, so the focus of its inputs is not the editor's; the buttons and toggles do not take the focus (the keys work from the inputs; step 6.5 adds their focus). The input of a find is one line (VS Code's grows to several: a multiline search string needs `findWithSelection` or an argument and is shown on one line). Deviation: `editor.find.addExtraSpaceOnTop` is not implemented (it needs view zones to push the first line down); the widget covers the first lines until the user scrolls, and the setting is not registered.
- **Highlights**: while the widget is open the overlay under the text draws the decorations of the find owner after the selections and the guides: `findScope` and `rangeHighlight` (the lines of the current match) across the whole row with `editor.findRangeHighlightBackground` and its border, `findMatch` with `editor.findMatchHighlightBackground` and its border, `currentFindMatch` with `editor.findMatchBackground` and its border (a match in a folded line is not drawn). The **overview ruler** is a layer over the vertical scrollbar's track (the width of the scrollbar, under its slider): a mark of at least 2 px for every match (middle third, `editorOverviewRuler.findMatchForeground`) and for the lines of the current match (all of the width, `editorOverviewRuler.rangeHighlightForeground`), at the height the line has in the whole content scaled to the height of the editor; marks that overlap are drawn once. Seeded colors: the find, widget, input and toggle colors of VS Code (`editorWidget.*`, `input.*`, `inputOption.*`, `inputValidation.errorBorder`, `toolbar.hoverBackground`, `widget.border`).
- **`kit.InputBox` and `kit.Toggle`** (§10.2) are first versions: the input box is Glutter's `EditableText` in a 25 px box with the input colors, a border that shows the focus or an error, a placeholder and trailing widgets; the toggle is VS Code's 20 px icon toggle (border and tint while on, hover background). Step 6.5 adds history, validation messages, several lines, focus and tooltips. The icon button was finished by step 6.1 (§10.2: 22 px, focus, tooltip, keyboard).

### 9.9 Snippets (`core/snippet`)

Parser for VS Code's snippet grammar (`$1`, `${1:default}`, `${1|a,b|}`, the variables, `${1/regex/format/flags}` transforms, `$0`). Variables are resolved synchronously from values the UI gathers first (the clipboard text is read before inserting). A snippet session tracks tab stops as decorations, mirrors edits to equal tab stops, and ends when the cursor leaves the snippet or reaches `$0`. Snippet files: `~/.config/emetos/snippets/<language>.json` and `*.code-snippets` (global, with `scope`; §9.9.2). Tab priority follows VS Code's when-clauses (`inSnippetMode`, `hasNextTabstop`, `hasSnippetCompletions`, Emmet's).

#### 9.9.1 The parser and the variables (`core/snippet`)

- **Parser** (`Parser`, a port of VS Code's `SnippetParser`): the scanner cuts the text into tokens (`$ : , { } \ / | + - ?`, numbers, names, other text) and the parser builds a tree of markers: `Text`, `Placeholder` (`$1`, `${1}`, `${1:default}`, `${1|a,b|}` for indexes above 0, `${1/regex/format/flags}`), `Variable` (`$name`, `${name}`, `${name:default}`, `${name/regex/format/flags}`), `Choice`, `Transform` and `FormatString` (`$1`, `${1}`, `${1:/upcase}`, `${1:+if}`, `${1:-else}`, `${1:?if:else}`, `${1:else}`), under a `TextmateSnippet`. `\$`, `\}` and `\\` are text; any other backslash is a backslash. Text that is not valid syntax (a missing `}`, an unbalanced regular expression, invalid flags) stays text: a snippet always parses. Placeholders of an index that has no default take the default of the first one that has; nested and cyclic references end. `Parse` can add the final tab stop `$0` (`InsertFinalTabstop`, `EnforceFinalTabstop`). Lengths and offsets of markers are bytes (§6.2). `ToTextmateString` writes a tree back as snippet text (as in VS Code, a placeholder with no default is written `$1`, so a digit after it reads on into the number).
- **Transforms** use `core/regex` in ECMAScript syntax with the flags `d g i m s u v y` (each once); a search is limited to one second and ends the replacing when it runs over. The shorthands are `upcase`, `downcase`, `capitalize`, `pascalcase`, `camelcase`, `kebabcase` and `snakecase` (with Unicode letters); an unknown one leaves the value. When nothing matched and a format string has an else branch, the else branches are the result.
- **Variables** are resolved synchronously by `VariableResolver`s from plain values the caller gathers before inserting: `SelectionResolver` (`SELECTION`, `TM_SELECTED_TEXT` with the lines of a selection of several lines re-indented as the variable is, `TM_CURRENT_LINE`, `TM_CURRENT_WORD`, `TM_LINE_INDEX`, `TM_LINE_NUMBER`, `CURSOR_INDEX`, `CURSOR_NUMBER`; `SelectionValuesOf` gathers them from a document; a cursor with no selection takes the text it typed over last), `FileResolver` (`TM_FILENAME`, `TM_FILENAME_BASE`, `TM_DIRECTORY`, `TM_DIRECTORY_BASE`, `TM_FILEPATH`, `RELATIVE_FILEPATH`), `ClipboardResolver` (`CLIPBOARD`, one line for each cursor when the lines are as many as the cursors), `CommentResolver` (`LINE_COMMENT`, `BLOCK_COMMENT_START`, `BLOCK_COMMENT_END`), `TimeResolver` (the `CURRENT_*` variables, all from one moment; the day and month names are English), `WorkspaceResolver` (`WORKSPACE_NAME`, `WORKSPACE_FOLDER`; empty with no folder; the window gives the name and path of its folder, §10.5) and `RandomResolver` (`RANDOM`, `RANDOM_HEX`, `UUID`), joined by `CompositeResolver`. A variable no resolver knows keeps its default text; one with a transform is always resolved (the transform sees an empty value).

#### 9.9.2 Sessions, snippet files and the Tab key (`core/snippet`, `gui/editor`)

- **Session** (`Session`, `Controller`; ports of VS Code's `SnippetSession` and `SnippetController2`): inserting a snippet resolves its variables (`Env`, gathered by the editor: the word separators, the path of the file and its path relative to the folder that is open, the comment tokens of the language, the folder, `editor.multiCursorPaste`, the clock and the zone, the clipboard text), adjusts its white space (the lines take the indentation of the line it goes into, tabs and spaces follow the document), replaces what the user typed to find it (`OverwriteBefore` and `OverwriteAfter`, bytes) and makes one edit for all the cursors, as one undo step. Every tab stop is a decoration of the editor's snippet owner (`snippet.Editor.Owner`; `DecorationOwner`, 6, when it names none; `snippetPlaceholder`; the final tab stop `finishSnippetPlaceholder`; the active tab stop grows when text is typed at its edges, the others do not). The cursors go to the first tab stop: one cursor for each placeholder of the same index (so the mirrors are typed together), and the text of a placeholder is selected. Tab and Shift+Tab move between the tab stops; leaving a placeholder applies the transforms of its mirrors; `$0` is the final stop, and a snippet without one ends where it was inserted. A snippet inserted while another is being filled in is nested into it (the tab stops are merged in order, the nested ones first). With several cursors each gets its own copy, and `editor.action.insertSnippet` works on all of them. The mode ends when the final tab stop is reached, when the cursors leave the tab stops (a selection that is not inside a placeholder), when the document is set again, when an undo comes back to the text before the snippet, or on Escape (`leaveSnippet`, which also collapses the cursors to the primary one); Enter does not end it.
- **Choices**: a tab stop with options (`${1|a,b|}`) shows them in a `SnippetPicker`, a short list below the caret that the editor widget shows as a `kit.ListOverlay` (above the caret when it does not fit; it takes the focus while it is open and gives it back). Enter on an option replaces the text of the tab stop by it and puts the cursor after it; Escape closes the list and leaves the first option. Step 6.17 moves the lists to the quick input.
- **Context keys** (set in the editor's scope): `inSnippetMode`, `hasNextTabstop`, `hasPrevTabstop`, `inSnippetChoice` and `hasSnippetCompletions` (the Tab key would insert a snippet).
- **Commands and keys** (ids as VS Code's): `jumpToNextSnippetPlaceholder` (Tab; in snippet mode with a next tab stop), `jumpToPrevSnippetPlaceholder` (Shift+Tab; with a previous one), `leaveSnippet` (Escape and Shift+Escape in snippet mode), `acceptSnippet` (goes through the tab stops to the final one; no key), `insertSnippet` (Tab; with `hasSnippetCompletions`, not in snippet mode: the Tab key of `editor.tabCompletion`) and `editor.action.insertSnippet` ("Insert Snippet"; writable documents; the argument is `{"snippet": "<text>"}`, or `{"name": "<name>", "langId": "<language>"}`, or nothing, and the user then picks from a filterable list of the snippets of the language at the cursor, those without a prefix too). The three tab stop commands weigh `WeightEditorContrib + 30`, so they win over `tab`, `outdent` and `insertSnippet`, which win over `tab` in turn; Escape in snippet mode wins over `removeSecondaryCursors` and `cancelSelection`.
- **Snippet files** (`File`, `Service`; ports of `snippetsFile.ts` and `snippetsService.ts`): the user's folder is `<config>/snippets` (§15). `<language>.json` is for that language; `*.code-snippets` is for any language, and each snippet names the languages in `scope` (a comma separated list; a scope `source.js` also matches the language `source`). The text is JSON with comments and trailing commas; a snippet is an object with a non-empty `body` (a string or an array of lines joined by `\n`), `prefix` (a string or an array: one snippet for each; none gives no snippet; missing is no prefix), `description`, `isFileTemplate`, `include` and `exclude` (globs, matched ignoring case against the file name, or the whole path when the glob has a `/`; exclude wins, include limits). In a `.code-snippets` file an object without a `body` is a group of snippets. A name that is not a variable (`${foo}`) becomes a placeholder (`${1:foo}`; the same name gets the same index), as in VS Code. `Service.Reload(ctx)` reads the folder again (the watcher of step 6.13 calls it; a file that cannot be read is left out and the first failure is returned); `Service.Snippets(Query)` gives the snippets of a language and a file, sorted by source and name. Not ported: snippets of extensions and of the workspace (`.vscode/*.code-snippets`; step 6.13), sorting by recent use, the toggle that disables snippets (`SetDisabled` takes identifiers, nothing calls it yet), the file template commands ("Fill File with Snippet") and the editor for snippet files.
- **Tab completion** (`editor.tabCompletion`: `off` (default), `onlySnippets`, `on`): with `onlySnippets` the editor looks, whenever the cursor moves, for the snippets of the language whose prefix the text before the cursor ends with (the word back to the last white space, at most 100 characters), or, for a selection on one line of at most 100 characters, that equal the selection. One match is inserted by Tab (the prefix is replaced); several are offered in the list. `on` needs the suggestions of area 3 and does nothing until then.
- **Colors**: `editor.snippetTabstopHighlightBackground` (`#7C7C7C4D` dark and high contrast dark, `#0A326433` light), `editor.snippetTabstopHighlightBorder` (none), `editor.snippetFinalTabstopHighlightBackground` (none) and `editor.snippetFinalTabstopHighlightBorder` (`#525252`, `#0A326480` light, `#292929` high contrast light). The tab stops are drawn under the text, with the occurrences; one with no text (the final tab stop is usually empty) is not drawn, the cursor is there.
- Deviations: the clipboard is read first when the snippet uses `CLIPBOARD` (the insertion waits for the desktop and is dropped if the document or the cursors changed meanwhile, as VS Code does); the text a cursor typed over (`TM_SELECTED_TEXT` for an empty selection) is not tracked yet (`Overtyped` is nil); the languages at the cursor are not told apart inside an embedded language (the language of the document is used); the Tab key does not wait for tokenization.

### 9.10 Emmet (`core/emmet`)

Abbreviation parser and HTML output; CSS abbreviations from Emmet's snippets (MIT); abbreviation extraction before the cursor; `emmet.includeLanguages`, `emmet.syntaxProfiles`, `emmet.triggerExpansionOnTab` (off by default, as in VS Code).

#### 9.10.1 Abbreviations and markup output (`core/emmet`)

Step 5.10 ports Emmet's markup abbreviations (`emmetio/emmet`, MIT; the code says "Ported from Emmet: <file>"). The package is plain Go with no UI; offsets are byte offsets (every character with a meaning in an abbreviation is ASCII, the other bytes are text; the no-break space is white space and ä, ö, ü and their capitals are letters of element names, as in Emmet). Step 5.11 added the CSS part, the extraction of the abbreviation before the cursor and the expansion at the cursor (`Config.Type`, the `Stylesheet*` options, `css.json`, `ExtractAbbreviation`, `ExpandAt`: §9.10.2).

- **Pipeline** (the layers of Emmet): `Tokenize` (the scanner and tokenizer) -> `ParseTokens` (elements and groups, `Statement`) -> `Convert` (unrolls groups and repeaters into `Node` trees; `ParseAbbreviation` does the three) -> `Parse` (adds the markup steps: snippets, then the transformations) -> `Stringify` (a formatter for the syntax); `Expand(abbr, cfg)` is `Parse` and `Stringify`. `Resolve` does the markup steps for a tree that is parsed already.
- **Grammar**: elements with names of letters, digits, `_ - : !` and umlauts; `>` child, `+` sibling, `^` climb up (any number), `( )` groups, `*N` repeaters and `*` (implicit: one copy for each non-blank line of the wrapped text), `#id`, `.class` (the shorthands may be repeated: `..foo` is a second kind of class, see JSX), `[attr attr=value attr="quoted" attr='quoted' attr={expression} attr. !implied "default value"]`, `{text}` (nested braces are allowed), `$` numbering (`$$$` padded, `$@-` reversed, `$@3` base, `$@^` numbering of the parent repeater), `$#` the text of the implicit repeater, `${1:placeholder}` fields, `${name}` variables, `/` self-closing, `\` escapes, a `/` between two digits in a class name (`w1/2`). Implicit tags: an element with attributes and no name is a `li` in `ul`/`ol`, `td` in `tr`, `span` in an inline element, `div` otherwise (the parent is the closest element, or `Config.Context`). Text given with the abbreviation (`Config.Text`: a string, or a list of lines) goes into the implicitly repeated elements, or into the deepest element; a link that wraps a URL or an e-mail address takes its `href` (`Options.MarkupHref`).
- **Snippets**: `assets/html.json` (155 entries), `xsl.json` (37) and `pug.json` (1), and `variables.json` (`lang`, `locale`, `charset`, `indentation`, `newline`) are copied by `scripts/update-assets.sh` and embedded; a snippet is an abbreviation (`a:blank`, `fset`, `!`, ...), resolved recursively (a snippet that refers to itself, like `img`, is left as it is), with the attributes of the node added to it; a snippet that does not parse is left out (`Config.Warn` is told). `Config.Snippets` and `Config.Variables` start from these and the user adds over them (`SetSnippets`, `SetVariables`; the setting `emmet.variables` is read by `VariablesFromSettings`).
- **Transformations**: merging of attributes (equal names; classes are joined), `lorem[lang][N[-M]]` (Latin, `ru`, `sp`; random words, `Config.Rand` to make them repeatable; at most `MaxLoremWords` = 10000 words), the label preprocessor (`label>input` has no `for`/`id`), XSL (`select` of `xsl:variable` and `xsl:with-param` with content), BEM (`Options.BEMEnabled`: `-element`, `_modifier`, block from the ancestors or `Config.Context`).
- **Output** (`Stringify` by `Config.Syntax`): `html` (and `xml`, `xsl`, `jsx`, `vue`, `svelte` and any other name) with Emmet's formatting rules (block and inline elements, `inlineBreak`, `formatSkip`, `formatForce`, text with line breaks, snippets that wrap their children in a field, comments `[#ID][.CLASS]` templates), `haml`, `pug` and `slim` (the indent based formats). The editor's indentation and line break go in `Config.SetOutput(indent, newline, baseIndent)` (`Options.Indent`, `Options.Newline`, `Options.BaseIndent`; `${indentation}` and `${newline}` take the same values); the fields of the output (tab stops) are written by `Options.Field` (`SnippetField` writes `${1:placeholder}`; the default writes the placeholder) and the text by `Options.Text` (to escape it). Positions given to the hooks are bytes.
- **Syntax defaults** (`NewConfig(syntax)`): `xml` and `xsl` close with `/>`, `xhtml` with ` />`; `xsl` and `pug` add their snippets; `jsx` has `className`, `htmlFor`, `styleName` for `..foo` and `styles.foo` values, and expressions in braces; `vue` writes `..foo` as `:class="foo"`; `svelte` has the JSX mode.
- **Profiles** (`emmet.syntaxProfiles`; `Config.ApplyProfiles(profiles)` picks the profile named by the syntax, `ApplyProfile` applies one): the keys are Emmet 2's options by short name (`tagCase`, `attributeCase`, `attributeQuotes`, `format`, `formatLeafNode`, `formatSkip`, `formatForce`, `inlineBreak`, `compactBooleanAttributes`, `booleanAttributes`, `reverseAttributes`, `selfClosingStyle`, `inlineElements`) and the names of Emmet 1's profiles that VS Code's documentation still shows (`tag_case`, `attr_case`, `attr_quotes`, `tag_nl` (true, false or "decide" = true), `indent` (false is no indentation), `inline_break`, `self_closing_tag` (true `<br/>`, false `<br>`, "xhtml" `<br />`), `compact_bool`, `filters` ("bem", "c")). Unknown keys are ignored; a known key with a wrong value is the error `ProfileValueInvalid` and changes nothing. As in VS Code, JSX is closed like XHTML and XML and XSL like XML unless the profile sets the style. VS Code's helper library that maps the profile to Emmet's options is not in `reference/`; the table above is Emetos's own, built from the names Emmet 1 and 2 use.
- **Limits** (Emmet has none unless `maxRepeat` is given): the elements an abbreviation makes are limited to `Config.MaxRepeat` in all (default `DefaultMaxRepeat` = 1000, at most `HardMaxRepeat` = 10000; counts in the text are read up to 2^30), the nesting of groups and children to 1000 (`NestingTooDeep`), the width of `$$$` numbers to 64.
- **Errors** (`github.com/rm4n0s/errors`; the message ends with the 1-based position as Emmet's, the metadata has `pos` and the abbreviation): `UnexpectedCharacter`, `FieldUnclosed`, `PlaceholderUnclosed` (tokenizer), `UnexpectedToken`, `UnexpectedAttributeToken`, `UnclosedQuote`, `NestingTooDeep` (parser), `ProfileInvalid`, `ProfileValueInvalid`, `VariablesInvalid`, `VariableValueInvalid` (configuration), and `EmmetAssetMissing`, `EmmetAssetInvalid`, `LoremAssetMissing`, `LoremAssetInvalid` (the embedded files; a test checks them).
- **Settings registered**: `emmet.variables` and `emmet.syntaxProfiles` (objects, default `{}`, VS Code's descriptions); step 5.11 added `emmet.includeLanguages`, `emmet.excludeLanguages` and `emmet.triggerExpansionOnTab` (§9.10.2).
- **Deviations from Emmet**: offsets and the positions given to the output hooks are bytes (Emmet's are UTF-16 units); the limits above; `Config` is a struct changed in place instead of a merged partial (`NewConfig` then assign); the snippets are parsed every time they are used (no cache); a list of lines of text asked beyond its end is empty (Emmet's `undefined`); `Convert` of an empty abbreviation with text gives no nodes (Emmet throws); two bugs of Emmet's token writer are fixed: a group bracket in the name of an attribute was written `}` and a field without a placeholder in a name lost its closing brace; `compactBoolean` is also named so (Emmet 2's long name is `compactBooleanAttributes`); no `cache`, no `emmet.preferences` as a registered setting (the core reads its stylesheet keys, §9.10.2), no `emmet.extensionsPath` (custom snippet files) and no `emmet.showExpandedAbbreviation`/`emmet.showAbbreviationSuggestions` (the completion of abbreviations is out of scope with the rest of the suggestions of area 3).
- **Tests**: ports of Emmet's `test/{markup,expand,format,output,snippets,lorem}.ts` and `packages/abbreviation/test/{tokenizer,parser,convert}.ts` (markup cases only), tables for the profiles, routes of every error tag, `FuzzParse` and a seeded random test.

#### 9.10.2 CSS abbreviations, extraction and expansion at the cursor (`core/emmet`)

Step 5.11 adds to the same package (plain Go, byte offsets, nothing of Glutter or `gui`), the stylesheet half of Emmet, the extraction of an abbreviation from a line, and the part of VS Code's Emmet extension (`extensions/emmet/src/abbreviationActions.ts`, `util.ts`) that does not need the document or the editor. The code says "Ported from Emmet: <file>" or "Ported from VS Code: <file>".

- **Stylesheet pipeline** (Emmet's `css-abbreviation` package and `src/stylesheet`): `TokenizeCSS(abbr, isValue)` -> `ParseCSSTokens` (`ParseCSS` does both; `CSSProperty{Name, Value []*CSSValue, Important}`; a function call is a `CSSToken` of type `CSSFunction`) -> `ParseStylesheet(abbr, cfg)` (fuzzy matching of property names, keywords and numbers) -> `StringifyStylesheet(props, cfg)`; `ExpandStylesheet` is the three, and `Expand` calls it when `Config.Type` is `TypeStylesheet`. `css.json` (249 entries, 253 names; copied by `scripts/update-assets.sh`) holds the snippets: a *property* snippet (`"bd": "border:${1:1px} ${2:solid} ${3:#000}"`, values separated by `|`) or a *raw* one (`@m`, `@kf`). The properties are nested (`background-position-x` into `background-position` into `background`) so that the keywords of the specific ones can be used with the shorthand. An abbreviation is matched with `scoreMatch` (the first letters must be equal; characters closer to the start of the name and after a `-` score more); `Options.StylesheetFuzzySearchMinScore` is the lowest score accepted. The rest as Emmet: `p10` is `padding: 10px`, `p.4` `padding: 0.4em`, `z10` `z-index: 10` (`StylesheetUnitless`), `10p` is `10%` and `10r` `10rem` (`StylesheetUnitAliases`), `m0-a` `margin: 0 auto` (`StylesheetKeywords`), `c#f.5` `color: rgba(255, 255, 255, 0.5)` and `c#fc0` `color: #fc0` (`StylesheetShortHex`), `lg(...)` a `linear-gradient`, `p!` `padding: ${0} !important`, `bxsh` a custom property; the output uses `StylesheetBetween` and `StylesheetAfter` and, with `StylesheetJSON`, is CSS-in-JS (`marginTop: '10px 20px',`). `Config.Context` is the scope as in Emmet: `ScopeSection` (raw snippets only, the properties that matched no snippet are left out), `ScopeProperty`, `ScopeGlobal`, `ScopeValue` or the name of a property (the abbreviation is its value). `StylesheetStrictMatch` leaves out what matches nothing. Raw snippets keep their tabs (`Options.Indent` is not applied to them): a snippet insertion turns them into the indentation of the document.
- **Configuration**: `Config.Type` (`TypeMarkup`, the default, or `TypeStylesheet`) and the `Options.Stylesheet*` fields (defaults of Emmet: keywords `auto inherit unset none`, unitless `z-index line-height opacity font-weight zoom flex flex-grow flex-shrink`, short hex on, between `": "`, after `";"`, `px`, `em`, aliases `e p x r`, no JSON, fuzzy score 0, not strict). `NewConfig(syntax)` makes a stylesheet configuration for `css scss less sss sass stylus` (`IsStylesheetSyntax`): `sass` has no `;`, `stylus` has no `;` and a space between name and value. `SnippetText` (for `Options.Text`) escapes `\` and `$` of the text for a snippet, as `SnippetField` (for `Options.Field`) writes the tab stops. `Config.ApplyPreferences(prefs)` reads the stylesheet keys of VS Code's `emmet.preferences` object: `css.intUnit`, `css.floatUnit`, `css.unitAliases` (an object, or Emmet 1's `e:em, p:%`), `css.fuzzySearchMinScore` (0 to 1), `css.color.short`, and `<syntax>.propertyEnd` and `<syntax>.valueSeparator` (the syntax of `scss`, `less` and `sss` is `css`); the other keys are ignored, and a wrong value changes nothing and is `PreferenceValueInvalid`. The setting `emmet.preferences` itself is not registered in this step (nothing passes it yet).
- **Extraction** (`ExtractAbbreviation(line, pos, ExtractOptions{LookAhead, Type, Prefix})` -> `Extracted{Abbreviation, Location, Start, End}`; Emmet's `extract`): the abbreviation that ends at `pos` (a byte offset in the line, clamped), found by reading back over letters, digits and `# . * : $ - _ ! @ % ^ + > /`, with `[...]` and `{...}` (attributes and text, markup only) and `(...)` kept balanced and with everything inside brackets accepted, stopping at the end of an HTML tag (`<span>` before the abbreviation) or at a character that does not belong; leading `* + > ^` are dropped. With `LookAhead` it first moves over the `]`, `}`, `)` and one quote that an editor closed after `pos`. With `Prefix` it starts at the nearest prefix before `pos` (`Start` is the place of the prefix). In `TypeStylesheet` only parentheses count. Limit: the search never goes back more than `MaxExtractLength` (4096) bytes, and an abbreviation that is longer is not found (Emmet has none; the scan is linear, but a minified line can be megabytes long). `isAtHTMLTag` and `consumeQuoted` are ports of `is-html.ts` and `quotes.ts`.
- **Languages** (VS Code's `util.ts` and `getSyntaxFromArgs`): `SyntaxFor(languageID, includeLanguages, excluded) (syntax, ok)` gives the Emmet syntax for a language id of the editor: excluded languages give false; `MappingForIncludedLanguages` merges VS Code's built-in mapping (`handlebars` and `php` to `html`) with `emmet.includeLanguages` (entries whose value is not one of `html jade slim haml xml xsl css scss sass less stylus javascriptreact typescriptreact` are dropped); `EmmetMode` maps `javascriptreact`, `typescriptreact` and `jsx-tags` to `jsx`, `jade` to `pug`, `sass-indented` to `sass`, and accepts only `html xml xsl jsx js pug slim haml css sass scss less sss stylus`, so `javascript`, `vue` and `markdown` give false unless `emmet.includeLanguages` maps them. `IncludeLanguagesFromSettings(value)` and `ExcludedLanguagesFromSettings(value)` read the two settings the way VS Code does (entries of the wrong type are ignored). `VS Code's `parentMode` (the language of the grammar a language is embedded in) is not supported.
- **`ExpandAt(req ExpandRequest) (ExpandResult, bool, error)`**: `ExpandRequest{Syntax, TextBefore, Selection, Variables, Profiles, Preferences, Indent, Newline, BaseIndent}`, `ExpandResult{Start, End, Abbreviation, Text, Syntax}`. `Syntax` is the result of `SyntaxFor`. `TextBefore` is the text of the cursor's line from its start to the cursor; `Selection`, when not empty, is the selected text and replaces `TextBefore`. It gives false with no error when there is nothing to expand: no syntax, `TextBefore` empty or ending with a space or a tab (the Tab key then is a Tab), nothing extracted (without a look ahead, `Type` by the syntax), the abbreviation is not valid (`IsAbbreviationValid`), or a stylesheet abbreviation ends with `:` (VS Code issue 1623). For `html`, `<div` before the cursor is `div` and the range takes the `<`. A selection is expanded as a whole: the abbreviation must start at its first byte (the helper's `extractAbbreviationFromText`), and wrapping the selection (`wrapWithAbbreviation`) is not done. Filters `|bem`, `|c` and `|t` (up to three) at the end of the text are removed from the abbreviation, kept in the range, and turn on BEM and comments (the profile's `filters` do the same). `Start` and `End` are byte offsets in `TextBefore` (in `Selection`); `Text` is a snippet: tab stops as `${1:name}`, `${1}` and `${0}`, with `\` and `$` of the text escaped, lines joined by `Newline` (default `"\n"`), indented by `Indent` (default a tab) and, from the second line, by `BaseIndent`. The configuration is made by `ExpandAt`: `NewConfig(Syntax)`, `Variables` (`emmet.variables`; Emmet's `indentation` and `newline` follow the output options), `Profiles` (`emmet.syntaxProfiles`, markup only), then for stylesheets the VS Code default `css.fuzzySearchMinScore` of 0.3 (`DefaultFuzzySearchMinScore`; Emmet's own is 0) and `Preferences`. An error is the tag of the parser or of the configuration (`NestingTooDeep`, `CSSUnexpectedToken`, `ProfileValueInvalid`, `PreferenceValueInvalid`, ...) with the route from `ExpandAt`. `IsAbbreviationValid(syntax, abbr)` is the check of VS Code's helper: a stylesheet abbreviation starts with a letter, `-`, `!`, `@` or `#`, with a `#` first it is a hex color of one to six digits, and before a `#` it is not the name of an HTML tag (`div#main` is a selector); a markup abbreviation starts with a letter, `!`, `(`, `[`, `#`, `.` or `{`, ends with a letter, a digit or one of `) ] } # . * $ ! /`, and `!` alone (any number of them) is valid when it starts with `!`.
- **The contract of the user interface** (`editor.emmet.action.expandAbbreviation`, "Emmet: Expand Abbreviation", writable documents; Tab with `editorTextFocus && tabDoesNotMoveFocus && config.emmet.triggerExpansionOnTab`; weight `EditorContrib`, so the tab stop commands of the snippet session win over it, §9.9.2): for the language id at the cursor (the document's language, or the embedded one when the editor knows it), `syntax, ok := SyntaxFor(id, IncludeLanguagesFromSettings(emmet.includeLanguages), ExcludedLanguagesFromSettings(emmet.excludeLanguages))`; when `!ok` the command does what Tab does (`tab`) if `emmet.triggerExpansionOnTab` is on, and nothing otherwise. With `emmet.triggerExpansionOnTab` on and any non-empty selection, the key is a plain Tab. Each cursor is expanded on its own, in reverse order of position: `TextBefore` is its line up to the cursor, `Selection` its text when it is not empty, `Variables` from `VariablesFromSettings(emmet.variables)`, `Profiles` the object `emmet.syntaxProfiles`, and `Indent`, `Newline` and `BaseIndent` empty (the snippet insertion indents the lines and uses the document's line break). The text `res.Text` replaces the bytes `res.Start..res.End` of the line (the selection when there is one) as a snippet through the session of §9.9.2 (`OverwriteBefore` is `End - Start`); when every cursor gave the same text, one snippet is inserted at all of them, else each gets its own. Nothing was expanded (all false) is a plain Tab when `emmet.triggerExpansionOnTab` is on; an error is shown as the notification "Failed to expand abbreviation" (and is logged) and the key is a plain Tab too.
- **Settings registered** (VS Code's names, defaults, descriptions and scopes): `emmet.includeLanguages` (object, `{}`), `emmet.excludeLanguages` (array of strings, `["markdown"]`) and `emmet.triggerExpansionOnTab` (boolean, `false`; language-overridable). `emmet.showExpandedAbbreviation`, `emmet.showAbbreviationSuggestions` and the other settings of the completion provider are not registered (suggestions are area 3).
- **Deviations**: (1) The helper library of VS Code, `@vscode/emmet-helper`, is not in `reference/`: `IsAbbreviationValid`, the filters and the use of the preferences are written from its documented behavior, not ported from its source, and may differ in the details (the markup rule that a number or numbers with dots only (`.5`, `1.5`) is not an abbreviation is Emetos's own). (2) The cursor is assumed to be where an abbreviation may be: for the languages of markup it is in markup, for stylesheets in a rule. VS Code's checks that need a parse of the document are not done: `isValidLocationForEmmetAbbreviation` (comments of a stylesheet, the selector of a rule and the value of a property, where only a color or `!` expand; the text of a tag, `<script>` types), the CSS inside `<style>` and `style=""` of an HTML document (unless the editor passes the id of the embedded language), `parsePartialStylesheet`, `getHtmlFlatNode`, and the check of symbols of JavaScript. (3) `wrapWithAbbreviation`, `emmet.extensionsPath`, `emmet.optimizeStylesheetParsing`, `emmet.useInlineCompletions` and the other Emmet commands (balance, match tag, ...) are not implemented. (4) A snippet of a stylesheet that does not parse is left out and `Config.Warn` is told (Emmet throws); `ScopeValue` and the property scopes are there for the editor to use when it can tell where the cursor is. (5) Property names, keywords and the abbreviation are ASCII: the order of the keywords of a property, the lowercase of the match and the `toFixed` of numbers follow JavaScript's (`jsToFixed`), but characters over 127 are not letters. (6) Errors, with the tags `CSSUnexpectedCharacter`, `CSSUnexpectedBracket`, `CSSFieldUnclosed`, `CSSPlaceholderUnclosed` (tokenizer), `CSSUnexpectedToken`, `CSSNestingTooDeep` (parser; function calls nested over 1000 deep), `CSSSnippetValueEmpty` (a snippet) and `PreferenceValueInvalid`; the messages end with the 1-based place for the tokenizer and the 0-based place for the parser, as Emmet's.
- **Tests**: ports of Emmet's `test/stylesheet.ts` (all 117 assertions), `test/extract-abbreviation.ts` (all 58) and `packages/css-abbreviation/test/{tokenizer,parser}.ts` (all 88), tables for `SyntaxFor`, `IsAbbreviationValid`, `ExpandAt` (markup and stylesheet, base indentation, a prefix that is not an abbreviation, the colon, the filters, multi-byte text), the preferences, routes of every error tag, `FuzzParseCSS`, `FuzzExtract` and a seeded random test.

- **In the editor** (`gui/editor/emmet.go`): `editor.emmet.action.expandAbbreviation` follows the contract above with the settings in `Options.Emmet` (the editor reads `emmet.*` when the settings change); the context key `config.emmet.triggerExpansionOnTab` is set in the editor's scope. The expansions of all the cursors go in through `snippet.Controller.Apply` (§9.9.2), so the tab stops work and the insertion is one undo step. The key is `Tab` with `editorTextFocus && !editorReadonly && !editorTabMovesFocus && !editorHasSelection && !inSnippetMode && config.emmet.triggerExpansionOnTab`, at `WeightEditorContrib` and registered before the snippet keys, so the order for Tab is: a tab stop of a snippet that is being filled in, then a snippet whose prefix is before the cursor (`insertSnippet`), then Emmet, then `tab`. A selection of several lines is left alone (Emmet's wrap command is not implemented). An error of the expansion (`VariablesInvalid` and the tags of §9.10.1) makes the key a plain Tab and is returned as the error of the command, which the shell shows as a notification and logs.

### 9.11 Diff and merge

- `core/diff`: VS Code's default ("advanced") lines diff: dynamic programming for small inputs and Myers O(ND) for large ones, VS Code's heuristics (shifting to line and blank-line boundaries), refinement to character changes, ignore trim whitespace, and a time limit (`diffEditor.maxComputationTime`, 5 s) after which the unrefined line diff is shown. Moved-code detection is out of scope.
- Three-way merge: (a) **conflict markers**: parse `<<<<<<<`, optional `|||||||` (diff3 base), `=======`, `>>>>>>>` into conflicts (VS Code's `merge-conflict` parser); the current and incoming inputs are the file with every conflict taken from one side, the base is the `|||||||` sections or, without them, empty conflict regions; (b) **`--merge` inputs**: base, input 1 (incoming) and input 2 (current) are diffed against the base, and overlapping changes become conflicts (VS Code's `ModifiedBaseRange`). The result starts as the base with every non-conflicting change applied and each conflict region holding the base text, marked unhandled.
- `gui/diffeditor`: two editors side by side (or inline), aligned with view zones, scroll-synced, changed lines and characters colored, an overview ruler, next/previous change (Alt+F5, Shift+Alt+F5); the original side is read-only; save and dirty apply to the modified side; narrow widths switch to inline (`diffEditor.useInlineViewWhenSpaceIsLimited`).
- `gui/mergeeditor`: incoming (left) and current (right) on top, the result below, with accept incoming/current/both (current then incoming) per conflict and for all, and "Complete Merge": for a marker file it saves the file; for `--merge` it writes the `result` path and exits 0 when `--wait` is on (1 if the window closes without completing).

## 10. The workbench (`gui/workbench` and others)

### 10.1 Layout

Menu bar (File, Edit, Selection, View, Go, Help) at the top, activity bar on the left, primary side bar, editor area, panel, status bar. Part sizes, visibility and the panel position are saved per window (§10.10). The window's title bar is the compositor's, or Glutter's where the compositor draws none (`DecorationsAuto`); Emetos adds nothing to it except the title (`<file> - <folder> - Emetos`).

**Built in `gui/workbench` (step 6.6).** `Workbench` is the widget that lays the parts out as VS Code's grid does, with `kit.SplitView`: the menu bar area over a row of the activity bar, the side bar and the center, over the status bar; the center is the editor area and the panel, in a split of its own. The parts are empty containers that the views of later steps fill (the options of `Workbench` take the content of each: the editor area, the title and body of the side bar, the tabs and body of the panel, the items of the status bar, the menus of the menu bar, the icons of the activity bar).

| Part | Size (VS Code's) | Notes |
|---|---|---|
| Menu bar area | 30 px, as high as `kit.MenuBar`; none when hidden | `window.menuBarVisibility`: classic and visible show it, toggle shows it after the Alt key (or `workbench.actions.menubar.focus`), hidden never. The bar is always mounted, for the Alt key. Background and border: `titleBar.activeBackground`, `titleBar.border` |
| Activity bar | 48 px wide, fixed | Side of the side bar (left, or right with the side bar). Icons at the top, a Manage area at the bottom. `activityBar.background`, `activityBar.border` |
| Side bar | 300 px, at least 170 | Title (uppercase, 11 px, 35 px high) over the body. Priority low. `sideBar.*`, `sideBarTitle.*` |
| Editor area | at least 220 x 70 | Highest priority: takes what the window gains or loses, until it is at its least; then the panel and the side bar give way, in that order of priority. Hosts the editor with its breadcrumbs, the notices and the home page |
| Panel | 300 px, at least 77 high or 300 wide | Bottom, top, left or right of the editor area. Title strip (35 px) with the tabs of its views, a maximize and a hide button. Priority low. `panel.*`, `panelTitle.*` |
| Status bar | 22 px | Left and right areas for the items of step 6.20. `statusBar.*`, and `statusBar.noFolder*` while no folder is open |

The split views never lay out for no room (a window that has no size yet, or is minimized): the panes keep the sizes they were given. A part that moves (the panel to another side, the side bar to the other side) keeps its widgets and their state (global keys), and a hidden part comes back with the size it had. Maximizing the panel hides the editor area and gives the panel its place; restoring gives the panel the size it had. Hiding a part that has the focus focuses the editor area (the panel, when the editor area is hidden).

**State.** `Layout` is the model (no widget): `State()` gives and `Restore(LayoutState)` takes the visibility of the side bar, activity bar, status bar and panel, the width of the side bar, the height and the width of the panel (also its last non-maximized size, since a maximized panel does not record its size), the side of the side bar, the position of the panel and whether it is maximized. Step 7.5 writes it. The settings below decide where the side bar is and whether the activity bar and the status bar are shown, now and whenever they change, as in VS Code; the position and the size of the panel are state, and `workbench.panel.defaultLocation` is where a new window starts. The panel is hidden in a new window, as in VS Code.

**Commands** (VS Code's ids, titles and Linux keys; they are registered with the other commands, §11.2): `workbench.action.toggleSidebarVisibility` (Ctrl+B), `workbench.action.togglePanel` (Ctrl+J), `workbench.action.toggleMaximizedPanel`, `workbench.action.positionPanelLeft`, `...Right`, `...Bottom`, `...Top`, `workbench.action.focusSideBar` (Ctrl+0), `workbench.action.focusActiveEditorGroup`, `workbench.action.focusPanel`, `workbench.action.focusStatusBar`, `workbench.action.focusActivityBar`, and the ones VS Code keeps in a setting, which write it: `workbench.action.toggleStatusbarVisibility` (`workbench.statusBar.visible`), `workbench.action.toggleActivityBarVisibility` (`workbench.activityBar.location`, hidden or default) and `workbench.action.toggleMenuBar` (`window.menuBarVisibility`: classic or visible to toggle, else classic), and `workbench.actions.menubar.focus`. Showing a part moves the panel or side bar into view before it gets the focus.

**Settings:** `workbench.sideBar.location` (left, right), `workbench.activityBar.location` (default, top, bottom, hidden; top and bottom are registered but the activity bar stays at the side of the side bar), `workbench.statusBar.visible`, `workbench.panel.defaultLocation` (left, bottom, top, right), `workbench.panel.opensMaximized` (always, never, preserve), `window.title`, `window.titleSeparator`.

**Context keys** (set in the scope of the window, named as VS Code's `contextkeys.ts` names them): `sideBarVisible`, `sideBarFocus`, `panelVisible`, `panelFocus`, `panelPosition`, `panelAlignment` (always `center`), `panelMaximized`, `mainEditorAreaVisible`, `editorAreaFocus`, `statusBarFocused`. Each part has a focus scope and a context key scope of its own below the window's (registered with `kit.FocusScopes`), for the views in it; the activity bar has no key of its own, as in VS Code.

**Dialogs.** The workbench holds the one `kit.DialogHost` of the window, over everything; while a dialog shows, the key dispatcher of the window runs no command and uses no key.

**Menus and the menu bar (step 6.7).** The menu bar is made from the **menu registry** (`command.MenuRegistry`, VS Code's `MenuRegistry` of `platform/actions/common/actions.ts`; it is in `core/command`, which §5.2 gives to the registries of commands, menus and views). A menu has an id (a string: VS Code's `MenuId`s `MenubarMainMenu`, `MenubarFileMenu`, `MenubarEditMenu`, `MenubarSelectionMenu`, `MenubarViewMenu`, `MenubarGoMenu`, `MenubarTerminalMenu`, `MenubarHelpMenu`, `MenubarPreferencesMenu`, `MenubarAppearanceMenu`, `MenubarRecentMenu`, `PanelPositionMenu`, `EditorContext`, `ExplorerContext` and `GlobalActivity`, the Manage menu) and holds items, each either a command or a submenu (another menu id) with an optional title (the command's when empty), a mnemonic title (`"&&Undo"`: `&&` marks the mnemonic as VS Code writes it), a toggled title, a `group` (`1_do`, `2_ccp`... as VS Code names them), an `order`, a `when` (the item is in the menu), a `precondition` (overrides the command's: the item stays, dimmed) and a `toggled` expression (the check mark). `MenuRegistry.Items(menu, ctx)` gives the entries as VS Code's `Menu.getActions` does: the items whose `when` holds, groups sorted by name (`navigation` first, no group last), items by order and then by title, one separator between two groups, no empty group, no empty submenu, no item whose command is not registered or that has no title. A menu can also have **providers** (`SetProvider`), functions asked each time the menu is built, whose items are sorted with the others: the recently opened files, for instance. `MenuRegistry.All()` lists the rows; a test checks that every row of `DefaultMenus` refers to a registered command and shows a title. The rows of the built-in menus are data in one file (`command/menus_default.go`), in VS Code's groups and orders: a step that adds a command VS Code puts in a menu adds its row there (rule 7 of the plan). `MnemonicMenuLabel` turns a title into a label of the menu widgets (`&&File` into `&File`, a single ampersand into `&&`).

`workbench.MenuSource` turns entries into `kit.MenuItem`s: labels with the mnemonics of the menu bar (the context menus show none), the key of the command (`keybinding.Resolver.LookupPrimaryKeybinding`, written in the label style of Linux: `Ctrl+Z`), the check mark, the dimmed look of a disabled item, submenus and separators. The menu bar is `BarMenus()`: the submenus of `MenubarMainMenu` that have items, so a menu with no command yet (File, Terminal and Help until their steps) is not in the bar, as in VS Code. Each menu is built when the user opens it (`kit.MenuBarMenu.Source`; `kit.MenuItem.Data` carries the arguments of the command back to `OnRun`, and `kit.MenuBarController.Open` opens a menu from outside), in the context of that moment (§11.2): the context keys of the window, the settings as the keys `config.<setting>` (`config.workbench.statusBar.visible`...) and the keys the window keeps for the editor it shows (`editorWordWrap`, `canToggleWordWrap`, `editorIsOpen`, `editorReadonly`), which the editor's own scope cannot give because the menu has the focus. Running an item runs its command through the registry with `command.SourceMenu` and the arguments of the item, in the second frame after the menu closed: the editor binds its commands while it has the focus, and a menu gives the focus back when it closes. A command that fails is logged. The **context menu of the editor** (`EditorContext`: Cut, Copy, Paste, a separator, Select All; Cut and Paste only while the editor is not read-only) opens on a right click, in a `kit.ContextMenuRegion` around the editor; the press of the secondary button gives the editor the focus and puts the cursor under the pointer unless a selection holds the place (VS Code's `contextmenu.ts`). Select All is not in VS Code's editor context menu (its simple editors have it); Emetos has it. Items for the commands VS Code puts in a context menu that Emetos does not have yet (Go to Definition, Format Document, Command Palette) arrive with those commands.

**Window title.** `window.title` (default `${dirty}${activeEditorShort}${separator}${rootName}${separator}${profileName}${separator}${appName}`) is expanded with VS Code's `template`: `activeEditorShort`, `activeEditorMedium`, `activeEditorLong`, `activeEditorLanguageId`, `activeFolderShort`, `activeFolderMedium`, `activeFolderLong`, `rootName`, `rootNameShort`, `rootPath`, `folderName`, `folderPath`, `dirty` (`● `), `appName` (Emetos), `profileName` (empty for the default profile), `focusedView`, `remoteName`, `activeEditorState` and `separator` (`window.titleSeparator`, ` - `, kept only between two values). The variables of a remote, a workspace file or a repository are empty. Paths in the home folder are written `~/...`. The title is set when the active editor, its dirty mark, the folder or the settings change; a title that comes out empty is `Emetos`.

The keyboard (the menu takes it with `Autofocus`): Up and Down move the focus over the items that can take it, wrapping, from no focus Down gives the first and Up the last; Home and PageUp go to the first, End and PageDown to the last (the Linux behavior of VS Code); Enter, the numpad's Enter and Space run the focused item or open its submenu with the first item focused; Right opens a submenu; Left and Escape close one and give its item the focus back; Escape in the first level calls `OnCancel`; with mnemonics on (`EnableMnemonics`; the mnemonic letter is underlined) the letter runs the item that has it (a submenu opens) or, if several share it, focuses the next of them each time; Tab does nothing. The pointer: moving over an item focuses it (only a pointer that moves does, not one that rests under a menu that has just appeared), a disabled item or a separator takes the highlight off, the pointer leaving the menu does too unless a submenu is open, a click runs the item (a click on a disabled item or a separator does nothing), the pointer resting on a submenu item opens its submenu after 250 ms and the submenu closes 750 ms after the pointer went to another item of its parent (a submenu opened by the pointer does not select an item). The submenus are `RawMenuAnchor`s inside the row of their item, one group for the whole tree (the menu makes a `RawMenuAnchorGroup` of its own when it is not inside a context menu or a menu bar), placed by `PlaceSubmenu` (right of the item, left without room, overlapping it by 10 px without room on either side; vertically level with the item, or ending at its bottom edge without room below). A menu that is higher than `MaxHeight` (the window less 35 px) scrolls (7 px scrollbar, the keyboard scrolls the focused item into view). `OnRun` gets the item (after its own `OnRun`), also from submenus; the code that shows the menu hides it there. A `MenuHandle` focuses the menu from outside and reports the focused path. Not ported: the alternative actions of Alt and Shift, touch gestures, the frosted glass and the opening animation of the modern UI. Ported tests: the mnemonic cases of `menubar.test.ts`, the stationary pointer cases of `menu.test.ts`, `layout.test.ts`; the others need VS Code's DOM or `ModifierKeyEmitter`.
- **`ContextMenu`** (`kit/contextmenu.go`): the host of a context menu, `NewContextMenu(child, opts)` with a `ContextMenuController` (`Show(position, items)`, `Hide`, `IsShowing`; the position is in window coordinates, calling `Show` with a menu open moves it), and `NewContextMenuRegion(child, items func() []MenuItem, opts)`, which opens it at the pointer on a click of the secondary button (the items are asked for at that moment; no items, no menu). The menu is in the root overlay, placed by `PlaceContextMenu`: the pointer is a 2 px block, the menu opens to its right and below it, flips above it without room below, flips left of it without room to the right, and is pushed against the window's edge when it fits on neither side (VS Code's `layout2d`; `Layout` is its `layout`). It takes the keyboard focus and gives it back when it closes; Escape, a click outside (which goes on to what is under it), the window changing size and an item running close it, `OnHide` is called, `OnRun` after the menu is hidden. By default no item is focused (`SelectFirst` focuses the first) and mnemonics are off (`EnableMnemonics`). A region also opens its menu for the menu key and Shift+F10 while a widget in its child has the focus, at that widget's bottom left corner (an editor that knows its cursor calls `Show` itself).
- **Drag and drop of tabs** (step 6.10; `kit/tabdrag.go`, `kit/bounds.go`; port of the drag and drop of `multiEditorTabsControl.ts`, see §10.3): `Tabs` takes `TabsOpts.OnDragStart`, `OnDragMove` and `OnDragEnd` (positions in window coordinates; a tab is dragged by the primary button after 4 px, Escape and a cancelled pointer end the drag with `dropped` false; the press activates the tab as before), `OnContextMenu` (a press of the secondary button), `Feedback` (a `TabDropFeedback`: the place of a 2 px line in `tab.dragAndDropBorder` before a tab, or after the last one, which the strip draws and updates without building the others again) and `Controller` (a `TabsController`: `Bounds`, `TabRect(i)` in window coordinates wherever the strip is scrolled to, `ScrollBy`, `Scrolled`, `Reveal(i)`; `RevealDelta` and `TabEdgeStep` are the pure rules). `Bounds` and `NewBoundsProbe(child, &bounds)` tell code outside a widget where it is in the window; `ScrollableElementOpts.Handle` (a `ScrollHandle`: `Position`, `ScrollTo`, `ScrollBy`) scrolls an element from outside. The window decides what a drop does (§10.3).
- **`MenuBar`** (`kit/menubar.go`; port of `menubar.ts`, `menubar.css` and `menubarControl.css`): titles of 13 px text, 22 px high with 8 px of padding and a radius of 5, in a bar 30 px high (the title bar's; `Height`), in `titleBar.activeForeground`; the title that is open, focused or under the pointer (while the bar is not focused) is in `menubar.selectionForeground` over `menubar.selectionBackground`, with a `menubar.selectionBorder` outline when the theme has one (solid, VS Code draws a dashed line for the pointer). A menu opens under its title (left edges aligned, pushed in where the window has no room). The state machine (`menuBarModel`) has VS Code's four states: hidden, visible, focused and open. The pointer: the press of the primary button on a title opens its menu and the release is ignored; a press on the title of the open menu closes it (on the release); with a menu open, entering another title opens that menu (no item selected); with the bar focused and no menu open, entering a title focuses it; a click outside the bar and its menus gives the focus up. The keyboard: a tap of Alt (pressed and released with no other key or pointer press and no other modifier between) focuses the first title and shows the mnemonics; a second tap, or Alt while the bar is focused, gives the focus up; Left and Right move between the titles (wrapping), Down and Enter open the focused menu with its first item focused, a mnemonic letter opens its menu, Escape gives the focus up; with a menu open, Left and Right (not in a submenu) switch to the previous or next menu, Escape closes the menu and leaves its title focused; Alt with a mnemonic letter opens that menu from anywhere (it needs no focus; the key still reaches the focused widget, Glutter does not let a key handler consume it). Alt held down underlines the mnemonics of the titles; they stay underlined while the bar is in use, and the menus have mnemonics only when they were opened by the keyboard or a mnemonic. When the bar gives the focus up, it goes back to the widget that had it. `MenuBarVisibility` (`window.menuBarVisibility`, registered in `core/settings`): `MenuBarClassic` shows the bar except in full screen (`FullScreen`), `MenuBarVisible` always, `MenuBarToggle` hides it until Alt focuses it and hides it again when it gives the focus up, `MenuBarHidden` never shows it for Alt (`compact` is not offered); a mnemonic with Alt opens its menu in the last two as in VS Code, showing the bar until the menu is left. A hidden bar is an `Offstage` (it takes no room, keeps its state). `DisableMnemonics` (`window.enableMenuBarMnemonics` off), `AlwaysOnMnemonics`, `DisableAltFocus` (`window.customMenuBarAltFocus` off; Alt still toggles the visibility toggle), `OnRun`, `OnVisibilityChange`, `OnFocusChange`, and a `MenuBarController` (`ToggleFocus`, `Blur`, `IsVisible`, `IsFocused`, `IsOpen`, `FocusedMenu`, `MnemonicsShown`) for the command that focuses the application menu. The settings that choose these options are wired by step 6.7. Not ported: the compact mode, the overflow menu of a bar that is too narrow, the macOS tab navigation, and the deferral of an update of the menus while the bar is in use.

### 10.3 Editor groups and tabs (`core/editorgroup`, `gui/workbench`)

A grid of groups (nested split views). Each group has its editors in order, a preview editor, pinned editors, an active editor and a most-recently-used order. Editors are text editors, diff editors, merge editors, the settings UI, the keybindings UI and, later, others; all implement one `EditorInput` interface (type id, resource, title, dirty, save, revert, serialize/deserialize for restore). `core/editorgroup` holds this as data; `gui/workbench` shows it.

**The model (step 6.8; `core/editorgroup`).** `Model` is a port of VS Code's `EditorGroupModel` (`editorGroupModel.ts`): the editors in tab order, at most one preview editor (a preview is replaced by the next preview; `Pin` keeps it, `Unpin` makes it a preview again), the **sticky** editors (VS Code's pinned tabs, with the pin icon, kept at the left; `Stick`/`Unstick`, the commands `pinEditor`/`unpinEditor`), the active editor, the most-recently-used order, and the events (open, close, move, active, pin, sticky, dirty, label, capabilities, will-dispose). `OpenEditor` follows `workbench.editor.openPositioning` (`left`, `right`, `first`, `last`; a sticky tab always keeps the first places) and `CloseEditor` follows `workbench.editor.focusRecentEditorAfterClose` (the most recently used editor, else the neighbour on the right, else the left). The terms: in the model and the code, "pin" means "keep" (not a preview) and "stick" means the pin icon; the commands and the settings use VS Code's words. `Serialize` and `RestoreModel` give and read the editors, the preview, the sticky count and the active editor as JSON, for step 10.x. `TabLabels` gives the labels of the tabs, and an editor whose name another one shares also shows its shortest differing folders (`Shorten`).

`EditorInput` is the interface of an editor's content: `TypeID`, `Resource`, `Name`, `Description`, `Title` (the tooltip), `Dirty`, `Matches`, `Capabilities` (`CapReadonly`, `CapUntitled`, `CapCanSplit`, `CapCannotClose`), `Serialize`, `Subscribe` (events `InputDirty`, `InputLabel`, `InputCapabilities`, `InputWillDispose`) and `Dispose`; `BaseInput` implements the events. Save and revert are added by step 7.1. `TextInput` (type id `emetos.textEditor`) shows a `*document.Document`: its name is the file's, its description the folder relative to the window's folder (or `~`), its title the full path, and it serializes as the file URI; it follows the dirty state of the document.

**Documents are counted.** An editor uses a document and several editors can show one (two groups, a diff). `Documents.Acquire` opens a file (or finds the open one) and counts one user, `Retain` counts another and `Release` takes one away; the release by the last user closes the document. `OpenFile` counts nobody (the users of step 3.x and the tests keep working, and a document nobody retained is never closed by a release).

**The tab strip (`kit.Tabs`).** Port of the `multiEditorTabsControl.ts` and `editorTabsControl.css` look: tabs 35 px high, 120 px at least, a 1 px `tab.border` at the right, the active tab in `tab.activeBackground` with `tab.activeBorderTop` (2 px, if the theme sets it) and `tab.activeBorder`, hover in `tab.hoverBackground`, the unfocused group in the `tab.unfocused*` colors; a preview tab has an italic label; a sticky tab has the pin icon in place of the file icon and sits left of `tab.lastPinnedBorder`; a modified tab shows the dot where the close button is (the pinned-and-modified icon on a sticky one), `tab.activeModifiedBorder` and the others when `workbench.editor.highlightModifiedTabs` is on. The close button shows on the active tab and under the pointer. A click activates, a double click on a preview tab keeps it (`OnPin`), a click on the pin icon unpins it, a middle click closes. The strip scrolls sideways (3 px scrollbar) and reveals the active tab. `TabsSingle` shows the active editor's title only (a simplified single-tab header: icon and label). The colors are registered in `core/theme` (`tab.*`, `editorGroupHeader.tabsBackground`, `editorGroupHeader.tabsBorder`, `editorGroupHeader.border`, `editorGroupHeader.noTabsBackground`) and carried by `kit.Colors`.

**Settings** (`core/settings/builtin.go`, VS Code's keys and defaults): `workbench.editor.showTabs` (`multiple`, `single`, `none`), `enablePreview` (true), `focusRecentEditorAfterClose` (true), `openPositioning` (`right`), `tabCloseButton` (`right`; `left`, `right`, `off`), `tabActionLocation` (`right`), `tabActionCloseVisibility` (true), `pinnedTabSizing` (`normal`; `compact`, `shrink`) and `highlightModifiedTabs` (false). VS Code's `tabActionUnpinVisibility` is not registered (the pin icon always unpins).

**The group in the app (`gui/app/group.go`, `editors.go`).** Step 6.8 shows one group: the tab strip, the breadcrumbs and the editor of the active tab. Each editor has a `textEditor`: a view model of its own over the shared document (so the cursors, the scroll position, the folds and the find state come back when its tab is activated again) and its own tokenizer, bracket pairs, indent levels and folding regions, stopped when the editor is closed. Files that the command line opens are kept (pinned) tabs; a file opened by the breadcrumbs picker or by navigation (`dev.openFile` included, with its arguments unchanged) is shown as a preview when `enablePreview` is on, an editor that is open already is activated, and an edit keeps a preview. The window title follows the active editor (`● name` while it is modified). With no editor the empty state (the logo and the name) is shown and `activeEditor` is cleared. `confirmClose` is a stub that returns true: step 7.2 puts the save prompt in it.

**Commands and keys** (VS Code's ids, titles and Linux keys): `workbench.action.closeActiveEditor` (Close Editor, Ctrl+W; also in the File menu), `closeEditorsInGroup` (Ctrl+K W), `closeUnmodifiedEditors` (Close Saved Editors in Group, Ctrl+K U), `closeOtherEditors`, `closeEditorsToTheRight`, `closeAllEditors` (Ctrl+K Ctrl+W), `keepEditor` (Ctrl+K Enter), `pinEditor` and `unpinEditor` (Ctrl+K Shift+Enter, by `activeEditorIsPinned`), `nextEditor` (Ctrl+PageDown), `previousEditor` (Ctrl+PageUp), `openNextRecentlyUsedEditorInGroup` (Ctrl+Tab) and `openPreviousRecentlyUsedEditorInGroup` (Ctrl+Shift+Tab). The commands that close many editors leave the sticky ones. The window's context keys are `activeEditor` (the type id of the active input), `activeEditorIsPinned` (sticky) and `activeEditorIsNotPreview`.

**The grid (step 6.9; `core/editorgroup`).** `Grid` is a port of the behavior of VS Code's `Grid`, `GridView` and `EditorPart`: a tree of splits (`Horizontal` puts the children side by side, `Vertical` stacks them; the children of a split have the other axis, and the root is always a split) whose leaves are `Group`s (an id that is never used again and a `Model`). The sizes are shares of the extent of the split (they add up to 1), not pixels; the view keeps the least sizes (a group is at least 220 px wide and 70 px high). A split never has one child: removing a group folds a split that is left with one child into its parent (a split of the other axis hoists its children), and a root left with one split becomes that split.
- **Adding** (`AddGroup(at, dir)`; `DirUp/Down/Left/Right`): next to a group along the axis of its split, or, across it, the group and the new one become the two halves of a new split. A single group makes the root run along the side. `workbench.editor.splitSizing` (`auto`, `distribute`, `split`; default `auto`) sizes it: `split` halves the group, `distribute` makes the whole split equal, `auto` does the second when the children of the split are equal already (within half a percent) and the first otherwise. **Removing** gives the room to the neighbor on the left or above (the one on the right for the first child), or distributes it by the same rule. `RemoveGroup` of a group with editors moves them first into the most recently active other group; the last group is never removed.
- **Closing empty groups** (`workbench.editor.closeEmptyGroups`, default true): a group whose last editor closes is removed (unless it is the only one), after the grid has told its listeners about the close; the active group then becomes the most recently active other group.
- **Active group and order**: `Activate`, `Active`, the most-recently-used order (`Groups(MostRecentlyActiveGroups)`), the order of the grid (`GridAppearance`: depth first, left to right, top to bottom, which "group 1..8" and `dev.openFile`'s `group` count in) and the creation order. Activating a group that is not the maximized one ends the maximized state.
- **Neighbors** (`FindByDirection(group, dir, wrap)`): the groups whose edge touches the edge of the group on that side (found by the geometry of the sizes), the most recently active first (a group that was never active sorts first, as VS Code's sort does); with `wrap` the edge of the grid leads to the opposite edge (a single group finds itself). `FindByLocation` gives the first, last, next or previous group of the grid order, with or without wrap. `FocusIndex(n, side)` is Ctrl+n: the n-th group, a new group on the preferred side of the last one for n = count + 1, nothing further away.
- **Editors between groups**: `MoveEditor` opens the very same input in the target (pinned, sticky when it was, active unless `Inactive`; at `Index` if given) and then closes it in the source with the context `CloseMove`, so an editor keeps its view model; a target that holds a matching editor keeps it. `CopyEditor` opens a copy (`Copier.CopyInput`, which `TextInput` has; an input without it stays in one group, as a singleton editor) and `SplitGroup` is `AddGroup` + copy of the active editor + `Activate`. `MergeGroup(group, target)` moves all the editors to the end of the target (those that are sticky in the target keep their place; only the active editor of the active group stays active) and removes the group; `MergeAllGroups` does it for all the others (`joinAllGroups`). `MoveOrCopyTarget(source, to, value, side)` is VS Code's `moveCopyEditorsToGroup`: `left`/`right`/`up`/`down` find the neighbor or add a group there, `first`/`last`/`previous`/`next` go by the grid order (`next` of the last group adds a group on the preferred side, `previous` of the first on the opposite one), `center` and `position`. `CopyGroup` clones a group (`Model.Clone`: the same order, preview, sticky, active and most-recently-used order, with copies of the inputs). `MoveGroup` moves a group next to another one (within its own split it reorders and keeps the sizes).
- **Sizes**: `DistributeSizes` makes every split equal (`evenEditorWidths`); `SetSizes(path, sizes)` records a sash drag without counting as a change; `Version` counts the changes the grid made to the tree and the sizes, which tell the view to start over from them. `Maximize`/`ExitMaximized`/`ToggleMaximize`: the other groups are hidden (VS Code hides them too; the sizes are kept and they come back as they were); adding, removing, moving, evening out, applying a layout and activating another group end it.
- **Layout and state** (for step 7.5): `Layout` and `ApplyLayout` are VS Code's `EditorGroupLayout` (`{orientation, groups: [{size, groups}]}`; the nodes without a size share what the sized ones leave; a split of one node is that node; with fewer places than groups the editors of the extra groups are merged into the last place, with more empty groups are added; the groups keep their places in the grid order). `Serialize` and `RestoreGrid` give and read the whole grid as JSON: the tree with sizes and the serialized model of each group, the active group, the most-recently-used order, the maximized group and the next id; a state that is not a tree of groups fails with the tag `GridStateInvalid`. The other failures have the tags `GroupUnknown` (a group that is not in the grid), `GroupMoveOntoItself`, `GroupMergeOntoItself`, `GroupTargetInvalid` and `LayoutInvalid`.

**The grid in the app (`gui/app/group.go`, `gridview.go`, `groupcommands.go`).** The editor area is the grid: a `kit.SplitView` for each split (proportional, `editorGroup.border` between the panes, the sizes of the grid as the first sizes, the shell asks for a new split view with a new key whenever `Version` changes) and for each group a tab strip, the breadcrumbs and the editor of its active tab, or, for an empty group, the logo and the name (a click gives it the focus; `editorGroup.emptyBackground` and, while it is active, `editorGroup.focusedEmptyBorder`). A group keeps its widgets (and so their state) when it moves in the tree, through a global key; an editor keeps its own when it moves to another group. The strip of a group that is not the active group has the `tab.unfocused*` colors. Every editor in every group has a view model of its own over the document, which several groups share through `Documents.Acquire/Retain/Release` (an editor counts one use; the document stays open while any group shows it, and a closed group releases its editors' uses). **The view models of one document have owners of their own**: a view model reserves 8 consecutive owners (`Document.AllocOwners`) and uses them as slots (auto-closed pairs 1, folding 2, find 3, word highlight 4, selection highlight 5, snippets 6, which `ViewModel.owner(slot)` turns into the document's owner; `snippet.Editor.Owner` names the one of the snippets), so each editor sees and replaces only its own marks, and the first view model of a document has the owners 1 to 6 as before. A pointer pressed in a group, a tab chosen, or the focus moving into an editor or its find widget makes its group the active group; every change of the active group, and an editor that had the focus closing, gives the keyboard focus to the active group (its editor, or its empty area), tried again over a few frames until the widgets are there, and the focus is not followed while that waits. Opening a file (`dev.openFile`, the breadcrumbs) goes to the active group unless a group is given, and makes that group the active one. `workbench.editor.openSideBySideDirection` (`right`, `down`; default `right`) is the side `workbench.action.splitEditor` splits to (`splitEditorOrthogonal` the other one).

**Commands and keys of the grid** (VS Code's ids, titles and Linux keys; registered in `core/command/builtin.go` and `core/keybinding/defaults.go`): `workbench.action.splitEditor` (Ctrl+\), `splitEditorOrthogonal` (Ctrl+K Ctrl+\; VS Code's source gives this chord to the four directional splits too, which cannot all have it), `splitEditorLeft/Right/Up/Down`, `focusFirstEditorGroup` (Ctrl+1) to `focusEighthEditorGroup` (Ctrl+8; the second to eighth have no title, as in VS Code), `focusLastEditorGroup`, `focusNextGroup`, `focusPreviousGroup`, `navigateEditorGroups`, `focusLeftGroup/RightGroup/AboveGroup/BelowGroup` (Ctrl+K Ctrl+arrows; they wrap) and the four `...WithoutWrap` ones, `moveEditorToPreviousGroup` (Ctrl+Alt+Left), `moveEditorToNextGroup` (Ctrl+Alt+Right), `moveEditorToAboveGroup/BelowGroup/LeftGroup/RightGroup`, `moveEditorToFirstGroup` (Shift+Alt+1), `moveEditorToLastGroup` (Shift+Alt+9), the same eight as `splitEditorTo...Group` (copies), `moveActiveEditor` and `copyActiveEditor` (the argument `{"to", "by": "tab"|"group", "value"}`; by tab only moves), `newGroupLeft/Right/Above/Below`, `moveActiveEditorGroupLeft/Right/Up/Down` (Ctrl+K arrows; the target may also be across the direction, as in VS Code), `duplicateActiveEditorGroupLeft/Right/Up/Down`, `joinTwoGroups` (the neighbor on the right, else below, left, above), `joinAllGroups`, `closeGroup` (Ctrl+W while the active group is empty and there are several, a rule of its own that wins over Close Editor), `closeEditorsAndGroup`, `closeAllGroups` (Ctrl+K Ctrl+Shift+W; closes the sticky editors too and removes the empty groups whatever `closeEmptyGroups` says), `closeEditorsInOtherGroups`, `closeEditorInAllGroups`, `evenEditorWidths` (Reset Editor Group Sizes), `toggleMaximizeEditorGroup` (Ctrl+K Ctrl+M, enabled with several groups or while one is maximized) and the layouts `editorLayoutSingle`, `TwoColumns`, `ThreeColumns`, `TwoRows`, `ThreeRows`, `TwoByTwoGrid`, `TwoColumnsBottom`, `TwoRowsRight` and `layoutEditorGroups` (the argument is a `Layout`). `closeEditorsInGroup` now closes the group when it empties, and `closeAllEditors` (Ctrl+K Ctrl+W) closes the editors of every group. The context keys are `multipleEditorGroups`, `editorPartMultipleEditorGroups`, `editorPartMaximizedEditorGroup` and `activeEditorGroupEmpty`, besides those of step 6.8. The menus are View > Editor Layout (Split Up, Down, Left, Right and the layouts, VS Code's groups and order) and Go > Switch Group (Group 1 to 5, Next and Previous Group, Group Left, Right, Above, Below; the rows from Group 3 on and the rest are enabled when there are several groups). Not done: the commands that expand a group (`minimizeOtherEditors`, `minimizeOtherEditorsHideSidebar`, `toggleEditorWidths`; they need the least size of a group in pixels in the model), `maximizeEditorHideSidebar`, locking groups, side-by-side editors and moving to a new window. Settings: `workbench.editor.openSideBySideDirection`, `workbench.editor.closeEmptyGroups` and `workbench.editor.splitSizing`. Colors: `editorGroup.border` (`#444444`, `#E7E7E7`), `editorGroup.emptyBackground` and `editorGroup.focusedEmptyBorder`.

**Tab interactions (step 6.10; `gui/app/tabdrag.go`, `gui/app/tabmenu.go`, `core/editorgroup/droptarget.go`).** A tab is dragged (primary button, 4 px, a label with the name of the editor follows the pointer, 12 px below and to the right of it, kept inside the window) over the tab strips and the editor areas of all the groups. The places are found from where the widgets are on the screen (`kit.TabsController` for a strip and its tabs, a `kit.Bounds` for the group). The rules are pure and tested without a window (`core/editorgroup`): `TabDropIndex(spans, x)` is the place in a strip (before the tab the pointer is over when it is in the left half or on the middle, after it in the right half, at the end past the last tab; the line shows it, and the tab dragged over a strip scrolls into view when the pointer comes to it); `ZoneAt(x, y, w, h, opts)` is the zone of an editor area (the area below the tab strip, or all of an empty group): the middle (all but a ring of a tenth of the width and the height) is `DropCenter`, and in the ring the area is in thirds along the preferred axis (`PreferVertical`: `openSideBySideDirection` is `right`: left third, right third, then up and down in halves of the middle third; otherwise up, down, and left and right in halves) giving `DropLeft/Right/Up/Down`, which split; without `workbench.editor.splitOnDragAndDrop` (default true, which Alt turns around for one drag) the whole area is the center; `ZoneRect` is the half of the area that a split zone highlights (the whole area for the center) in `editorGroup.dropBackground`; `DropAllowed` refuses moving the only editor of a group onto its own group. The drop is `Grid.DropOnTabs(from, editor, onto, index, copied)` (within a group the place counts the tab itself; a place in the pinned region pins the tab; the group becomes active) and `Grid.DropOnZone(from, editor, onto, zone, copied)` (the center moves the editor into the group; a side adds a group next to it and moves the editor into that; when the editor is the last of its group, `closeEmptyGroups` is on and it moves, the group itself moves next to the target, with its editor). Ctrl held at the drop copies instead of moves (VS Code's Ctrl on Linux). Escape cancels; a drag that ends over nothing drops nothing. While the pointer rests within 35 px of an end of a strip the strip scrolls (`TabEdgeStep`: up to 14 px each frame). Not here (VS Code has them): dragging groups, dragging several selected tabs, dropping files from the file manager, the drop-into-editor prompt, dragging a tab out of the window, opening the tab that a drag rests on for 1.5 s, and `workbench.editor.dragToOpenWindow`.
**The context menu of a tab.** A right click on a tab opens the `EditorTitleContext` menu (rows as data in `core/command/menus_default.go`, VS Code's groups and order): Close, Close Others (dimmed when the group has one editor), Close to the Right (dimmed for the last tab; only while the tabs show), Close Saved and Close All (`1_close`); Copy Path and Copy Relative Path (`1_cutcopypaste`, for files); Keep Open (dimmed unless the tab is a preview; only with `workbench.editor.enablePreview`) and Pin or Unpin (`3_preview`); Split Right (Split Down while `openSideBySideDirection` is `down`) and the Split & Move submenu (Split Up/Down/Left/Right, Move Above/Below/Left/Right; `5_split`). Reveal in Explorer View (`revealInExplorer`, group `2_files`, when `isFileSystemResource`) is there since step 6.14 (§10.8). Not yet: Save and Save As (step 7.1), Reveal in File Manager (step 7.x), Reopen Editor With, Share, the moves into a new window. The when-clauses and preconditions read the keys of the tab that was clicked, set for the menu as VS Code sets them (`activeEditorIsNotPreview`, `activeEditorIsPinned`, `activeEditorIsDirty`, `activeEditorIsFirstInGroup`, `activeEditorIsLastInGroup`, `groupEditorsCount`, `editorTabsVisible`, `isFileSystemResource`, and `splitEditorsVertically`, which is also a key of the window: the direction is `down`). **Every row runs its command with the context `{"groupId": n, "editorIndex": n}`** (VS Code's `resolveCommandsContext`): the commands that act on an editor (`closeActiveEditor`, `closeEditorsInGroup`, `closeUnmodifiedEditors`, `closeOtherEditors`, `closeEditorsToTheRight`, `keepEditor`, `pinEditor`, `unpinEditor`, `splitEditor` and `splitEditorLeft/Right/Up/Down` through `Grid.SplitEditor`, `moveEditorTo...Group` and `splitEditorTo...Group`, `copyFilePath`, `copyRelativeFilePath`) act on that editor and its group, and on the active editor of the active group without it; a context whose group or tab is gone does nothing. `closeEditorsToTheRight` keeps the active editor (it is pinned, as before) and closes what is on the right of the tab that was clicked. **Copy path:** `copyFilePath` (Ctrl+Alt+C outside the editor, Ctrl+K Ctrl+Alt+C in it), `copyRelativeFilePath` (Ctrl+Shift+Alt+C, Ctrl+K Ctrl+Shift+Alt+C) and `workbench.action.files.copyPathOfActiveFile` (Ctrl+K P) put the path of the file on the system clipboard (through the clipboard of the editor widget); the relative path is relative to the folder of the window and is the full path for a file outside it or without a folder; the settings `explorer.copyPathSeparator` and `explorer.copyRelativePathSeparator` are not registered. Menu rows run through `workbench.MenuSource`, like the other menus. The menu closes, and the keyboard focus goes back to the active group. **Colors:** `tab.dragAndDropBorder` (the active tab's foreground; `contrastActiveBorder` in the high contrast themes) and `editorGroup.dropBackground` (`#53595D` at 50 %, `#2677CB` at 18 %, none in high contrast dark, `#0F4A85` at 50 %). **Setting:** `workbench.editor.splitOnDragAndDrop`. **Focus:** an editor that was replaced by another in its group (the active tab changed, a file opened over it) gives the keyboard focus to the new active editor of the group, as a closed editor does, instead of letting the focus fall to an editor of another group, which made that group active. ### 10.4 Activity bar and side bar views

Activity bar entries for Explorer (and, later, Search, Source Control, Run and Debug, Extensions), plus the Manage menu (settings, keybindings, themes, profiles). Views are registered with an id, title, icon and container, so later areas add their own.

**Built in `core/command` and `gui/workbench` (step 6.7).**

- **View registry** (`command.ViewRegistry`, VS Code's `ViewContainersRegistry` and `ViewsRegistry` of `workbench/common/views.ts`). A **view container** has an id, a title, the code point of its Codicon, an order and a location (`sidebar`, the default, or `panel`). A **view** has an id, a name, a container, a `when`, an order and whether it starts `Collapsed`. `Containers(location)` lists the containers in the order of the activity bar (equal orders keep the registration order), `Views(container, ctx)` the views whose `when` holds, in order. Registering fails with `ViewContainerInvalid`, `ViewContainerDuplicate`, `ViewInvalid`, `ViewContainerUnknown` or `ViewDuplicate`. `DefaultViews` has the panel containers of step 6.12 (§10.13) and the Explorer (`workbench.view.explorer`, "Explorer", the `files` Codicon, order 0) with the views `workbench.explorer.openEditorsView` ("Open Editors", order 0, `HideByDefault`), `workbench.explorer.emptyView` ("No Folder Opened", when `workbenchState == 'empty'`) and `workbench.explorer.fileView` ("Folders", when `workbenchState != 'empty'`) (§10.8); the steps that build the views of a container register their containers and views there. A view is a header over an empty body until its step. A `View` has `HideByDefault`, and `workbench.Views` keeps which views are hidden (`IsHidden`, `SetHidden`, which also unfolds a view that is shown); the side bar skips a hidden view. The side bar takes slots from the window (`workbench.Options.ViewName`, `ViewActions`, `ViewBodyHeight`, `OnViewFocus`): a view can be titled other than its registry name (the folder view has the name of the folder), have buttons at the right end of its header that show while the pointer is over the view or the focus is in it, have a body of a fixed height instead of a share of what is left, and tell where the focus is.
- **State** (`workbench.Views`, one per window): the container the side bar shows (the first of the activity bar to begin with) and which views the user collapsed or expanded (a view starts as its descriptor says). `Open(id)` shows a container and the side bar; `Toggle(id)` is a click on its icon: the container that is open hides the side bar, any other opens.
- **Activity bar** (`workbench.ActivityIcons`, `workbench.ManageButton`, filled by the workbench when `Options.Views` is set): a column of icons, 48 px squares with 24 px Codicons, in `activityBar.inactiveForeground`, in `activityBar.foreground` under the pointer or when active, the active one with a line of 2 px beside it in `activityBar.activeBorder` (none is active while the side bar is hidden); a `kit.Hover` with the title of the container shows to the right of an icon; Enter and Space on a focused icon run it. At the bottom is the **Manage** gear: it opens the Manage menu (`GlobalActivity`) to the right of the activity bar, its bottom on the bottom of the gear; a second click closes it. Until a step adds items to `GlobalActivity` (Command Palette, Profiles, Settings, Keyboard Shortcuts, Themes), the menu has one dimmed item, `(empty)`.
- **Side bar** (`workbench.SideBarViews`): the title of the active container (uppercase, 11 px, 35 px high) over its views. A view header is 22 px high with a chevron and the name in bold capitals (11 px) on `sideBarSectionHeader.background`, a line above it in `sideBarSectionHeader.border` unless it is the first; a click, Enter or Space toggles the view, Right opens and Left folds it. The bodies of the views that are open share the height that is left; a view that is folded takes its header only. A body is built by `Options.ViewBody`; a view it gives nothing for has an empty body.
- Colors registered with this step: `activityBar.foreground`, `activityBar.inactiveForeground`, `activityBar.activeBorder`, `activityBar.activeFocusBorder`, `activityBar.activeBackground`, `sideBarSectionHeader.background`, `sideBarSectionHeader.foreground`, `sideBarSectionHeader.border`.

Not built: badges on the icons (`activityBarBadge.*`), the position of the activity bar (top, bottom), drag and drop of icons and views, the context menus of the activity bar and of the view headers, and the Account entry of VS Code's global activity.

### 10.5 Explorer (`core/workspace`, `gui/views/explorer`)

- `core/glob` has VS Code's glob patterns (`Parse`, `ParseRelative`, `ParseExpression` for `files.exclude`-style objects with `when` sibling clauses, `BasenameTerms` and `PathTerms` for searches) and a gitignore matcher (`Ignore`: nested `.gitignore` and `.ignore` files, negation, folder-only and anchored patterns, `**`, character classes, and the rule that a path below an excluded folder stays excluded; checked against `git check-ignore` by a test that needs git). Patterns run on Go's `regexp`. Sibling checks are synchronous (VS Code also accepts promises).
- The tree model reads folders lazily, sorts like VS Code (`explorer.sortOrder`), hides `files.exclude` matches (`core/glob`, VS Code's glob syntax), and watches with inotify (`golang.org/x/sys/unix`): the opened folder (recursively, as folders are read) and the parent folder of every open file outside it; events are coalesced every 50 ms; watching a directory (not inodes) sees files replaced by rename. Events for a file whose `FileStat` matches Emetos's own last write are ignored. Watching falls back to polling a folder when the inotify limit is reached, with a notice.

**As built (step 6.13, `core/workspace`).** Ports: `explorerModel.ts` (the tree), the `FileSorter`, `FilesFilter` and `ExplorerCompressionDelegate` of `explorerViewer.ts`, `comparers.ts`, and `platform/files/common/watcher.ts` (`EventCoalescer`). The package imports no Glutter. The files are `compare.go`, `config.go`, `workspace.go`, `sort.go`, `apply.go`, `events.go` (the coalescer), `watcher.go`, `inotify_linux.go` (and `inotify_other.go`, a stub that makes other systems poll).

*Model.* `workspace.Open(ctx, path)` opens one folder (Emetos has no multi-root workspaces): the path is made absolute and clean and must be a folder (`WorkspacePathInvalid`, `WorkspaceFolderNotFound`, `WorkspaceStatFailed`, `WorkspaceNotDirectory`, `WorkspaceOpenCancelled`). A `Workspace` is a tree of `Item`s (name, path, `IsDir`, `IsSymlink` with `IsDir` telling what a link points at, `IsUnknown` for sockets and devices, size, modification time, `Resolved`, `Err`); it is safe for concurrent use. Nothing is read at open: `Item.Children(ctx)` reads a folder the first time (`os.ReadDir` through the injectable `FS`; a link is a folder when its target is), drops what `files.exclude` hides, and returns the children sorted. A folder that cannot be read keeps the error on the item (`Err`) and stays unread, so the next `Children` tries again, and fails with `WorkspaceReadDirFailed` or `WorkspaceReadCancelled`; the rest of the tree is not affected. Links are shown but never followed by the model itself (a link to a parent loop is a folder that can be expanded again and again, only by the user). `Refresh(ctx, item)` reads again a folder and every folder below it that was read, keeping the `Item`s that are still there (and so what was read below them); a folder that is gone leaves the tree; `Excluded`, `Find` and `Loaded` complete it. `explorer.sortOrder` has VS Code's six values: `default` (folders first, names), `mixed`, `filesFirst`, `type` (folders first, files by extension then name), `modified` (folders first, newest first, names breaking ties) and `foldersNestsFiles` (file nesting is not built, so it sorts as `default`); `explorer.sortOrderLexicographicOptions` (`default`, `upper`, `lower`, `unicode`) and `explorer.sortOrderReverse` are read as `FileSorter` reads them. Names compare as `comparers.ts` does, with the root collation of `golang.org/x/text/collate` where VS Code uses `Intl.Collator` of the user's locale: numbers compare as numbers (`file2` before `file10`), punctuation first, `a` before `A`, and names equal as numbers (`foo1`, `foo01`) are told apart by length. `files.exclude` is parsed with `glob.ParseExpression` and matched against the path relative to the folder, with the siblings of the entry for the clauses with a `when`. **Compact folders** (`explorer.compactFolders`, default true): `Workspace.CompactChain(ctx, item)` gives the folders the Explorer shows as one element, `a/b/c`: the item and then its only child while that is a folder, reading the folders it needs. As in VS Code's `ExplorerCompressionDelegate`, the root and the folders directly below it never take part in a chain; Emetos also never goes through a link. `SetConfig` changes the settings of the tree (the order follows at once, `Refresh` applies `files.exclude`), `ConfigFromSettings` reads them.

*Events and changes.* The watcher reports `Event`s (`EventCreated`, `EventChanged`, `EventDeleted`, `EventRenamed` with `OldPath`, and `EventRescan` for a folder whose events were lost). `Workspace.Apply(ctx, events)` applies them to what the tree has read and tells the listeners of `OnChange` (called on the goroutine that applied them, with no lock held) a `Change` each: `ChangeAdded`, `ChangeRemoved`, `ChangeUpdated`, `ChangeRenamed` or `ChangeRefreshed`. An event for a folder whose children were not read is ignored (reading it later finds the new state), so is one for a path outside the folder or one `files.exclude` hides. A created or changed path the tree does not have is added, one it has is updated (a file replaced by rename arrives as a change). A renamed or moved item keeps what was read below it and its paths follow; a move out of the read part of the tree is a removal; a rename over an item replaces it. The deletion of the folder itself is reported (`ChangeRemoved` of the root) and the tree is left as it was. The explorer view (§10.8) listens to these changes and shows them on the UI thread (`Post`).

*Watcher.* `workspace.NewWatcher(ctx, WatcherOptions)` starts a watcher that stops with `ctx` (`Done()` closes when its goroutines are gone). `Watch(ctx, Target)` adds a target and returns the function that removes it: a folder (`Recursive`: every folder below it is watched, also those that appear later, `IN_DONT_FOLLOW` so links are not followed) or a file (`File`: its folder is watched, not recursively, and only events of that path are reported; the app uses it for the open files outside the folder). `Exclude` takes the keys of `files.watcherExclude` (matched with `TrimForExclusions`, so `.git/objects/**` also covers the folder `.git/objects`; relative to the target, or absolute): excluded folders get no watch and their events are dropped. `Watch` reads the tree to place the watches, so it runs on a goroutine (`WatcherPathInvalid`, `WatcherPathNotFound`, `WatcherStatFailed`, `WatcherStopped`, `WatcherAddFailed` for the target itself; a subfolder that cannot be watched is left out and logged). inotify is used through `os.NewFile` over a non-blocking descriptor, so closing it ends the read; the mask is create, delete, modify, close-write, attrib, moved from/to, delete self and move self. A queue overflow sends `EventRescan` for every target. *Coalescing* (`coalescer`, port of `EventCoalescer` plus renames): events are gathered for `DefaultDebounce` (50 ms, from the first event of a batch; the clock is injectable) and then reported in one batch, in the order deletes (shortest path first), renames, creates and changes, rescans. Rules: created then deleted cancels both; deleted then created is changed; created then changed stays created; otherwise the last kind wins; a delete below a deleted folder is dropped. A move from and a move to with the same cookie are one `EventRenamed`; an unpaired move from is a delete and an unpaired move to a create; a rename of a path created in the same batch (the temporary file of an atomic save), or onto a watched path from one that is not watched, is a `EventChanged` of the new path (inotify does not say whether the target existed, so a first save of a new file also arrives as a change: consumers treat a change of an unknown path as a creation, as `Apply` does). Folders moved inside the tree keep their watches under the new path; folders moved out lose them. **Own writes:** `Suppress(path, FileStat)` records the `FileStat` that a write or read of the editor returned (`fileio.Write` does); a created, changed or renamed event for that path whose file still has the same size and modification time is dropped, another stat or a delete forgets the entry (256 entries are kept). Step 7.1 calls it when it saves. **Polling:** a target is polled (a snapshot of the paths, sizes and times every `DefaultPollInterval`, 2 s, compared with the last one; it produces created, changed and deleted, no renames, and skips excluded folders; at most 500,000 entries) when `ForcePolling` is set, when inotify cannot be initialised (`WatcherInitFailed`, a `NoticePollingFallback` notice), or when its watches run out (`ENOSPC`: that target alone is polled, its inotify watches are dropped, an `EventRescan` is sent and a `NoticeWatchLimit` notice). Each kind of notice is sent once per watcher. The app shows a notice as one warning notification.

*Settings* (VS Code's keys, defaults and scopes): `files.exclude` (`**/.git`, `**/.svn`, `**/.hg`, `**/.jj`, `**/.DS_Store`, `**/Thumbs.db`), `files.watcherExclude` (the six `.git/objects`, `.git/subtree-cache` and `.hg/store` patterns), `files.watcherInclude` (`[]`), `explorer.sortOrder`, `explorer.sortOrderLexicographicOptions`, `explorer.sortOrderReverse` and `explorer.compactFolders`. Not registered: `explorer.excludeGitIgnore`, `explorer.fileNesting.*`, and `files.legacyWatcher`.

*In the app* (`gui/app/workspace.go`). `NewWindow` opens the folder as `Window.Workspace` (`Window.Folder` is its path; a folder that is not there fails the window, route `NewWindow->Window.openWorkspace->Open.WorkspaceFolderNotFound`). `cmd/emetos [folder] [files...]` already passed the first directory argument as the folder. The window uses the workspace for the breadcrumbs (`BreadcrumbsOpts.Root`: the folder first, then the path inside it), the title (`${rootName}`, `${folderName}`, `${folderPath}`), `Window.SnippetWorkspace()` (`WORKSPACE_NAME`, `WORKSPACE_FOLDER`, and `RELATIVE_FILEPATH` relative to the folder), and the Problems panel. `Window.StartWatching(ctx)` starts the watcher (the shell calls it when it is created, with its lifetime; it does nothing unless the process was made with `ProcessOptions.WatchFiles`, which the editor sets and tests leave off, since the widget tester never disposes a window): targets are the folder (recursive, with `files.watcherExclude`, plus the entries of `files.watcherInclude`: relative paths joined to the folder, absolute ones only inside it), the user's configuration folder (recursive; it is made if it is missing), and every open file outside the folder (`Documents` tells the window when a file is opened or closed). On a batch of events the window reads `settings.json` (user and `<folder>/.emetos/settings.json`) again with `Store.Reload`, the snippets with `snippet.Service.Reload` when something in the snippets folder changed, and applies the events to the tree. A change of `explorer.*` or `files.exclude` makes the workspace take the new configuration and refresh; a change of `files.watcherExclude` or `files.watcherInclude` restarts the watch of the folder. Keybindings are not reloaded (there is no user keymap yet).

Not built: multi-root workspaces, file nesting, `explorer.excludeGitIgnore`, the file operations (step 6.15), renames reported by the polling fallback, and the use of `files.exclude` in the Problems panel and the breadcrumbs picker.
- File operations (new, rename, move, copy, delete to trash, paste) are undoable from the explorer (Ctrl+Z when the explorer has focus; undoing a delete restores from the trash), and open editors follow renames and moves. Cut/copy/paste uses an internal clipboard and also puts the files' URIs on the system clipboard (`text/uri-list`), so a file manager can paste them.

### 10.6 Quick input (`core/fuzzy`, `gui/quickinput`)

One quick input widget with modes by prefix, as in VS Code: no prefix (files), `>` (commands), `:` (go to line, revealing the line while typing), `?` (help), `@` (symbols, area 3), `#` (workspace symbols, area 3), `view ` (views). It reports the active item while the user moves through the list (used for theme preview), and restores focus to the previous widget when it closes. File search lists the folder's files in the background, respecting `files.exclude`, `search.exclude` and, with `search.useIgnoreFiles` (default true), `.gitignore` and `.ignore` files; it scores with VS Code's fuzzy scorer and shows recently opened files first. The command palette lists commands with their keybindings and recently used commands first. Recent items are kept in memory until UI state persistence exists (§10.10).

### 10.7 Notifications and dialogs

Notifications (`core/notify`) have a severity, message, actions, an optional progress, and a source. Any part of Emetos can post one from the start (before the UI shows them, they go to the log). Toasts show at the bottom right, at most 3 at once; the notification center keeps them; do-not-disturb hides non-error toasts. Modal dialogs (unsaved changes, overwrite, delete) are in-window (`kit.Dialog`), keyboard operable.

**Notifications as built (step 6.11).** The model (`core/notify`, port of `NotificationsModel` and `NotificationViewItem`): a `Notification` has a `Severity` (`Info`, `Warning`, `Error`), a `Message`, an optional `Source`, `Actions` (the buttons: `Label`, `Command` and `Args`, a `Run` callback and `KeepOpen`; the first is the primary button, the others are secondary buttons), `Sticky`, `Silent` and an optional `Progress` (`Infinite`, or `Total` and `Worked`, and `Done`; a progress is running while it is not done and is infinite or has a total or some work done). `Service.Notify` returns the id (0 without a message) and logs the notification as before; a notification equal to one in the list (same severity, message, source and button labels, neither with a progress) replaces it. `Service` also has `Get`, `Items` (oldest first), `Dismiss`, `ClearAll` (newest first), `UpdateProgress`, `SetExpanded` and `SetDoNotDisturb`/`DoNotDisturb`, and tells its listeners with `Added`, `Dismissed`, `Updated` and `DoNotDisturbChanged` events (from any goroutine). An item with buttons starts expanded and cannot be collapsed; an item is sticky when `Sticky` is set, when it is an error with buttons, when it was expanded (and has no buttons) or when its progress is running (`Item.IsSticky`). Do not disturb (`notifications.toggleDoNotDisturbMode`; VS Code's `NotificationsFilter.ERROR`) makes the notifications that are not errors silent when they are sent, and hides the toasts that show when it is turned on; it is not a setting and does not survive the process.

`notify.Presenter` (one per window, `Window.Notifications`; port of the state of `NotificationsToasts` and `NotificationsCenter`) lives on the UI thread and decides what shows. `Bind(post, after)` makes it follow the service (the events are handed to the UI thread with `post`, the timers are `after`, the timer of the UI thread) and makes toasts of the notifications that are in the service already. A toast is made for an added notification unless the center is open, the item is silent, or more than `SpamLimit` (3) toasts were made within `SpamInterval` (800 ms) of the first. `Toasts()` lists the toasts that show, newest first, at most `MaxToasts` (3): the newest three; an older one comes back when a newer one goes away. A toast goes away after `PurgeTimeout` (10 s for an information, 12 s for a warning, 15 s for an error; VS Code's values), unless its item is sticky, the pointer is over it or the focus is in it, in which case the time starts again; the notification stays in the center. Opening the center (`ShowCenter`) takes the toasts away, and no toast shows while it is open; `ClearAll` closes the center and dismisses everything.

The widgets (`gui/workbench/notifications*.go`). `NotificationsHost` is placed once at the root of the workbench, over the workbench and below the dialogs (`workbench.Options.Notifications`), and reads the presenter. Toasts stack at the bottom right above the status bar (3 px from the window and 3 px above the status bar, with 4 px of margin around each toast, so the box is 7 px from both), 450 px wide at most (the window minus 16 px), the newest on top, each on `notifications.background` with `notifications.foreground`, a 1 px `notificationToast.border` border (none when transparent), a radius of 4 and a shadow. A row (`notificationRow`, the same in the toasts and in the center) is padded 10 px by 5 px: the severity icon (a Codicon `info`, `warning` or `error` at 18 px, in `notificationsInfoIcon.foreground`, `notificationsWarningIcon.foreground` or `notificationsErrorIcon.foreground`), the message on 22 px lines (13 px; one line with an ellipsis, or all of it when the item is expanded), and a toolbar that shows while the pointer is over the row, the focus is in it or the item is expanded: the expand (chevron up) or collapse (chevron down) button, shown when the item can collapse and is expanded, has a source, or its message does not fit on one line, and the close button ("Clear Notification"; none while a progress runs). An expanded item with a source or buttons has a details row (34 px, 8 px below the message): "Source: <source>" (12 px) and the buttons at the right (`kit.Button`, the first primary and the others secondary); a button runs its `Run`, then its `Command` (an error is reported as an error notification "Cannot run <command>: ..."), and then closes the notification unless `KeepOpen`. The progress shows as a `kit.ProgressBar` along the bottom of the row. The notification center is the same place (7 px from the window and from the status bar), 450 px wide at most, with a 1 px `notificationCenter.border` border, a radius of 4 and a shadow: a header of 35 px (`notificationCenterHeader.background`, `notificationCenterHeader.foreground` or the workbench's text) with the title "NOTIFICATIONS" (11 px, "NO NEW NOTIFICATIONS" when there is none), and the buttons Clear All Notifications (disabled with nothing to clear: items with a running progress are not cleared by it), Enable or Disable Do Not Disturb Mode (a toggle, `bell-slash`) and Hide Notification Center (chevron down), over the list of all the notifications, newest first, separated by 1 px lines in `notifications.border`, at most 400 px high (and no more than the window leaves) and scrolling with a `kit.ScrollableElement`. Opening the center gives it the focus (and closing it gives the focus back to what had it); the pointer and the focus pause the toasts. There is no animation: toasts appear and go away at once (VS Code slides and fades them in 300 ms).

Colors registered (VS Code's defaults): `notificationCenter.border`, `notificationToast.border` (`widget.border`; `contrastBorder` in high contrast), `notifications.foreground` (`editorWidget.foreground`), `notifications.background` (`editorWidget.background`), `notificationLink.foreground` (`textLink.foreground`, which is registered too: #3794FF, #006AB1, #21A6FF, #0F4A85; links in messages are not built), `notificationCenterHeader.foreground` (none), `notificationCenterHeader.background` (`notifications.background` lightened by 0.3 in dark themes and darkened by 0.05 in light ones), `notifications.border` (the header background), `notificationsErrorIcon.foreground`, `notificationsWarningIcon.foreground` and `notificationsInfoIcon.foreground` (`editorError.foreground`, `editorWarning.foreground`, `editorInfo.foreground`).

Commands (`core/command/builtin.go`; the host binds the handlers while it is on screen): `notifications.showList` (Show Notifications, Ctrl+K Ctrl+Shift+N), `notifications.hideList` (Hide Notifications, Escape when `notificationCenterVisible`, weight `WorkbenchContrib+50`), `notifications.toggleList`, `notifications.hideToasts` (Escape when `notificationToastsVisible`, weight `WorkbenchContrib-50`, and `WorkbenchContrib+100` when `notificationFocus` too), `notifications.focusToasts` (Focus Notification Toast: the newest toast takes the focus), `notifications.clearAll` (Clear All Notifications) and `notifications.toggleDoNotDisturbMode` (Toggle Do Not Disturb Mode); the palette titles have the category "Notifications". The host sets the context keys `notificationCenterVisible`, `notificationToastsVisible` and `notificationFocus` (the focus is in a toast or in the center) in the scope of the window. VS Code has no menu row for them (its bell in the status bar is step 6.20: `workbench.Options.StatusRight` is the slot, and the bell runs `notifications.showList` and `notifications.hideList`). Not built: `notification.clear`, `notification.expand`, `notification.collapse` and `notification.toggle` for the notification that has the focus, `notifications.focusNextToast` and its kin, `notifications.toggleDoNotDisturbModeBySource` (it needs the quick input, step 6.17) and the other do-not-disturb filters by source, `notification.acceptPrimaryAction`, the secondary actions and the configure menu of an item, links and markdown in messages, the position settings (`workbench.notifications.position`), the rule that hides toasts that do not fit in the height of the window, the wait for the window to have the focus before a toast goes away, and the middle click that closes a notification.

**Dialogs** (`kit/dialog.go`, step 6.5; port of `dialog.ts` and `dialog.css`). A `DialogSpec` has a `Type` (`DialogInfo`, `DialogWarning`, `DialogError`, `DialogQuestion` (the information icon, as VS Code), `DialogNone`), a `Message` and a `Detail` (with a detail the message is a bold 14 px title over the 13 px detail on 20 px lines, whose line breaks are kept; without one the message is shown as the detail), `Buttons` (labels, "OK" by default; the marks of a mnemonic `&&` are left out), a `CancelButton` index, `DisableClose`, an optional checkbox (`CheckboxLabel`, `CheckboxChecked`) and `OnAnswer(DialogResult{Button, Checked, Cancelled})`. Button 0 is the default: primary (the others are secondary), focused when the dialog opens. The buttons show in Linux order (`DialogButtonOrder`, from `rearrangeButtons`): the cancel button right before the default one, the default one last. `Escape`, the close button (a 16 px "x" at the top right, left out with `DisableClose`) and `DialogController.Dismiss` cancel: `Button` is `CancelButton` (-1 when there is none) and `Cancelled` is true; a button answers with its index. The box is 480 px wide (at most 90 % of the window, 90 % of its height, the detail scrolling past that), padded 8 px, with a radius of 12, a 1 px `widget.border` border and a `widget.shadow` shadow (8 px blur) on `editorWidget.background`, text in `editorWidget.foreground`; the 24 px type icon is in `problemsErrorIcon.foreground`, `problemsWarningIcon.foreground` or `problemsInfoIcon.foreground` (VS Code has no `dialog.*` colors: its dialog styles are those, `editorWidget.*`, `widget.border` and `widget.shadow`). Keys: Tab and Shift+Tab (and Right and Left) go round the checkbox and the buttons (never out of the dialog), Enter and Space press the focused button, Enter and Space flip the focused checkbox (VS Code's `Toggle`), Escape cancels, and Enter with the focus on the dialog itself presses the default button. Not ported: inputs, the vertical alignment, custom bodies and footers, links, the button with a dropdown, the pending type and the mnemonics.

`DialogHost` (`NewDialogHost(child, controller)`) is placed once at the root of the workbench: it shows the dialog of a `DialogController` over its child in the same stack, in the middle of a scrim of 50 % black. The dialog is modal: the child keeps its place in the tree, so its state, but its pointer events are absorbed and its focus is excluded (the scrim also swallows the clicks, and a click on it brings the focus back into the dialog); the focus the window had when the first dialog opened is given back when the last one closes (if that widget is still there). `DialogController.Show(spec)` adds a dialog: one shows at a time, the others wait in order (`Pending`), a dialog shown from an `OnAnswer` goes behind the ones that wait; `IsShowing` tells the keybinding dispatcher of the window to let no command through, `Current`, `Dismiss` and `Clear` (drops the waiting ones) complete it. The controller is used from the UI thread only; other goroutines use the binding's `Post`.

### 10.8 Icons for files

VS Code's file icon themes are a font plus a JSON mapping (file extensions, file names, language ids and folder names to font characters and colors, with light-theme variants). Emetos bundles Seti, VS Code's default (`extensions/theme-seti/icons/seti.woff` and `vs-seti-icon-theme.json`), loads its font through `RunAppOpts.Fonts`, and reads the mapping in VS Code's icon theme format, so the explorer, tabs, breadcrumbs and quick open show the same icons as VS Code. "None" (no file icons) is the other choice.

**As built (step 6.14).**

*File icon themes* (`core/theme/fileicons.go`; port of `processIconThemeDocument` of `fileIconThemeData.ts` and of `getIconClasses.ts`; no Glutter import). `ParseFileIconTheme(id, data)` reads a theme file in VS Code's format (`iconDefinitions` with `fontCharacter`, `fontColor`, `fontSize` and `fontId`; `fonts`; `file`, `folder`, `folderExpanded`, `rootFolder`, `rootFolderExpanded`; `fileExtensions`, `fileNames`, `languageIds`, `folderNames`, `folderNamesExpanded`, `rootFolderNames`, `rootFolderNamesExpanded`; and the `light` and `highContrast` sections; a definition with an image path is not read) and fails with `FileIconThemeInvalid`; `BundledFileIconTheme("vs-seti")` is the Seti theme (`FileIconThemeNotFound` for another id). `IconFor(FileIconQuery{Kind, Name, Parent, LanguageID, Expanded, Type})` gives the `FileIcon` (the glyph, the family of its font, the color when the theme has one, the size as a factor of the text: 1.5 for Seti's "150%") or false. VS Code makes a CSS rule of each association and lets the specificity of the selectors choose, so the choice is by the number of class selectors of the rule: the default file icon 2, a language 3, an extension `segments + 3` (an extension is matched by a dot before it in the lowercase name, so `a.test.go` has `test.go` and `go`, and `test.go` beats `go`), a file name `segments + 4`, a key written `folder/name` one more when the folder the file is in has that name; for a folder the default 2, a name 3, the "expanded" rules 4 more when the folder is open (so an open folder takes `folderNamesExpanded`, then `folderExpanded`, then `folderNames`); the section of the theme type (`light` for light themes, `highContrast` for both high contrast themes) adds 1 to its rules, so it beats the document's own rules of the same kind; a tie goes to the file name, then the extension, then the language. `jsonc` has the icon of `json` when it has none of its own. A definition that has no character draws nothing and is skipped. Seti has no folder icons, as in VS Code: folders show their chevron and name only. The mapping is `internal/core/theme/iconassets/vs-seti-icon-theme.json`, copied by `scripts/update-assets.sh` (its license is `third_party/seti/`, listed in `NOTICE`); the font is the one of step 0.4. The setting `workbench.iconTheme` (default `vs-seti`, `null` for none) chooses the theme; `Window.FileIcons()` loads it (an unknown id is reported once as a warning and shows no icons). `kit.Colors.Type` is the type of the color theme. `explorer.FileIconWidget` draws the glyph in the family of the theme at 13 px times the scale (19.5 px for Seti), in the color of the theme or the color of the text, centered in a box 16 px wide and 22 px high, with 6 px between it and the label. The icons are used by the Explorer and the Open Editors; the tabs, the breadcrumbs, the Problems and the quick open still show the Codicons they had.

*The Explorer container* (`workbench.view.explorer`, "Show Explorer", Ctrl+Shift+E shows it and focuses the tree). It has the views of §10.4: **Open Editors** (above, hidden until it is shown, as the descriptor of VS Code 1.143 says: `workbench.files.action.focusOpenEditorsView`, Ctrl+K E, shows it, unfolds it and focuses its list; the container's own menu that shows and hides views is not built, `View.HideByDefault` is the switch), then either **Folders** (the tree of the folder; its header has the name of the folder, as VS Code's, or "Folders" with none) or, in a window with no folder, **No Folder Opened** with the welcome content.

*The folder view* (`gui/views/explorer`, `View`, `NewBody`, `NewActions`; port of `explorerView.ts` and of the data source and renderer of `explorerViewer.ts`). A `kit.Tree` keyed by path over a `workspace.Workspace`, showing the children of the folder at the top (the folder itself is the header). A row is the twistie, the icon of the file (the language comes from the registry, as a document's does, so `main.go` has the Go icon and `Makefile` the make one) and the name; a folder with `explorer.compactFolders` shows a chain of single child folders as one row, `a/b/c`, keyed by the first folder (`workspace.LoadedChain` gives the chain of what was read; reading a folder also reads the chain of its only child, as VS Code resolves single child descendants). Folders are read lazily in the background with the context of the window (the row shows "Loading..." meanwhile); a folder that cannot be read stays closed, so the next expansion tries again, and is reported as an error notification; a folder of the window that cannot be read shows its error in place of the tree. The rows are made again, once for any number of changes, when `Workspace.OnChange` fires (everything but a new size or time), and the expansion, the focus and the selection stay (they are by key). **Mouse and keys** are the tree's (§10.2): a click on a file selects it and opens it as a preview editor in the active group (`workbench.editor.enablePreview`), a double click or Enter keeps it; a click on a folder opens or closes it; Right, Left, Up, Down, Home, End and the page keys move as the tree's; a letter starts the find box (highlight mode, a fuzzy match). The keyboard focus stays in the tree when a preview opens. **Reveal** (`View.Reveal(path, RevealSelect | RevealNoScroll, done)`): the folders above the path are read in the background, then the rows are made again, the folders above the node are opened, the node is selected and focused, and (not for `RevealNoScroll`) scrolled into view after the next frame; a path outside the folder, one that `files.exclude` hides, or one that is not there is not found. `explorer.autoReveal` (`true`, `false`, `"focusNoScroll"`) reveals the file of the active editor when it changes and when the folder view comes on screen (the side bar shows the Explorer and the view is not folded). Not ported: `explorer.autoRevealExclude`, the find provider of the Explorer (the tree's own find box is used), the progress bar of a slow read, the decorations (git, problems) and the compact folder navigation commands. The buttons in the header of the folder view (shown while the pointer is over the view or the focus is in it): Refresh Explorer (`workbench.files.action.refreshFilesExplorer`: reads the folders that were read again) and Collapse Folders in Explorer (`workbench.files.action.collapseExplorerFolders`); New File and New Folder come with step 6.15.

*Open Editors* (`OpenEditors`, `NewOpenEditorsBody`; port of `openEditorsView.ts`): a `kit.List` of the editors of every group in grid order, with a row for each group ("GROUP 1", bold, 11 px) when there are several groups. An editor row is the close button, the icon, the name (in italics for the preview editor) and the folder dimmed; the button is a dot while the editor has unsaved changes, a cross for the row under the pointer, the selected row and a dirty editor (a click on it closes the editor). The active editor of the active group is selected. A click on a row makes its editor the active one of its group and the group the active group, a double click or Enter keeps it; a click on a group makes it active. `explorer.openEditors.sortOrder` (`editorOrder`, `alphabetical`, `fullPath`; the sorts of `getElements`) orders each group, `explorer.openEditors.visible` (default 9) is the number of rows the body has room for before it scrolls (at least one, at most the number of rows). Not built: the count of unsaved editors in the header, the drag and drop of editors, the context menu, `explorer.openEditors.minVisible` and the middle click.

*Welcome* (`NewWelcome`): "You have not yet opened a folder." over a button "Open Folder" (and, with editors open, "Opening a folder will close all currently open editors."). The button runs `workbench.action.files.openFolder` ("Open Folder...", Ctrl+K Ctrl+O, File menu row in group `2_open`), which shows the folder dialog of the desktop (the file chooser portal through `desktop.OpenFiles` with `Directory`, on a goroutine; a dialog that fails is the error `OpenFolderDialogFailed` and an error notification; a cancel does nothing) and opens the folder chosen with `Window.SetFolder` (§10.11). `workbench.action.closeFolder` ("Close Workspace", Ctrl+K F, File menu row "Close Folder" while a folder is open) gives the window no folder.

*Commands* (`core/command/builtin.go`, bound by `gui/app/explorer.go`; the view-less ones are no-ops): `workbench.view.explorer`, `workbench.explorer.fileView.focus` and `workbench.files.action.focusFilesExplorer` (show the Explorer and focus the tree), `workbench.files.action.focusOpenEditorsView`, `workbench.files.action.showActiveFileInExplorer` ("Reveal Active File in Explorer View"), `revealInExplorer` ("Reveal in Explorer View": the argument is a path or the context of a tab, else the active editor; it shows the Explorer, reveals the file and focuses the tree; a file outside the folder goes to the Open Editors when they are shown; the row is in the context menu of a tab), `workbench.files.action.refreshFilesExplorer`, `workbench.files.action.collapseExplorerFolders`, `workbench.action.files.openFolder` and `workbench.action.closeFolder`. **Context keys** on the window's keys: `workbenchState` (`"folder"` or `"empty"`), `explorerViewletVisible`, `foldersViewVisible`, `explorerViewletFocus`, `filesExplorerFocus`, `openEditorsFocus` (the focus is in the view, its header included), `explorerResourceIsFolder` (the focused row), `explorerResourceIsRoot` and `explorerResourceReadonly` (always false: there is no root row and no read-only folder) and `groupFocusedInOpenEditors`. **Settings**: `explorer.autoReveal`, `explorer.openEditors.visible`, `explorer.openEditors.sortOrder` and `workbench.iconTheme`.

### 10.9 Zen mode, full screen, zoom

- Zen mode (Ctrl+K Z) hides the activity bar, side bar, panel, status bar and tabs, centers the layout, and goes full screen (`zenMode.*` settings); full screen (F11); centered layout (`workbench.editor.centeredLayout*`).
- **Window zoom** (`window.zoomLevel`; Ctrl+=, Ctrl+-, Ctrl+Numpad0, as VS Code's Linux keys) scales the whole window by 1.2 per level: a `kit.Zoom` widget at the root lays out its child with the constraints divided by the factor and paints it scaled (Glutter has no zoom of its own; if this proves poor, it becomes a Glutter issue). Editor font zoom (`editor.mouseWheelZoom`, the font zoom commands) changes only the editor's font size.

### 10.10 State, backups and restore (`core/storage`)

- Paths (XDG): user configuration in `$XDG_CONFIG_HOME/emetos/` (default profile) or `$XDG_CONFIG_HOME/emetos/profiles/<name>/`; state in `$XDG_STATE_HOME/emetos/` (with `profiles/<name>/` for a profile's UI state); cache in `$XDG_CACHE_HOME/emetos/`; the socket in `$XDG_RUNTIME_DIR`. Every path is computed from these variables, so tests and proofs can redirect them (§15).
- **Window identity**: a window with a folder is identified by the first 16 hex digits of the SHA-256 of the folder's absolute path; a window without a folder gets a random id stored in the global state.
- UI state (global and per window id): open editors and their groups, view state per editor (selections, scroll, folds), layout, the explorer's expanded folders, window size, maximized and full-screen state, recently opened folders and files. Saved as JSON on change (debounced 1 s, atomic replace) and on exit.
- **Hot exit** (`files.hotExit`):
  - Backups: one second after a dirty document's last change, its content, encoding and the `FileStat` of the file it came from are written to `$XDG_STATE_HOME/emetos/backups/<window id>/<SHA-256 of the URI>.json` (atomically); a backup is removed after a successful save or a revert.
  - `onExit` (default): when the application quits (the last window closes or "Quit"), dirty documents are not asked about; their backups are restored on the next start. Closing a window that isn't the last asks about its dirty documents.
  - `onExitAndWindowClose`: closing any window doesn't ask either; its backups are restored when its folder (or the empty window) opens again.
  - `off`: always ask; no backups are restored.
  - A crash: each window writes a `running` marker in its state folder and removes it on a clean close; a marker found at start means the last run crashed, and that window's backups are restored whatever `files.hotExit` says.
  - A backup whose file changed on disk since opens dirty with a notice.

### 10.11 Command line and windows (`cmd/emetos`, `core/ipc`)

- `emetos [options] [paths...]`: `-n`/`--new-window`, `-r`/`--reuse-window`, `-g`/`--goto file:line[:col]`, `-d`/`--diff <a> <b>`, `-m`/`--merge <path1> <path2> <base> <result>`, `-w`/`--wait` (exit when the files are closed, for `git commit`), `--profile <name>`, `--log <level>`, `--version`, `--help`. A folder path opens it; file paths open the files. The options are parsed by hand (short and long forms, and positional counts for `--diff` and `--merge`).
- A running instance listens on `$XDG_RUNTIME_DIR/emetos-<uid>.sock` (versioned JSON messages); a second `emetos` hands its arguments and working directory over and exits, or waits with `--wait`. A stale socket (nobody listening) is removed. Two launches at once: the one that binds the socket wins; the other retries the hand-over.
- Multiple windows are Glutter windows of one process (§5.1). "Open Folder" in a window that has no dirty documents (or after their prompts) replaces its workspace: the window's services are disposed and created again for the new folder. **As built (step 6.14):** `Window.SetFolder(ctx, folder)` (an empty path is no folder) replaces the model of the folder, the workspace layer of the settings (`settings.Store.SetWorkspacePath`), the watch of the folder, `workbenchState` and the context of the window, and tells `OnFolderChange`; the Explorer, the Problems and the title follow. The services that do not belong to the folder (the documents' language registry, the notifications, the keymap, the theme) stay. The command (`workbench.action.files.openFolder`, `workbench.action.closeFolder`) first closes every editor, and refuses with a warning while a document has unsaved changes (the prompt of step 7.2 will ask instead); the process still has one window, so opening a folder in a new window (`-n`, step 7.x) is not built. Closing a window asks about its dirty documents per `files.hotExit` (§10.10); closing the last window quits.

### 10.12 Profiles

A profile is a name with its own `settings.json`, `keybindings.json`, `snippets/` (in its configuration folder) and UI state (in its state folder), §10.10. The default profile is the plain `emetos/` folders. Names are 1–64 characters of letters, digits, spaces, `-` and `_`. A window uses one profile: the one last used with its folder, else the default; `--profile` chooses it. Switching a window's profile reloads its settings, keybindings, snippets and theme in place (editors stay open). Backups belong to windows, not profiles. Export/import is one JSON file: `{"name", "settings", "keybindings", "snippets": {file name: text}}`, with the files' texts as strings.

### 10.13 Panels: Output and Problems (`gui/views/output`, `gui/views/problems`)

The panel (§10.1) has one tab per view container of the `panel` location of the view registry, in order: **Problems** (`workbench.panel.markers`, the `warning` Codicon, order 0, with the view `workbench.panel.markers.view`) and **Output** (`workbench.panel.output`, the `output` Codicon, order 1, with the view `workbench.panel.output`); the Debug Console and the Terminal come with their steps. A tab shows its title in capitals (11 px) with a line under the active one; the Problems tab also shows the count of problems (errors, warnings and infos, whatever the filter) in a pill in `panelTitleBadge.background` and `panelTitleBadge.foreground` (VS Code's `NumberBadge`; "Total N Problems" on hover, none when there are no problems, "999+" above 999). `workbench.Views` (step 6.7) also keeps the container the panel shows (`ActivePanel`, `OpenPanel(id)` shows the panel and the tab); a click on a tab opens it. `workbench.Options` has `PanelTabs` (with `Badge` and `BadgeTooltip`), `PanelActions` (the actions of the open view, in the title strip before the maximize and close buttons, as VS Code's view title actions), `FocusPanelView` (called with the container once a command has opened it with the focus) and the existing `Panel` body. The window keeps the two views for as long as it is shown (`Window.Problems`, `Window.Output`), so what a tab holds (the filter, the expansion of the tree, the channel, the scroll lock) survives a change of tab.

**Output** (`output.View`, `NewBody`, `NewActions`). The channels are those of `core/logs` (§13): `Store` keeps the last `DefaultMaxLines` (10,000) lines of each channel, `Watch(channel, fn)` gives the lines and then every event (`EventChannelAdded`, `EventLine`, `EventCleared`) with no gap and no repeat, and `Clear(channel)` empties a channel, which stays. `Process.Channels` is the store of the log (the Emetos channel is `logs.MainChannel`), or one of its own when the process has no log file. The view shows the active channel in a **read-only editor** (the real editor widget over a `document` with the virtual URI `emetos-virtual:output`; the document is made writable only while the view appends, its history is dropped after each edit, and it never counts as dirty), with VS Code's options for an output text: word wrap on, no line numbers, glyph margin, folding, minimap, sticky scroll, rulers or current-line highlight, 20 px of line decorations. Lines are queued by the logging goroutine and shown on the UI thread, many in one go (`binding.Post`); a channel older than the limit loses its first lines as the store does; a message with line breaks is several lines. **Follow tail**: after lines are added the editor scrolls to the end (after the next frame, since its layout lags the text) while the view is not locked and was showing the end before the lines came (a view the user scrolled up stays where it is), whatever the position when `output.smartScroll.enabled` is off. The **scroll lock** (`outputView.scrollLock`) keeps the view still; it is toggled by the lock button and `workbench.output.action.toggleAutoScroll`, locked by a click on a line other than the last and unlocked by a click on the last line (the smart scroll, a cursor move that is not the focus changing), and unlocking goes to the end. Switching channel unlocks and shows the end. The title strip has the dropdown of the channels (a channel that appears while the panel is open is added), the Clear button (`workbench.output.action.clearOutput`, which empties the channel in the store) and the lock button (the `lock` Codicon, "Turn Auto Scrolling Off"; `unlock`, "Turn Auto Scrolling On", while locked). `workbench.action.openActiveLogOutputFile` opens the log file in an editor for the Emetos channel (a notification says that another channel has no file). Not built: the filter box and the log level actions, Add Compound Log, Remove Output, Show Output Channels and Show Logs (they need the quick input), save, import and export of logs, "Open Output in New Window", the context menu of the Output editor (`inOutput` is set while it has the focus), links in the text.

**Markers** (`problems.Service`, `Marker`, `Severity`, in `gui/views/problems`; VS Code's `IMarkerService`). No package of §5.2 holds markers, so the model lives with the panel that shows it, in files that do not import Glutter; a producer of area 3 (language servers, tasks) sets markers on the window's `Window.Markers` from `gui/app`. A `Marker` has an owner, a resource (the absolute path of the file), a severity (`SeverityHint` 1, `SeverityInfo` 2, `SeverityWarning` 4, `SeverityError` 8, VS Code's values), a code, a source, a message, a range (`StartLine`, `StartColumn`, `EndLine`, `EndColumn`, counted from 1; a column counts UTF-16 units) and related information. `Set(owner, resource, markers)` replaces the markers of an owner for a file (none removes them; a marker with no message is dropped, and a range is made valid: positions from 1, the end not before the start); `Remove(owner, resources...)` removes those of the given files or of all of them; `Read(ReadFilter{Owner, Resource, Severities, Take})` gives markers sorted by seriousness (errors first), then resource and position; `Stats()` counts errors, warnings, infos and the rest; `Subscribe` is told which resources a change touched (on the goroutine that changed them; the service is safe for concurrent use). The hints are not shown in the panel.

**Problems** (`problems.Model`, `View`, `NewBody`, `NewActions`). The `Model` groups the markers by file, sorted as VS Code sorts them (a file whose first marker is more serious comes first, then by path; the markers of a file errors first, each severity by position), narrows them with a `FilterOptions` and counts the total and the filtered. It refreshes on the UI thread, once for any number of changes. **Filter**: the severity switches (errors, warnings, infos), the active file only (`SetActiveFile` is told by the window which file the active editor shows), and the text of the filter box, which as in VS Code's `FilterOptions` is words that match, case-insensitively, the message, source and code of a marker and the name of its file (a match on the name shows all the markers of the file); a leading `!` shows what does not match; the patterns separated by commas are globs (`**/*.go`, `.go` for `*.go`, `pkg` for a folder anywhere; they are matched against the whole path) that include files, and a `!` before one excludes its files; `@source:name` (quoted when it has spaces, `!@source:name` to exclude) keeps the markers of a source. Not built: fuzzy matching of the words (they match as substrings), the exclusion by `files.exclude` (`FilterOptions.Exclude` takes it; there is no setting before step 6.13), the table view and its commands (`problems.defaultViewMode`), the multi-line messages, the related information rows, the quick fix and copy actions, `problems.autoReveal`, `problems.sortOrder` and `problems.showCurrentInStatus` (no consumer yet), and the settings `problems.visibility` and `problems.decorations.enabled` (they hide the squiggles and the status of area 3). The tree (`kit.Tree` over the model, 22 px rows) has a row per file (a file icon placeholder (the file icon theme of step 6.14, §10.8, is not used here yet), the name, the folder dimmed and relative to the folder of the window, and a count `kit.Badge`) and a row per marker below it (the icon of the severity in `problemsErrorIcon.foreground`, `problemsWarningIcon.foreground` or `problemsInfoIcon.foreground`, the first line of the message, the source and code dimmed as `source(code)`, and the position `[Ln 3, Col 5]` dimmed); a file that gets markers is expanded, and one the user folded stays folded while it has markers. A click on a file folds or unfolds it; a click on a marker, or Enter, opens the file as a preview in the active group with the range of the marker selected (the file is read in the background; a column is converted from UTF-16 units to bytes; a double click keeps the editor). Without markers the body says "No problems have been detected in the workspace." (or "... in the current file." with the active file only), and when the filter lets nothing through "No results found with provided filter criteria." with a "Clear Filters" link. The title strip has the filter box (placeholder "Filter (e.g. text, **/*.ts, !**/node_modules/**, @source:ts)"), a switch for each severity and one for the active file, and the Collapse All button; the switches show VS Code's "more filters" menu as separate buttons.

**Commands** (ids, titles and keys of VS Code, Linux): `workbench.actions.view.problems` "Toggle Problems" (Ctrl+Shift+M) and `workbench.action.output.toggleOutput` "Toggle Output" (Ctrl+K Ctrl+H: VS Code binds Ctrl+Shift+U, and Ctrl+K Ctrl+H on Linux, where the desktop takes Ctrl+Shift+U) show the tab with the focus, or hide the panel when its view has the focus; `workbench.panel.markers.view.focus`, `workbench.panel.output.focus` and `workbench.action.problems.focus` show a tab with the focus; `workbench.actions.view.toggleProblems` hides the panel when the Problems are shown, else shows them with the focus; `workbench.action.showErrorsWarnings` shows them without the focus. All but the toggles are in the View menu: Problems and Output, in the group `5_panel` after Editor Layout. The commands of the Problems view: `problems.action.focusFilter` (Ctrl+F while `focusedView == 'workbench.panel.markers.view'`), `problems.action.focusProblemsFromFilter` (Ctrl+Down while `problemsFilterFocus`), `problems.action.clearFilterText` (Escape while `problemsFilterFocus`), `workbench.actions.treeView.workbench.panel.markers.view.collapseAll` and `workbench.actions.workbench.panel.markers.view.toggleErrors`, `.toggleWarnings`, `.toggleInfos` and `.toggleActiveFile`; and of the Output view: `workbench.output.action.clearOutput`, `workbench.output.action.toggleAutoScroll` (VS Code's id: this version of VS Code has no `toggleOutputScrollLock`) and `workbench.action.openActiveLogOutputFile`. **Context keys** (set on the window's keys): `activePanel` (the container the panel shows) and `problemsVisibility` (the panel is shown with the Problems) by the workbench; `focusedView` (the view that has the focus: `workbench.panel.markers.view` or `workbench.panel.output`), `problemFocus` (the tree), `problemsFilterFocus`, `problems.filter.errors`, `problems.filter.warnings`, `problems.filter.info` and `problems.filter.activeFile` by the Problems; `inOutput`, `outputView.scrollLock` and `activeOutputChannel` by the Output. **Colors**: `problemsErrorIcon.foreground`, `problemsWarningIcon.foreground` and `problemsInfoIcon.foreground` (step 6.5), and with this step `activityBarBadge.background`, `activityBarBadge.foreground`, `panelTitleBadge.background` and `panelTitleBadge.foreground`; the tree and the editor use the list, input, badge and editor colors. **Settings**: `output.smartScroll.enabled` (true).

## 11. Configuration

### 11.1 Settings (`core/jsonc`, `core/settings`)

- `settings.json` files are JSON with comments and trailing commas. `core/jsonc` parses them with positions, and edits a value while keeping comments and formatting (as VS Code's `jsonc-parser` does), given formatting options (tab size, spaces, line ending).
- Layers, lowest to highest: defaults, user (profile), workspace (`<folder>/.emetos/settings.json` only, D12), and language-specific blocks (`"[go]": {...}`) inside each layer.
- Every setting is registered with key, type, default, description, enum values and descriptions, range, scope, and category, by the step that first uses it, with VS Code's values (`editorOptions.ts` for `editor.*`, the workbench's configuration contributions for the rest). Reading an unregistered key is a programmer error (a panic in debug builds). Unknown keys in a file are kept and reported. Change events carry the affected keys. Writing a value creates the file and its folder when needed.
- **Resolution** (as VS Code): the layers are merged (objects key by key, anything else replaced) and then the `[language]` blocks of the merged result are applied for the language asked about, so a block of any layer wins over the plain settings of every layer, a workspace block over a user block, and a block of one language alone over a block shared with others (`"[go][json]"`). A language's defaults (a language contributes them like VS Code's `configurationDefaults`) are blocks of the defaults layer. Settings of the application scope are read from the user file only; a workspace file that sets one gets a problem and the value is ignored. A value that its setting does not allow (type, enum, range) falls back to the default and is listed as a problem; so are syntax errors, unknown keys and ignored keys. Writing a value keeps the comments and the file's own indentation, line ending and byte order mark, edits a setting written as nested objects where it is, and creates the file and its folder.
- The settings UI shows registered settings by category with search, edits user or workspace values, and links to the JSON.

### 11.2 Commands and context keys (`core/command`, `core/contextkey`)

- Commands have an id (VS Code's ids where the command exists in VS Code), a title, a category, a precondition, and a handler. The registry holds metadata first; the handler is attached by the package that implements it (an editor command's handler lives in `gui/editor` and calls `core/edit`). Menus, keybindings, the palette and dev commands all run commands by id, with optional JSON-compatible arguments. A command VS Code does not list in the palette (the cursor commands) has no title, and the palette skips it. Setting a handler on a command that has one stacks it: the last one runs, and its remover brings the previous one back. `Run` does not check the precondition; menus, the palette and the dispatcher call `Enabled` first, as VS Code does.
- **Menus** hold items that run commands by id (§10.1 "Menus and the menu bar"). A command that VS Code puts in a menu gets its row in `command/menus_default.go` with VS Code's menu id, group, order, `when` and mnemonic title; the menus show an item dimmed when the precondition of its command does not hold and leave it out when its `when` does not. The built-in menus have rows for the commands that exist, and a menu appears in the menu bar when it has a row.
- Context keys (e.g. `editorTextFocus`, `editorHasSelection`, `findWidgetVisible`, `explorerViewletFocus`, `resourceExtname`) live in scopes: a tree of scopes (window → part → widget); a widget gets a child scope from its parent's and sets its keys there; a lookup walks up the tree; the dispatcher (§5.4) evaluates against the scope of the focused widget. When-clauses use VS Code's syntax: `!`, `&&`, `||`, `==`, `!=`, `=~` (regex), `<`, `>`, `in`, `not in`, parentheses. Evaluation follows JavaScript's rules where VS Code relies on them (`==` is loose, a key that is not set is tested as the string "undefined" by `=~`, `<` and `>` parse the value as a float). Expressions are kept in VS Code's normal form (flat, sorted, `||` outermost) so that `Negate`, `Equals` and `Implies` behave as in VS Code. Regular expressions use Go's engine until `core/regex` has its ECMAScript mode; a pattern it cannot run (lookahead, backreferences) is accepted and never matches.
- The notification host sets `notificationCenterVisible`, `notificationToastsVisible` and `notificationFocus` on the window's keys (step 6.11, §10.7); the Escape rules of `notifications.hideList` and `notifications.hideToasts` have their `when` on them.
- The editor group sets `activeEditor` (the type id of the active input, unset with none), `activeEditorIsPinned` (the active tab is sticky) and `activeEditorIsNotPreview` on the window's keys (step 6.8, §10.3); the Close Editor row of the File menu has the precondition `activeEditor`. The grid of groups (step 6.9) adds `multipleEditorGroups`, `editorPartMultipleEditorGroups`, `editorPartMaximizedEditorGroup` and `activeEditorGroupEmpty`; the Switch Group rows and `toggleMaximizeEditorGroup` have their preconditions on them and Ctrl+W has a second rule, `closeGroup`, under `activeEditorGroupEmpty && multipleEditorGroups`.

- The panels set `activePanel`, `problemsVisibility`, `focusedView`, `problemFocus`, `problemsFilterFocus`, `problems.filter.errors`, `problems.filter.warnings`, `problems.filter.info`, `problems.filter.activeFile`, `inOutput`, `outputView.scrollLock` and `activeOutputChannel` on the window's keys (step 6.12, §10.13); the Ctrl+F, Ctrl+Down and Escape rules of the Problems view have their `when` on `focusedView` and `problemsFilterFocus`.
- The window and the Explorer set `workbenchState` (`"folder"` or `"empty"`), `explorerViewletVisible`, `foldersViewVisible`, `explorerViewletFocus`, `filesExplorerFocus`, `openEditorsFocus`, `explorerResourceIsFolder`, `explorerResourceIsRoot`, `explorerResourceReadonly` and `groupFocusedInOpenEditors` (step 6.14, §10.8); the Close Folder row of the File menu and the views of the Explorer have their `when` on `workbenchState`.

### 11.3 Keybindings (`core/keybinding`)

- The default keymap is VS Code's Linux keymap for the commands Emetos has. VS Code registers its defaults in code (`registerKeybinding`/`KeybindingsRegistry` calls in `coreCommands.ts` and the contributions); each step that adds a command adds its default binding from there.
- `keybindings.json` entries: `key` (with chords such as `ctrl+k ctrl+c`), `command` (a leading `-` removes a default), `when`, `args`. A leading `^` in a default's command id means the key is not consumed. An entry whose key, command id or when-clause cannot be read is reported as a problem and skipped (VS Code keeps an entry with an unknown key as an unbound command, so a typo in a removal would remove every key of the command). The `[KeyCode]` spelling of keys is not supported.
- Keys are VS Code's `KeyCode`s; the resolver matches the string `ctrl+shift+alt+meta+<Key>` of a pressed chord (the UI name of the key, such as `K`, `LeftArrow`, `[`). A pressed sequence resolves to no match, more chords needed, or a command; of several bindings that match, the last one registered whose when-clause holds wins, after the sort by weight (core 0, contributions 100, workbench 200), command id and secondary-key order. The dispatcher (`keybinding.Dispatcher`) keeps the pending chords and forgets them after 5 seconds (`Expire`, called from a timer); a key that completes no binding ends chord mode and is consumed, and shows "The key combination (Ctrl+K, X) is not a command.". Keybindings made of a lone modifier ("shift shift") resolve, but the dispatcher does not yet detect the double press (it needs key-up events: the workbench step).
- A chord's first key shows "(Ctrl+K) was pressed. Waiting for second key of chord..." in the status bar.
- A **recording mode** (for the keybindings UI) hands every key event to a recorder before resolution.
- The keybindings UI lists every command with its key, source (default/user) and when-clause; it searches by name and by recorded key, and edits `keybindings.json`.

## 12. Privacy

- Emetos never opens a network connection of its own: no telemetry, crash reports, update checks, extension galleries or remote fonts. `internal/archtest` fails the build when a package imports `net/http` (§5.3).
- Links in notifications or help open in the user's browser through the desktop portal; that is the only path to the network, and only on a click.
- Logs stay on disk (§13).

## 13. Errors and logging

- Every error uses `github.com/rm4n0s/errors` (CLAUDE.md). Errors shown to the user become notifications with a short message; the full error goes to the log as a `slog` attribute (`"err", err`).
- Logs: `log/slog` to `$XDG_STATE_HOME/emetos/logs/<date>/main.log` (kept 7 days), and to the "Emetos" channel of the Output panel (§10.13: `logs.Store` has `Subscribe`, `Watch` and `Clear`). `emetos --log debug` raises the level.
- A panic in a background goroutine is recovered, logged, and reported once as an error notification; the window stays open. A panic in the UI goroutine is handled by Glutter's error reporting, logged, and Emetos tries to write backups (§10.10) before exiting.

## 15. Testing

### 15.1 Tests

- Core packages: table-driven unit tests, fuzz tests for the buffer (random edits checked against a plain string), the JSONC parser, the snippet parser, the when-clause parser, and the tokenizer (no panics, bounded time).
- **Ported VS Code tests** use 1-based lines and UTF-16 columns; `core/vstest` converts them to Emetos positions. A case with non-ASCII text has its expected positions worked out again for byte columns, with a comment saying so. A case that needs VS Code's TypeScript harness (a full editor, services) is skipped, and the count of skipped cases is recorded.
- Tokenization: VS Code's own oracle, `extensions/vscode-colorize-tests/test/colorize-fixtures` and `colorize-results` (scopes per token), for every bundled language that has fixtures there; small fixtures of Emetos's own for the others.
- UI: `gluttertest` widget tests with the fake platform (keys through `SendKeyEvent`, IME through `SendTextInputEvent`, clipboard, file choosers, window close), and golden images with `MatchesGolden`.
- Golden images need deterministic fonts: UI tests load Go Mono (regular, bold, italic, bold italic), Codicons and Seti through `gluttertest.Opts.Fonts`, and set `editor.fontFamily` to Go Mono (D14). Glyphs Go Mono lacks (CJK, emoji) show as boxes, so their layout is checked through the paragraph queries, not by goldens.
- **Isolation**: no test, proof or check reads or writes the user's real configuration, state, cache, trash or socket. Go tests call a helper that points every `XDG_*` variable at `t.TempDir()`; scripts run the app through `scripts/isolated.sh`, which does the same with a temporary folder (and can copy a fixture configuration in).
- Display tests (`emetos_display` tag) start the real app under a headless Wayland compositor.
- Performance benchmarks (§14) are Go benchmarks plus `scripts/perf.sh`, which runs the app with `GLUTTER_FRAME_STATS=1`.

### 15.2 Dev commands

`EMETOS_DEV_COMMANDS` holds a JSON array of steps run after the first frame, each `["<command id>", <args>]` or `["sleep", "<duration>"]`, for example `[["workbench.action.quickOpen", ">line"], ["sleep", "200ms"]]`. Any registered command can be used; commands whose id starts with `dev.` exist only for this (opening a file at a position in a group, posting a notification, typing text) and are registered only in debug and `emetos_dev` builds (D15). `dev.openFile {"path", "line", "column", "group", "preview"}` shows a file in an editor group of the window (a relative path is relative to the folder Emetos runs in; line and column count from 1 and are optional; `group` is the place of an existing group, counted from 1 in the order the groups appear in the grid, and the file opens in the active group when it is not given; the group becomes the active group; a `group` that is not a whole number of 1 or more fails with the tag `DevOpenFileInvalid`, and one that does not exist with `DevOpenFileGroupInvalid`; `"preview": true` opens it as the preview editor of the group (an italic tab that the next preview replaces; only with `workbench.editor.enablePreview` and for a document without changes), as a navigation does, where the default is a kept editor, and a `preview` that is not true or false fails with `DevOpenFilePreviewInvalid`); `dev.openMenu {"id", "x", "y"}` opens a menu of the window (step 6.7): the id of a menu of the menu bar (`MenubarEditMenu`: opened as a click on its title does), `GlobalActivity` (the Manage menu) or `EditorContext` (the context menu of the editor, at `x` and `y` in window coordinates, 400 and 250 by default; the argument may also be the id as a string); an id of any other menu, and a menu of the bar that has no item, fail; `dev.notify {"severity", "message", "source", "actions", "progress"}` sends a notification through `core/notify` (step 6.11; the argument may also be the message as a string): `severity` is `"info"` (the default), `"warning"` or `"error"`, `message` is a text that is not empty, `source` a text, `actions` a list of button labels (a button closes the toast and writes `dev.notify action` with the label to the log) and `progress` a number from 0 to 100 (the bar of a running progress) or `"infinite"`; a bad argument fails with its own tag, `DevNotifyArgumentsInvalid`, `DevNotifySeverityInvalid`, `DevNotifyMessageInvalid`, `DevNotifySourceInvalid`, `DevNotifyActionsInvalid` or `DevNotifyProgressInvalid`; `dev.setMarkers {"owner", "resource", "markers": [{"severity", "message", "startLine", "startColumn", "endLine", "endColumn", "source", "code"}]}` sets the markers an owner (`"dev"` by default) has for a file, so that the Problems panel has something to show before area 3 (step 6.12; the window implements it; `resource` is a path, relative to the folder Emetos runs in or absolute; a missing or empty `markers` removes the markers of the owner for that file; `severity` is `"error"` (the default), `"warning"`, `"info"` or `"hint"`, `message` a text that is not empty, the four positions whole numbers from 1 (1, 1, the start line and the start column when missing), `source` and `code` texts); a bad argument fails with its own tag, `DevSetMarkersArgumentsInvalid`, `DevSetMarkersOwnerInvalid`, `DevSetMarkersResourceInvalid`, `DevSetMarkersCwdFailed`, `DevSetMarkersMarkersInvalid`, `DevSetMarkersMarkerInvalid`, `DevSetMarkersSeverityInvalid`, `DevSetMarkersMessageInvalid`, `DevSetMarkersPositionInvalid` or `DevSetMarkersTextInvalid`, and without a window it fails with `DevNoWindow`; `dev.log {"channel", "message"}` appends a line to a log channel of the Output panel (`"Emetos"` by default; the argument may also be the message as a string), and fails with `DevLogArgumentsInvalid`, `DevLogChannelInvalid` or `DevLogMessageInvalid`; `dev.type` (a text, one character in each frame) and `dev.scroll` act on the editor that has the focus. The runner waits two frames after each command, so that what the command made (an editor, the focus) is there for the next. The keyboard focus of a new active group follows a few frames later (§10.3), so a script that types after a command that changes the group puts a `sleep` between them.

## 20. Risks

| Risk | Mitigation |
|---|---|
| Text rendering through Glutter is too slow for an editor | Per-line paragraph cache, repaint boundary for the text, the performance check in step 3.11 before anything else is built on the editor; fixes go into Glutter (D8). Glutter's own numbers (41–58 µs per cold code line, 5–10 µs for an unchanged one) fit the budget of §14 |
| TextMate grammars written for Oniguruma behave differently with regexp2 | Translation layer in `core/regex`, a test that compiles every pattern of every bundled grammar, VS Code's colorize oracles, timeouts |
| Glutter is young; Emetos is its first large app | Workarounds are marked and listed (D8); Glutter fixes are made in the Glutter repository |
| Glutter's close requests for the first window are app-wide | Step 7.8 checks which hook reaches each window, and records a Glutter issue if the first window can't be told apart |
| The scope of "what VS Code has" grows | Areas 3–11 are outside this spec until planned; every feature in §3 is a row with a defined behavior |
