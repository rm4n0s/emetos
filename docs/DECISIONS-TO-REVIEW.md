## 2026-10-25: remote control (the user's design and answers)

33. **Remote control of one workspace** between two Emetos instances (milestone M15): A turns it on per workspace with a port and a list of allowed SSH public keys, kept in `~/.local/state/emetos/remote-control.json` and edited only through Emetos's "Remote Control" page; A listens only while it is on, with an idle timeout (30 minutes) and a visible "connected" banner with Disconnect. B opens a "Remote Workspace..." window tab with host, port and private key. B gets **its own view** of the workspace at its tab size (own cursor and scroll, same files), not a mirror of A's screen.
34. **Transport (the user's choice): QUIC over UDP by default, SSH for login.** B logs in over an embedded SSH server on A (TCP, `golang.org/x/crypto/ssh`: only listed keys, no shell, host key pinned like `known_hosts`, keys read directly with passphrase and `ssh-agent` support); inside that authenticated channel A gives B a long random session token and the fingerprint of A's QUIC certificate; B then opens **QUIC** (UDP, `github.com/quic-go/quic-go`, TLS 1.3 inside) on the same port number with the token, so the QUIC certificate is checked against the fingerprint learned over SSH. Picture tiles go as QUIC **datagrams** (latest picture wins, losses repaired by the next frame and a periodic refresh); input, clipboard and notifications go on reliable QUIC streams. If UDP is blocked, the session falls back to channels of the SSH connection (TCP). Both dependencies were approved by the user and added to CLAUDE.md's allowed list.

## 2026-10-25: step 11.1 (the extension contract), decided by the agent and accepted by me

46. **`extension/` is the pure contract** (it imports nothing of Emetos); the host that runs extensions is `internal/gui/exthost`, and `extensions.All()` is a function returning a fresh list. ## 2026-10-25: step 11.2 (events), decided by the agent and accepted by me

49. **`Request` takes a reply callback** instead of returning `(Event, error)` as the spec said (a blocking call on the UI thread could freeze it for the 10 s timeout); a handler can answer later with **`HandleAsync`** (the Agents extension needs it). One handler per topic per scope; requests time out after 10 s unless the `ctx` says otherwise.
50. **Topics and patterns:** dotted, case-sensitive segments; `*` is one segment, a final `**` one or more. Fast topics (`emetos.document.changed`, `emetos.editor.selectionChanged`, and those an extension declares fast) arrive once per frame as a batch; order is kept per publisher and topic. Extensions cannot take the `emetos.*` ids. A handler or subscriber slower than 50 ms is logged.

## 2026-10-25: step 11.3 (event sharing between window tabs), decided by the agent and accepted by me

51. **A tab is named in a link by its folder** (the cleaned absolute path), so a link survives restarts; an extension window tab will be `<extension id>:<tab id>` (11.7). **A No Folder tab takes part in no sharing** (it has no stable name; links to it would pile up dead).
52. **The data's direction decides:** a request made in office for a handler in notes needs the link `notes → office`, and the reply comes back along it (the spec's "request along the link" would have let the prompt create a link that does not authorize the request; the spec is reworded). A cross-tab `Read` needs a link carrying `emetos.document.changed` and is never asked about (it is synchronous). A private workspace sends nothing, answers no request, allows no read out, is never asked about, and makes no requests to other tabs (a request carries its value out); it still receives along links.
53. **The prompt** shows in the receiving tab (it waits there; the window does not switch tabs): one question per pair of tabs at a time, Allow saves the link (merged into an existing one), This Session Only keeps it in memory, Deny (also Escape) stores nothing and is remembered until the extension is activated again. Events published before the answer are dropped. Removing a link on the page counts as a Deny for the extensions that listened to it.

## 2026-10-28: step 17d.1 (the emulator; decided by the agent, to be accepted by me)

120. **Width is wcwidth's model.** East Asian Width wide and fullwidth take two cells (emoji with emoji presentation among them), Mn, Me, Cf and the Hangul medial and final jamo take none and join the cell before; a variation selector, a zero width joiner or a regional indicator does not change a width, and the emoji after a joiner gets its own cell. This is what programs compute with `wcwidth(3)`, so what they lay out is what the emulator draws; the modern "grapheme cluster" widths (VS16 widening, ZWJ families as one glyph of two cells, flags) would put a program's idea of a line out of step with the screen. Mode 2027 is answered as permanently reset. `width_gen.go` is generated from `golang.org/x/text/width` and the standard library, so there is no new data file or license.
121. **Where xterm leaves room I chose:** `IL` and `DL` move the cursor to column 1 (the VT510 manual does not say; DEC STD 070 does); a scroll of a region that is not the whole screen keeps nothing in the scrollback; ED 2 on the normal screen pushes the lines up to the last one that holds something into the scrollback and then clears (**changed in step 17d.2**, as VS Code, VTE and foot do: Ctrl+L in bash sends `CSI H CSI 2 J` and the earlier output must stay reachable; ED 3 still deletes the scrollback and the alternate screen is not changed; a `clear` command that ends with `ESC [ 3 J` still empties it); RIS keeps the scrollback; a wide character at the last column of a terminal with autowrap off is dropped; a combining mark at column 1 is dropped; the default cursor is a steady block and DECSCUSR 0 is a blinking block; the keypad in application mode sends the VT220 letters (`SS3 p` to `SS3 y`, `n` for the decimal point); F13 to F20 are sent as Shift+F1 to Shift+F8, which is what `kf13` to `kf20` of the `xterm-256color` terminfo entry say (the VT220 codes `CSI 25 ~` ... would not match the entry programs read); a `:` separates the parameters of every CSI.
122. **The hyperlink is part of the style** (an OSC 8 link changes the style index of the cells it covers), not a side table of the row as SPEC §10.25 "Speed" first said. The table of styles and the table of links hold 65,535 entries each; when one is full the styles no cell uses are dropped (a scan of every cell, at most once per 65,535 refused entries) and then 24-bit colors are rounded to the 256-color cube and, last, the default style is used, so the memory is bounded and a rainbow of 100,000 colors costs 100 MB/s, not a freeze.
123. **The throughput tests have floors for the two inputs §14 gives no budget for** (scrolling in a region 200 MB/s, cursor motion 60 MB/s) **and for the worst case of the style table** (40 MB/s), about a quarter to a half of what was measured, so that a regression shows without a noisy test; the three budgets of §14 are held as written (the best of five runs of 8 MiB).
124. **Answers to the program:** DA1 is `CSI ? 1 ; 2 c` ("VT100 with Advanced Video Option", which every program accepts), DA2 is `CSI > 0 ; 276 ; 0 c` (xterm's patch level 276, the one `vim` and others test for), XTVERSION `DCS > | Emetos(version) ST`; `CSI 18 t` and `19 t` report the size in characters; the window operations that move, resize or report pixels are ignored (a program cannot move the editor's window); OSC 52 goes to a callback that the host sets, and does nothing otherwise (as VS Code's default).
125. **Serialization** starts with RIS and `ESC [ 3 J` so that it can be fed to a terminal that was used; it does not carry the saved cursor or the character sets, and in origin mode a cursor outside the scroll region goes to the nearest margin (origin mode cannot place it there). It keeps a row's autowrap only if the next row holds something (a stale flag left by an erase is dropped), and it writes `ESC [ K` after each row so that cells the pen painted when the row scrolled in are default again.
126. **The tests of the programs keep what they recorded** (`testdata/programs/*.raw`, written by `-update-goldens` next to the `.golden`), and `TestReplayRecordings` replays it without the programs, so the goldens are checked on a machine that has none of `vim`, `less`, `tmux` or `git`; the live test skips when a program is missing. `htop` is checked by layout (its screen changes every second). The programs run in a temporary home with `TERM=xterm-256color`, `-u NONE` for `vim`, `-f` of our own for `tmux`, `GIT_CONFIG_*` pointing nowhere.

## 2026-10-28: step 17e.2 (Search across files; decided by the agent, to be accepted by me)

150. **The engine walks the folder itself** (`internal/core/search`), on one goroutine that lists files while a worker per CPU (at most 8) reads and matches them, so the first result comes within a few milliseconds. It does not use the workspace's file index to walk, but takes its list of files (instead of walking) when the walk of the index is done and the search is the plain one (the settings' excludes and ignore files on); the index has the same exclusions applied. Hidden files are searched, as VS Code's `rg --hidden` does, and `.git` is never entered. A file over 64 MiB is skipped (`Summary.TooLarge`), a file with a NUL in its first 8 KiB (and no byte order mark of UTF-16) is binary and skipped, and a lone `\r` is not a line break.
151. **The container of the view is `emetos.search.container`, not VS Code's `workbench.view.search`**, because the ids of the containers and views of an extension start with its own id (`CheckManifest`). The command `workbench.view.search` ("Show Search") shows it, so VS Code's id still works in a keybinding. VS Code's context keys (`searchViewletVisible`, `hasSearchResult`, ...) are set through a new field of the manifest, `Contributes.ContextKeys`, which lets an extension set the keys it names whole besides those under its own id (the field came with the terminal in 17d.2; at the rebase 17e.2's second copy of it was dropped and the terminal's design kept, whose checks are `ExtensionContextKeyDeclInvalid` and `ExtensionContextKeyDeclDuplicate`); the view's `searchViewletVisible` is true once the view was built (the host does not tell when it is hidden).
152. **The include and exclude boxes follow VS Code's `parseSearchPaths`** for the segments it can honour in one folder: `./src` is relative to the folder, a bare `src` or `*.ts` is searched for anywhere, a path inside the folder is made relative, and `../x`, `~/x` and a path outside the folder are left out (the search never leaves the folder).
153. **Replace as VS Code's, with what the API has**: the matches of a file that an editor has open are replaced with `Documents().Apply` (one undo step for the file; the cursors keep their place) and the document is then saved through the core topic `emetos.document.save`, as VS Code saves after a replace; the files that no editor has open go through a new `Workspace().ReplaceInFiles`, which reads the file as the editor does and writes it back atomically with the same encoding, byte order mark and line ending, and skips a match whose text is not the one the search found (the file changed since). Replace All asks first with a quick pick (**Replace** / **Cancel**), as VS Code asks with a dialog.
154. **The replace preview is the diff editor of `Editors().OpenProposedChange`**: a click on a match, while the replace box has text, opens the file as it is against the file with all of its replacements; **Accept** replaces the file, **Reject** or closing does nothing. VS Code's preview is the same two sides, with its own accept path.
155. **Find in Folder... is a command of the core** (`filesExplorer.findInFolder`, Shift+Alt+F in the Explorer, group `4_search` of the Explorer's menu), not of the extension, because only the window knows which folder was clicked; it runs the extension's `workbench.action.findInFiles` with `filesToInclude` set to `./<folder>`, and says so in a notification when the extension is off. The commands of the Search view act inside the workspace only, so Relay clients may run them (`clientpolicy_test.go` allows the new command on purpose).
156. **Not built in this step**: Open to the Side (`search.action.openResultToSide`, the API has no side option for `Documents().Show`), the right-click menu of the results, file icons in the rows, the "Open in editor" link and the Search Editor, Quick Search, AI search, history of the boxes across restarts (Up and Down go through the values of the session), `search.sortOrder: modified` (the search does not know the times of the files, so it sorts as `default`), and `search.seedOnFocus`. The "Open Settings" link of the message shows a quick pick with the one row that opens the settings, because an extension has no call that runs a command of the editor directly.
157. **`search.maxResults` empty (`null`) means 20000**, not unlimited as in VS Code: the results are kept in memory and in the tree. The description of the setting says so.
158. **The results reach the UI thread at most every 30 ms** (one `api.Post` for a batch, then a gap of 30 ms), and each take rebuilds the nodes of the tree; the longest turn measured with 20,000 matches in 2,000 files streaming in is 10.7 ms (`TestTheUIThreadStaysUnderAFrameWhileAHugeSearchStreams`). A result list is not paginated.
159. **A regular expression that does not compile is reported with the error of `internal/core/regex`** (its message under the search box, in the input's error color); the engine has no tag of its own for it, because an error that came from that package is returned untouched (CLAUDE.md "Error handling"). A search whose context ends has the tag `SearchCancelled`.

## 2026-10-28: step 17d.4 (the terminal's events and Relay; decided by the agent, to be accepted by me)

180. **Allow terminals is a third level, per key and workspace, off by default, and never for Watch only.** It is stored as `terminals` (folder to true) in each key of `relay.json`; a file that allows it where the key may not send is refused as a whole (`RelayConfigInvalid`), and taking Watch and send back drops it. It is checked when a request is read and again when it is acted on, so unchecking it stops what is already queued. The checkbox sits under each Watch and send row in Be a Host with the SPEC's warning, red while on.
181. **`list` and `snapshot` are allowed with Watch only; everything else of `emetos.terminal.*` needs Watch and send and Allow terminals.** The output events are already seen with Watch only, and a panel that may not type needs the list and the screen to show anything. The cost is that a snapshot also gives the scrollback from before the client connected: the Security notes and the README say so. Any `emetos.terminal.*` request not named is refused until it is thought about (default deny), with `RelayTerminalRefused`.
182. **A client may not publish in `emetos.terminal.*` (`RelayTerminalRefused`) or `emetos.relay.*` (`RelayTopicRefused`).** A client that could publish the output of a terminal could show the host's user what never happened there, or take the mark of its typing away. The host stamps `by` into the requests it makes for a client (`relay:<key comment>`); a `by` sent by a client is overwritten.
183. **The protocol stays at version 1.** The Hello's `Workspace` gained the optional `terminals` field; an older client ignores it and a client of this version with an older host sees none and stays read-only. No new message types.
184. **The output stream is pieces with `seq`, and a snapshot is exact.** The observer runs under the lock that guards the emulator's `Write`, so a snapshot (pending text published, then the screen serialized) is the screen after piece `seq`. A piece is at most 64 KiB or 50 ms of output, always valid UTF-8 (invalid bytes become U+FFFD by the maximal-subpart rule; an incomplete tail is carried over). A client that sees a gap, a dropped marker or a reconnect asks for a new snapshot; while one is loading, pieces are queued. Cost, measured with `BenchmarkFeed` (64 KiB chunks of colored text, 160x45, no `-race`): 533 MB/s with no observer and 437 MB/s with one that publishes (the validation and the copy into the piece); both are above the 400 MB/s budget of SPEC §14 for the parser, and the publishing runs on the 50 ms timer, except for a piece that fills 64 KiB, which is published by the terminal's own goroutine.
185. **What is typed at a password prompt is never published.** `emetos.terminal.input` carries `hidden: true` with no `data` when the pty's `ECHO` is off **and** `ICANON` is on (`pty.Process.LineMode`), or when the mode cannot be read, so a password typed by the user or a client does not reach the events, and so not Watch only clients nor the log. Why both flags: `getpass`, `sudo`, `ssh`, `passwd` and `read -s` read a password in canonical mode (line by line) with the echo off. A line editor (bash's readline, zsh's line editor, fish) and a full-screen program (vim, less, htop) put the terminal in raw mode (`ICANON` off) with `ECHO` off and echo by themselves, so ECHO alone hid every key typed at an ordinary prompt and a Relay client never saw an input event for normal typing (changed 2026-10-29; the first version of this decision looked at `ECHO` alone). In raw mode the data is published, whatever `ECHO` is: the program draws what it wants on the screen anyway, which the output events carry. A paste of several lines from a client goes only to a program that turned bracketed paste on; otherwise the panel says it was not sent (each line would run as a command on a computer the user is not sitting at).
186. **The mark "Relay: <key comment>" on a terminal's tab is cleared by an event of the host (`emetos.relay.disconnected` `{by}`)** when the last session of that key name ends, so the terminal extension does not need to know about sessions. It is on a second line of the tab row so that it is never cut off; the session's banner says "typing in terminals" once the client has typed.
187. **The client's panel draws with the emulator through a small widget of Relay's own.** An extension cannot import another, so `internal/archtest` now lets `extensions/relay` import `extensions/terminal/emulator` (a package with no UI, which already had its own boundary rule). The widget has no atlas, selection, find, links or scrollback commands: it draws the rows with paragraphs, takes keys through the emulator's encoder and scrolls with the wheel. The terminal extension's panel is not reused because it is bound to a pty.
188. **A terminal made by a client (`create`) is quiet:** it does not take the keyboard or open the panel on the host, and New Terminal sends no arguments (the host's default profile, in the workspace folder; `cwd` is confined as every path of §10.19).
189. **The emulator got two changes for the serialization** (`AppendValidUTF8`, and the pen restored when DECSET 1049 leaves the alternate screen), found by the tests that compare a snapshot plus the events with the host's cells with seeded random output. The test compares cells, not the serialized bytes, because the serialization of the same screen differs in soft-wrap flags.

## 2026-10-28: step 17d.5 (shell integration; decided by the agent, to be accepted by me)

190. **The fish script is sourced with `TERM_PROGRAM` set to `vscode` for the time it loads.** VS Code's `shellIntegration.fish` refuses to run unless `$TERM_PROGRAM` is `vscode`, and Emetos's terminals have `TERM_PROGRAM=emetos`. 195. **The quick fixes of PowerShell read the lines of the command's output (`outputLines`), and Free Port types the command again without running it.** VS Code matches PowerShell's "Suggestion [cmd-not-found]" and General errors on the last lines of the buffer; Emetos reads the lines between the executed marker and the end of the output, which is the same text without the prompt. 196. **Where the files go.** The scripts are written to `$XDG_CACHE_HOME/emetos/shell-integration/<hash of their content>/` when a shell starts (a changed script gets a new folder; old ones are not removed, they are small), and the history of earlier sessions is `terminal-history.json` in the state folder (`$XDG_STATE_HOME/emetos/`), mode 0600, written atomically. 197. **Copy Output as HTML puts HTML text on the clipboard as plain text.** Glutter's clipboard has plain text only (`docs/GLUTTER-ISSUES.md`), so the HTML is not offered with the `text/html` type that a rich editor would paste as formatted text. The markup is a `pre` with the terminal's foreground and background colors and a `span` per run of cells that has a color or style.
198. **PSReadLine's modules are not bundled.** VS Code ships `psreadline` next to the pwsh script for its screen-reader mode on Windows (binaries). The script runs without them; the mode it serves is not in Emetos.
199. **The recent-command quick pick has no separators and no buttons.** `extension.QuickPickItem` has neither, so the groups of VS Code's list (this session, previous sessions, shell history) are told apart by the description of each item (the folder and `exitCode: N`, `previous session`, the history file), Alt+Enter (type without running) and the buttons that remove a command or show its output are not built. The extension API did not change for this; adding separators and buttons to the quick pick is a small API step if you want them.

## 2026-10-29: step 19.2 (SQL drivers, dialects and the schema explorer; decided by the agent, to be accepted by me)

270. **`emetos.sql` is the language pack and the driver in one extension; one driver object serves every window tab.** The SPEC names `emetos.sql` "SQL Databases", and the SQL language pack already had that id, so the pack's manifest is kept (languages, activation on startup) and extended with the command and the engines. `sql.New` is gone: `sql.NewHub(dbHub)` makes the one `Service` and driver (in `extensions.All()`, like Remote Work's hub) and `sql.FactoryOf(hub)` the extension of each tab. Each tab registers the same driver in the Databases hub, which meant two small changes to `dbconn`: `dbconn.APIDriver` / `Hub.ActionsIn(api, ...)` (a menu entry that opens an editor must open it in the tab of the menu, and `Actions` has no tab), and a driver's unregistering no longer closes the connections of an engine that another registration still serves (closing one tab used to close the connections of the others). The events `emetos.sql.connected` / `disconnected` carry `{"connection": id}` (the ID, not the name: a name is the user's text and the ID is what other extensions can look up) and are published by each tab's extension in its own scope, from the callbacks of the `Service`. `emetos.sql.` is refused to Relay clients (class `outside`), so the prefix is on the same rule line as `emetos.databases.`: a merge with step 18.1's prefixes is one line.
271. **Four engines, MySQL and MariaDB as one.** `postgres`, `mysql` ("MySQL / MariaDB"), `sqlite`, `sqlserver`. The two MySQL servers share the driver and every catalog query (`information_schema`, `SHOW CREATE`), and the real-server tests run both. The engines' own fields: "Show system databases and schemas", "Connect timeout" (default 15 s), SQL Server's named instance and SQLite's "Create the file if it does not exist". A SQLite file must be absolute or `~/...` (a relative path would depend on where Emetos was started) and is opened `mode=rw` unless the connection says create, so that Test Connection and a mistyped path never make an empty database. Every driver is used through its `driver.Connector` and `sql.OpenDB`: nothing is registered with `database/sql` (it is process-global state), and the pool is 5 connections with 2 kept idle.
272. **Levels, system objects and large schemas.** PostgreSQL: databases > schemas; MySQL: databases; SQLite: schemas (the attached files; `main` is shown, so an attached file is browsable); SQL Server: databases > schemas. PostgreSQL's connection serves one database, so browsing another one opens a pool for it with the same settings and password (the password stays in the closure of the connector, in memory, until Disconnect, as D24 allows). System databases and schemas, and SQLite's `sqlite_*` tables, are hidden unless the connection has the field "Show system databases and schemas" (DBeaver does the same; the SPEC did not say). A listing is cut at 10,000 objects and says so in a last row, so a schema with a hundred thousand tables does not build a hundred thousand rows. Partitions of a PostgreSQL table are listed as tables.
273. **TLS modes map to each driver as follows** (the mode names are PostgreSQL's): PostgreSQL passes them to pgx; MySQL builds a `tls.Config` (`verify-ca` is a custom chain check without the name, which the driver cannot do by itself); SQL Server: `disable` is `encrypt=disable`, `prefer` is `encrypt=false` with the certificate trusted (found by test: against SQL Server 2022, which encrypts by default, `encrypt=false` alone checks the self-signed certificate and fails), `require` is `encrypt=true` with the certificate trusted, and **`verify-ca` and `verify-full` both check chain and name**, because go-mssqldb has no way to check one without the other. Real servers cover disable, prefer and require; verify-ca and verify-full are tested against a local TLS server with a generated CA (right CA, other CA, wrong name).
274. **Read-only is the engine's own mechanism where it has one, run on every new connection of the pool, and only a hint for SQL Server.** `SET default_transaction_read_only = on`, `SET SESSION TRANSACTION READ ONLY`, `PRAGMA query_only = ON` run through a connector wrapper (`initConnector`) that closes the connection when a statement fails; SQLite opens `mode=ro` too. SQL Server has no such statement: `ApplicationIntent=ReadOnly` is sent (only when a database is named; go-mssqldb refuses it otherwise) but it only tells an availability group where to route the session, so a read-only SQL Server connection still accepts writes until step 19.3's own check refuses them (SPEC §10.21 "Safety" already says "and the session is set read-only where the engine has it"). The real-server test for read-only is skipped for SQL Server with that reason.
275. **Cancel runs `pg_cancel_backend` / `KILL QUERY` from another connection for PostgreSQL and MySQL, and ends the context for SQLite and SQL Server.** The SPEC says "pgx's cancel request, MySQL's KILL QUERY": pgx's default on a context that ends is to close the connection (a deadline in the past), which would end an open transaction, so pgx is also given `CancelRequestContextWatcherHandler` as a fallback, and the session id (`pg_backend_pid()`, `CONNECTION_ID()`) is read when a `Session` is taken. `go-sql-driver/mysql` closes the connection when a context ends and the server goes on with the statement, so `KILL QUERY` is the only real cancel there. The `Session` type (`Begin`, `Cancel`, `Close`) is new in this step because the dialect's cancel needs it; step 19.3 builds the query editors on it. Real servers cover a one-minute statement cancelled after two seconds and the session used afterwards, for all four.
276. **Generated statements are safe to run unfilled, and SQL Server names have three parts.** INSERT has `NULL` values with a remark per column; UPDATE and DELETE end in `WHERE key = NULL` (never true) or `WHERE <condition>` (a syntax error) when the table has no primary key; Drop is only ever text in an editor. CREATE is the catalog's own statement where the engine keeps one (MySQL, SQLite; views and routines everywhere) and is written from the catalog for PostgreSQL and SQL Server tables (columns, NOT NULL, DEFAULT, the primary key as a named constraint, foreign keys, the other indexes). SQL Server statements say `[database].[schema].[name]`, as VS Code's SQL Server extension does: a connection is in one database at a time and the explorer lists them all (found by the real-server test: `SELECT TOP (1000) * FROM [sales].[orders]` ran in `master`).
277. **New Query and Select Top 1000 open an unbound untitled `sql` editor in this step.** Binding to a connection and database, and running the statement, are step 19.3's (`// TODO(step 19.3)` marks both). The API an extension had for this did not exist: `Documents().OpenUntitled(languageID, text)` is new in `extension/` (implemented over the same code as File > New File; the fake API records it). The text is set as the first state of the document (`Document.SetText`: the undo history is empty, so Ctrl+Z cannot empty the editor), and, as VS Code's, an untitled document with a text counts as changed.
278. **The filter is the tree's typed find in "filter" mode, in the shared view.** `ui.FindMode` and `ui.FindModeFilter` are exported from `extension/ui`; `dbconn`'s view sets the mode, so the MongoDB and Redis explorers have the same filter. It filters the rows that are read; the SPEC says "lazy loading, a filter, Refresh" and a filter that read every closed table of every schema would defeat the laziness. `dbconn.Extension.TreeRows` and `ExpandTree` are exported for the tests of the engine extensions (they cannot reach the view's tree model; `dbconn`'s own tests do).
279. **The real-server tests of the SQL extension run on step 18.1's harness, and there is no SQL Server container.** `sqltest.Runner` starts a server for a test; `sqltest.Docker()`, `Podman()` and `OnHarness(h)` implement it over `containerapitest` (it replaced the first version, which called the `docker` program). The rules are the harness's: pinned images listed in one place (`containerapitest/images.go` now also lists `postgres:17.6-alpine`, `mysql:8.4.6` and `mariadb:11.4.8`), `emetos-test-<random>`, label `dev.emetos.test=1`, `127.0.0.1` only, no mounts, removed in `t.Cleanup` also when the test fails, a check that nothing labelled is left, and the password in the body of the create call (never in an argument or a log). **SQL Server has no container test**: its image starts only with `ACCEPT_EULA=Y`, and setting it would accept Microsoft's license terms on the user's behalf, which the user does not do. Its driver, its connection string, its dialect and its statements are tested against fakes only (the fake `database/sql` driver and connector), so what only a real server shows (its catalog queries against the real catalog views, `WAITFOR` cancel, TLS) is not tested; if the user accepts the terms one day, a `server` entry in `extensions/sql/docker_test.go` and an image in `images.go` are all that is needed. The image `mcr.microsoft.com/mssql/server:2022-CU20-ubuntu-22.04` was pulled into the user's engine by the first version of the tests; it is left there for the user to remove (`docker rmi`); no step removes it.
